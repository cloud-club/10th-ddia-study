# 04. OLTP와 OLAP

## 이번에 답하려는 질문

- OLTP와 OLAP는 무엇이 다르고, 왜 DB를 따로 두나?
- 분석용 DB는 왜 로우가 아니라 칼럼 단위로 저장하나?
- 칼럼 저장소는 압축·정렬·쓰기를 어떻게 처리하나?
- 집계를 미리 계산해 두면 무엇을 얻고 무엇을 잃나?

## 한 줄 요약

OLTP는 키로 레코드 몇 개를 빠르게 읽고 쓰는 일이고 OLAP는 수많은 레코드를 훑어 집계하는 일이라 병목이 서로 달라서(디스크 탐색 대 디스크 대역폭), 분석은 데이터 웨어하우스로 떼어 내고 칼럼 단위로 저장한다.

## 핵심 내용

### 1. 두 가지 접근 패턴

같은 "판매" 데이터라도 질의 모양이 완전히 다르다.

```sql
-- OLTP: 주문 한 건을 키로 찾는다. 색인을 타고 로우 몇 개만 읽는다.
SELECT * FROM orders WHERE order_id = 1042;

-- OLAP: 1년 치 판매를 훑어 집계한다. 로우는 수억 개, 칼럼은 서너 개만 쓴다.
SELECT d.weekday, p.category, SUM(f.quantity) AS total
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
JOIN dim_product p ON f.product_sk = p.product_sk
WHERE d.year = 2026 AND p.category IN ('과일', '과자')
GROUP BY d.weekday, p.category;
```

| 항목 | OLTP (트랜잭션 처리) | OLAP (분석 처리) |
|---|---|---|
| 읽기 패턴 | 질의당 적은 수의 레코드를 키로 가져옴 | 많은 레코드를 훑어 집계 |
| 쓰기 패턴 | 사용자 입력에 따른 임의 접근, 낮은 지연 | 대량 적재(ETL) 또는 이벤트 스트림 |
| 쓰는 사람 | 웹·앱을 쓰는 최종 사용자 | 의사결정을 돕는 내부 분석가 |
| 데이터가 나타내는 것 | 지금 시점의 최신 상태 | 시간이 흐르며 쌓인 사건 이력 |
| 데이터 크기 | GB ~ TB | TB ~ PB |
| 병목 | 디스크 탐색 | 디스크 대역폭 |
| 질의 수 | 매우 많고 각각 가벼움 | 적지만 각각 무거움 |

"트랜잭션"이라는 말은 초기 DB가 상거래(판매, 주문, 급여 지급)를 기록하던 데서 왔다. 여기서 트랜잭션은 ACID를 뜻하지 않는다. 일괄 처리와 달리 **클라이언트가 지연 시간이 짧은 읽기·쓰기를 한다**는 뜻이다.

### 2. 데이터 웨어하우스: 분석을 떼어 낸다

처음에는 한 DB로 둘 다 했다. 1980년대 말~1990년대 초부터 회사들이 분석을 별도 DB로 옮기기 시작했고, 그 별도 DB가 데이터 웨어하우스다.

떼어 내는 이유는 두 가지다.

- **OLTP를 지킨다.** OLTP DB는 업무 운영에 직결돼 높은 가용성과 낮은 지연이 필요하다. 분석가가 데이터 대부분을 훑는 무거운 질의를 날리면 동시에 돌던 트랜잭션이 느려진다.
- **분석에 맞게 최적화한다.** 3장 앞부분의 색인(LSM 트리, B 트리)은 키로 레코드를 찾는 데 맞춰져 있어 대량 집계에는 잘 맞지 않는다.

데이터는 **ETL**로 옮긴다.

```text
판매 DB ─┐
재고 DB ─┼─ Extract(추출) → Transform(변환·정리) → Load(적재) → 데이터 웨어하우스 ← 분석가
배송 DB ─┘
```

- 추출: 주기적으로 덤프하거나 변경 스트림을 계속 받는다.
- 변환: 분석하기 좋은 스키마로 바꾸고 데이터를 정리한다.
- 적재: 웨어하우스에 넣는다. 웨어하우스는 OLTP 데이터의 **읽기 전용 복사본**이다.

작은 회사는 OLTP 시스템이 몇 개 없고 데이터도 작아서 웨어하우스 없이 일반 SQL DB나 스프레드시트로 분석해도 된다. 웨어하우스는 대개 큰 회사에 있다.

겉으로는 OLTP DB와 웨어하우스가 둘 다 SQL 인터페이스라 비슷해 보이지만, 내부 저장소와 질의 엔진은 전혀 다르게 최적화돼 있다.

| 구분 | 예 |
|---|---|
| 상용 웨어하우스 | Teradata, Vertica, SAP HANA, ParAccel (Amazon Redshift는 ParAccel의 호스팅 버전) |
| 오픈소스 SQL-on-Hadoop | Apache Hive, Spark SQL, Cloudera Impala, Presto, Apache Tajo, Apache Drill |

### 3. 스키마: 별 모양과 눈꽃송이

OLTP는 애플리케이션마다 데이터 모델이 다양하지만, 분석은 대부분 **별 모양 스키마(차원 모델링)** 하나로 수렴한다.

```text
                 dim_date
                    │
dim_product ─── fact_sales ─── dim_store
                    │
        dim_customer   dim_promotion
```

- **사실 테이블(fact table)**: 가운데에 있다. 로우 하나가 특정 시각에 일어난 사건 하나다(판매라면 고객이 상품 하나를 산 일). 칼럼 일부는 값(판매가, 원가)이고 나머지는 차원 테이블을 가리키는 외래 키다.
- **차원 테이블(dimension table)**: 사건의 누가·무엇을·어디서·언제·어떻게·왜를 담는다. 날짜도 차원 테이블로 두는데, 그래야 공휴일 여부 같은 정보를 붙여 "공휴일과 평일 판매 비교" 같은 질의를 할 수 있다.
- **눈꽃송이 스키마**: 차원을 하위 차원으로 더 쪼갠 변형이다(`dim_product`가 브랜드·카테고리 테이블을 다시 참조). 더 정규화돼 있지만 분석가에게는 별 모양이 단순해서 더 선호된다.

분석 질의를 어렵게 만드는 건 사실 테이블의 모양이다.

- **넓다.** 칼럼이 100개를 넘는 경우가 흔하고 수백 개일 때도 있다.
- **길다.** 큰 회사는 수십 PB의 거래 이력을 웨어하우스에 두고, 대부분이 사실 테이블이다.
- 그런데 질의 하나는 그중 **칼럼 4~5개**만 쓴다.

### 4. 칼럼 지향 저장소

로우 지향 저장소는 한 로우의 값을 서로 붙여 저장한다. 그래서 칼럼 3개만 필요해도 100개짜리 로우를 통째로 디스크에서 읽어 파싱하고 걸러야 한다.

칼럼 지향 저장소는 **각 칼럼의 값을 따로 모아 저장한다.** 질의에 쓰는 칼럼 파일만 읽으면 된다.

```text
로우 지향 (로우 단위로 붙여 저장)
  로우1: 2026-11-01, 사과, 강남점, 3, 4500, ...
  로우2: 2026-11-01, 우유, 홍대점, 1, 2800, ...
  로우3: 2026-11-02, 사과, 강남점, 2, 3000, ...

칼럼 지향 (칼럼마다 파일 하나)
  date_key.col   : 2026-11-01, 2026-11-01, 2026-11-02
  product_sk.col : 사과, 우유, 사과
  store_sk.col   : 강남점, 홍대점, 강남점
  quantity.col   : 3, 1, 2
  net_price.col  : 4500, 2800, 3000
```

지켜야 할 규칙은 하나다. **모든 칼럼 파일이 로우를 같은 순서로 담는다.** 그래야 각 파일의 k번째 값을 모아 k번째 로우를 다시 만들 수 있다.

헷갈리기 쉬운 점: Cassandra·HBase의 **칼럼 패밀리**는 칼럼 지향이 아니다. 칼럼 패밀리 안에서는 한 로우의 칼럼을 로우 키와 함께 모아 저장하므로 여전히 로우 지향에 가깝다.

### 5. 칼럼 압축

한 칼럼에는 같은 값이 반복해서 나온다. 상품이 10만 종이어도 판매 로우는 수십억 개다. 이럴 때 **비트맵 부호화**가 잘 맞는다. 고유한 값마다 비트맵을 하나 두고, 로우마다 그 값이면 1을 적는다.

```text
product_sk 칼럼 : 30 30 31 68 31 30 69 69

product_sk = 30 : 1 1 0 0 0 1 0 0
product_sk = 31 : 0 0 1 0 1 0 0 0
product_sk = 68 : 0 0 0 1 0 0 0 0
product_sk = 69 : 0 0 0 0 0 0 1 1
```

- 고유한 값이 많으면 비트맵 대부분이 0이라 희소해진다. 이때는 **런 렝스 부호화**(0이 몇 개, 1이 몇 개)를 더해 훨씬 줄인다.
- 비트맵은 질의에도 그대로 쓰인다.
  - `WHERE product_sk IN (30, 68, 69)`: 비트맵 세 개를 비트 OR 한다 → `1 1 0 1 0 1 1 1`
  - `WHERE product_sk = 31 AND store_sk = 3`: 두 칼럼의 비트맵을 비트 AND 한다. 두 칼럼이 로우 순서가 같아서 가능하다.

압축은 디스크만 아끼는 게 아니다. 분석 질의의 또 다른 병목은 **메모리에서 CPU 캐시로 가는 대역폭**이다. 압축된 칼럼 덩어리는 L1 캐시에 들어가고, 분기 없는 빡빡한 루프로 한꺼번에 처리할 수 있다(벡터화 처리).

### 6. 정렬 순서

칼럼 저장소에서 로우 순서는 꼭 삽입 순서일 필요가 없다. 순서를 정해 두면 색인처럼 쓸 수 있다.

- 정렬은 **로우 단위**로 한다. 칼럼을 각자 따로 정렬하면 어느 값이 어느 로우 것인지 알 수 없게 된다.
- 정렬 키는 자주 쓰는 질의에 맞춰 고른다. 날짜 범위 질의가 많으면 첫 정렬 키를 `date_key`로 둬서 해당 구간만 읽게 한다. 둘째 키를 `product_sk`로 두면 같은 날 안에서 같은 상품이 모인다.
- 정렬은 압축도 돕는다. 첫 정렬 키는 같은 값이 길게 이어져 런 렝스 부호화로 아주 작아진다. 둘째, 셋째 키로 갈수록 값이 섞여 효과가 줄어든다.
- 질의마다 유리한 정렬이 다르므로, **같은 데이터를 여러 정렬 순서로 저장**하기도 한다(Vertica). 어차피 장애에 대비해 여러 장비에 복제하니, 복제본마다 다르게 정렬해 두고 질의에 맞는 것을 고른다.

### 7. 칼럼 저장소에 쓰기

압축과 정렬은 읽기를 빠르게 하지만 쓰기를 어렵게 한다.

- B 트리처럼 제자리에서 고칠 수 없다. 정렬된 테이블 중간에 로우 하나를 넣으려면 그 뒤의 모든 칼럼 파일을 다시 써야 한다.
- 해법은 3장 앞부분의 **LSM 트리**다. 쓰기는 먼저 메모리의 정렬된 구조에 모으고, 충분히 쌓이면 디스크의 칼럼 파일과 병합해 새 파일로 한꺼번에 쓴다.
- 질의는 디스크의 칼럼 데이터와 메모리의 최근 쓰기를 둘 다 보고 합쳐야 한다. 이 일은 질의 최적화기가 감춰 준다.

### 8. 미리 계산해 두기: 구체화 뷰와 데이터 큐브

`COUNT`, `SUM`, `AVG` 같은 집계를 여러 질의가 반복해서 쓴다면 미리 계산해 캐시해 둘 수 있다.

- **구체화 뷰**: 질의 결과를 디스크에 실제로 써 둔 복사본이다. 일반 뷰(가상 뷰)는 질의를 짧게 쓰는 방법일 뿐이라 읽을 때마다 원래 질의를 실행한다.
- 원본이 바뀌면 구체화 뷰도 갱신해야 해서 **쓰기가 비싸진다.** 그래서 OLTP에서는 잘 안 쓰고, 읽기가 많은 웨어하우스에 더 맞는다.
- **데이터 큐브(OLAP 큐브)**: 차원별로 묶은 집계의 격자다.

날짜와 상품 두 차원이면 표 하나가 된다. 칸은 그 날짜·상품 조합의 판매 합계이고, 행과 열을 따라 다시 합하면 차원 하나를 줄인 집계가 나온다.

| | 사과 | 우유 | 빵 | 날짜별 합계 |
|---|---|---|---|---|
| 11-01 | 10 | 20 | 5 | 35 |
| 11-02 | 15 | 10 | 10 | 35 |
| 상품별 합계 | 25 | 30 | 15 | 70 |

차원이 다섯 개(날짜, 상품, 매장, 프로모션, 고객)면 5차원 큐브가 된다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 데이터 큐브 | 미리 계산돼 있어 해당 질의가 매우 빠름 | 차원에 없는 조건으로는 못 자름 |

예를 들어 "10만 원 넘는 상품이 매출에서 차지하는 비율"은 가격이 차원이 아니라서 큐브로는 답할 수 없다. 그래서 웨어하우스는 원본 데이터를 최대한 남겨 두고, 큐브는 특정 질의를 빠르게 하는 보조 수단으로만 쓴다.

### 9. 정리

| | OLTP | OLAP |
|---|---|---|
| 저장소 엔진 | 로그 구조(LSM 트리) 또는 제자리 갱신(B 트리) | 칼럼 지향 저장소 |
| 색인 | 키로 레코드를 찾는 색인이 핵심 | 색인보다 압축과 순차 스캔이 핵심 |
| 최적화 목표 | 디스크 탐색을 줄인다 | 읽어야 할 데이터 양을 줄인다 |
| 스키마 | 애플리케이션마다 다양 | 별 모양·눈꽃송이 |

## 남은 질문

- 책은 OLTP와 OLAP를 나누는데, 한 DB에서 둘 다 처리한다는 HTAP 계열(TiDB, SingleStore 등)은 로우 저장소와 칼럼 저장소를 내부에서 어떻게 같이 두나?
- BigQuery·Snowflake처럼 저장과 연산을 분리한 클라우드 웨어하우스에서도 "여러 정렬 순서로 복제"가 쓰이나, 아니면 파티셔닝·클러스터링으로 대체됐나?
- ETL 대신 원본을 먼저 적재하고 웨어하우스 안에서 변환하는 ELT가 요즘 흔한데, 무엇이 달라져서 순서가 바뀌었나?
- PostgreSQL 같은 OLTP DB에 칼럼 저장 확장을 붙이면 어디까지 분석을 감당할 수 있나?
