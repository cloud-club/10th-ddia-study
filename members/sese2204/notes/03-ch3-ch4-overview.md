# 03. 3·4장 개요

## 이번에 답하려는 질문

- 3장 「저장소와 검색」과 4장 「부호화와 발전」은 각각 무슨 문제를 다루나?
- 저장소 엔진의 두 계열(LSM 트리, B 트리)은 무엇이 다른가?
- 신·구 버전 코드가 같이 돌아갈 때 데이터 형식은 어떻게 호환되나?

## 한 줄 요약

3장은 DB가 데이터를 디스크에 쓰고 다시 찾는 방법(색인은 읽기를 빠르게 하지만 쓰기를 느리게 한다)을, 4장은 코드가 바뀌어도 예전 데이터와 새 데이터를 서로 읽을 수 있게 하는 부호화 형식을 다룬다.

## 핵심 내용

### 1. 3장: 저장소 엔진의 두 계열

| | 로그 구조 (LSM 트리) | 페이지 지향 (B 트리) |
|---|---|---|
| 쓰기 방식 | 추가 전용 파일에 순차 기록, 덮어쓰지 않음 | 고정 크기 페이지(보통 4KB)를 제자리에서 덮어씀 |
| 구조 | 멤테이블(메모리 정렬 구조) → 가득 차면 SS테이블(키로 정렬된 파일)로 내보냄 → 백그라운드에서 병합·컴팩션 | 루트에서 리프까지 페이지 참조를 따라감, 깊이는 보통 3~4단계 |
| 장애 복구 | 멤테이블용 별도 로그 | WAL(쓰기 전 로그) |
| 강점 | 쓰기 처리량, 압축률 | 읽기 성능 예측 가능, 키가 한 곳에만 있어 트랜잭션 잠금이 쉬움 |
| 약점 | 컴팩션이 읽기·쓰기를 방해할 수 있음, 없는 키 조회가 느림(블룸 필터로 보완) | 쓰기 증폭(WAL과 페이지에 두 번 씀), 파편화 |
| 예 | LevelDB, RocksDB, Cassandra, HBase | 대부분의 관계형 DB |

MongoDB가 어느 계열인지는 [05번 노트](05-mongodb-storage-engine-and-grpc.md)에 따로 정리했다.

### 2. 3장: 그 밖의 색인

- **해시 색인**: 가장 단순한 형태로, 메모리 해시 맵에 키별 파일 오프셋을 둔다(Bitcask). 키가 메모리에 다 들어가야 하고 범위 질의가 안 된다.
- **보조 색인**: 기본 키가 아닌 칼럼으로 찾는다. 키가 고유하지 않을 수 있다.
- **클러스터드 색인과 커버링 색인**: 색인 안에 로우 전체를 저장하면 클러스터드 색인, 일부 칼럼만 넣으면 커버링 색인이다. 읽기는 빨라지고 쓰기와 저장 공간 부담은 늘어난다.
- **다중 칼럼 색인**: 여러 칼럼을 이어 붙인 결합 색인, 위도·경도처럼 여러 차원을 한꺼번에 찾는 다차원 색인(R 트리).
- **전문 검색·퍼지 색인**: 철자가 조금 다른 단어까지 찾는다.
- **인메모리 DB**: 빠른 이유는 디스크를 안 읽어서가 아니다. 메모리 자료구조를 디스크 형식으로 부호화하는 오버헤드가 없어서다.

### 3. 3장: OLTP와 OLAP

| | OLTP | OLAP |
|---|---|---|
| 읽기 | 키로 소수 레코드 조회 | 대량 레코드 집계 |
| 쓰기 | 사용자 입력에 따른 임의 접근, 낮은 지연 | 대량 적재(ETL) 또는 이벤트 스트림 |
| 병목 | 디스크 탐색 | 디스크 대역폭 |
| 사용자 | 최종 사용자 | 분석가 |

- **데이터 웨어하우스**: OLTP에 영향을 주지 않으려고 분석용 DB를 따로 두고 ETL로 채운다.
- **스키마**: 가운데 사실 테이블을 차원 테이블이 둘러싸는 별 모양 스키마를 쓴다.
- **칼럼 지향 저장소**: 칼럼 단위로 저장해 필요한 칼럼만 읽고, 반복되는 값을 압축한다.
- **구체화 뷰와 데이터 큐브**: 자주 쓰는 집계를 미리 계산해 둔다.

자세한 내용은 [04번 노트](04-oltp-olap.md)에 있다.

### 4. 4장: 왜 호환성이 필요한가

애플리케이션은 계속 바뀌고, 신·구 버전이 동시에 돌아간다.

- 서버는 순회식 업그레이드로 일부 노드만 새 버전인 시간이 생긴다.
- 클라이언트는 사용자가 업데이트를 안 할 수 있다.

그래서 호환성이 양방향으로 필요하다.

- **하위 호환성**: 새 코드가 예전 데이터를 읽을 수 있다.
- **상위 호환성**: 예전 코드가 새 데이터를 읽을 수 있다. 모르는 필드를 무시해야 해서 더 어렵다.

### 5. 4장: 부호화 형식

| 형식 | 특징 | 스키마 발전 방법 |
|---|---|---|
| 언어 내장 (Java Serializable, pickle) | 특정 언어에 묶이고, 보안·버전 관리·성능이 나쁨 | 쓰지 않는 게 좋음 |
| JSON·XML·CSV | 사람이 읽을 수 있고 널리 쓰임. 숫자 정밀도가 모호하고 이진 문자열을 지원하지 않음 | 명시적 규칙 없음 |
| Thrift·프로토콜 버퍼 | 스키마 필수, 필드 이름 대신 태그 번호로 부호화 | 새 필드는 새 태그 번호로, optional이거나 기본값이 있어야 함. 태그 번호는 못 바꿈 |
| Avro | 태그 번호도 없어 가장 작음. 쓰기 스키마와 읽기 스키마를 따로 두고 필드 이름으로 맞춤 | 기본값이 있는 필드만 추가·삭제 가능 |

- Avro는 태그 번호가 없어서 DB 스키마에서 자동 생성하는 동적 스키마에 잘 맞는다. 대신 읽는 쪽이 쓰기 스키마를 알아야 한다. 파일 헤더, 스키마 레지스트리의 버전 번호, 연결 시 협상 중 하나로 전달한다.
- 스키마 기반 이진 형식의 장점은 네 가지다. 크기가 작고, 스키마가 항상 최신인 문서 역할을 하고, 배포 전에 호환성을 검사할 수 있고, 정적 타입 코드를 생성할 수 있다.

### 6. 4장: 데이터가 흐르는 세 가지 방식

**데이터베이스를 거쳐서**

- 쓰는 프로세스가 부호화하고 나중에 읽는 프로세스가 복호화한다.
- 데이터가 코드보다 오래 산다. 5년 전에 쓴 데이터가 그대로 남아 있다.
- 예전 코드가 새 필드를 모른 채 읽고 다시 쓰면 그 필드가 사라질 수 있다.

**서비스 호출(REST, RPC)을 거쳐서**

- REST는 HTTP의 기능을 그대로 쓰는 설계 철학이고, SOAP은 XML 기반 프로토콜이다.
- RPC는 원격 호출을 로컬 함수처럼 보이게 하려 하지만 근본적으로 다르다.
  - 타임아웃이 나면 결과를 알 수 없다.
  - 재시도하면 중복 실행될 수 있어서 멱등성이 필요하다.
  - 지연 시간이 들쭉날쭉하다.
  - 인자를 전부 부호화해야 한다.
- 서버를 먼저 업그레이드한다고 가정하면 요청은 하위 호환성, 응답은 상위 호환성만 있으면 된다.

그런데도 RPC를 쓰는 이유는 [05번 노트](05-mongodb-storage-engine-and-grpc.md)에 정리했다.

**비동기 메시지 전달을 거쳐서**

- 메시지 브로커(Kafka, RabbitMQ)가 중간에 있다.
- 수신자가 죽어 있어도 버퍼링하고, 송신자와 수신자를 분리하고, 여러 수신자에게 보낼 수 있다.
- 단방향이라 응답은 별도 채널로 받는다.
- 액터 모델(Akka, Erlang)도 여기에 속한다.
