# 5장 복제

- 동기·비동기 복제와 Failover를 직접 눌러보며 정리한 인터랙션 페이지: <https://claude.ai/artifact/1utJDMy9QPscMmc7mEK8Da>
- 같은 주제의 딥다이브 노트: [replication-failover.md](replication-failover.md)

## 이번에 답하려는 질문

- 같은 데이터를 여러 서버에 두면 데이터가 바뀔 때 어떻게 맞출까?
- 복제가 늦어지면 사용자는 어떤 이상한 화면을 보게 될까?
- 여러 곳에서 동시에 쓰면 충돌은 어떻게 감지하고 해결할까?

## 한 줄 요약

복제의 어려움은 데이터가 바뀔 때 생긴다. 단일 리더, 다중 리더, 리더 없는 복제 세 방식이 있고, 각각 일관성과 가용성·지연 사이에서 다른 선택을 한다. 비동기 복제를 쓰면 복제 지연과 쓰기 충돌을 앱이나 DB가 직접 다뤄야 한다.

## 핵심 내용

### 0. 복제를 하는 이유

복제는 같은 데이터의 복사본을 네트워크로 연결된 여러 서버에 두는 것이다. 이유는 세 가지다.

- 사용자와 가까운 곳에 데이터를 둬서 지연을 줄인다.
- 서버 하나가 죽어도 서비스를 계속한다.
- 읽기 요청을 여러 서버로 나눈다.

이 장은 데이터가 서버 한 대에 다 들어간다고 가정한다. 데이터를 나눠 담는 파티셔닝은 6장에서 다룬다. 데이터가 안 바뀌면 한 번 복사하면 끝이므로, 이 장의 주제는 계속 바뀌는 데이터를 모든 복사본에 맞추는 방법이다. 복사본을 가진 서버 하나하나를 복제 서버(replica)라고 부른다.

### 1. 단일 리더 복제

#### 동작

복제 서버 하나를 리더로 정하고, 쓰기는 리더만 받는다. 나머지 팔로워는 리더가 보내는 복제 로그를 받아 같은 순서로 적용한다. 읽기는 리더와 팔로워 어디서든 할 수 있다. MySQL, PostgreSQL, MongoDB, Kafka가 이 방식을 쓴다.

#### 동기와 비동기

| | 동기 | 비동기 |
|---|---|---|
| 리더가 성공을 돌려주는 시점 | 팔로워가 받았다고 확인한 뒤 | 자기 디스크에 쓴 직후 |
| 장점 | 팔로워가 항상 최신이고, 리더가 죽어도 데이터가 남는다 | 팔로워가 죽거나 느려도 쓰기가 계속된다 |
| 단점 | 팔로워 하나가 응답하지 않으면 쓰기가 멈춘다 | 리더가 죽으면 아직 전달 안 된 쓰기가 사라진다 |

모든 팔로워를 동기로 두면 한 대만 고장 나도 전체가 멈춘다. 그래서 팔로워 하나만 동기로 두고 나머지는 비동기로 두는 반동기(semi-synchronous) 설정을 쓴다. 실무에서 가장 흔한 건 완전 비동기다. 성공을 받은 쓰기도 잃을 수 있지만, 팔로워가 많거나 지역이 나뉜 환경에서는 이쪽을 많이 쓴다.

#### 새 팔로워 추가

파일을 그냥 복사하면 복사하는 동안에도 쓰기가 들어와서 시점이 섞인다. 그래서 이렇게 한다.

1. 리더를 잠그지 않고 특정 시점의 스냅숏을 뜬다. MySQL은 Xtrabackup 같은 도구를 쓴다.
2. 스냅숏을 새 팔로워에 복사한다.
3. 팔로워가 스냅숏 시점 이후의 변경을 리더에게 요청한다. 이 위치를 PostgreSQL은 LSN, MySQL은 binlog 좌표라고 부른다.
4. 밀린 변경을 다 적용하면 따라잡은 것이고, 그 뒤로는 실시간 변경을 받는다.

#### 노드 장애

- 팔로워 장애: 팔로워는 받은 변경 로그를 디스크에 보관한다. 재시작하면 마지막 처리 위치부터 다시 요청해서 따라잡는다.
- 리더 장애(Failover): 팔로워 하나를 새 리더로 올리고 클라이언트와 다른 팔로워가 새 리더를 보게 한다. 자동으로 하면 세 단계다.
  1. 리더가 죽었는지 판단한다. 확실히 알 방법이 없어 타임아웃(예: 30초)을 쓴다.
  2. 가장 최신 데이터를 가진 팔로워를 새 리더로 고른다. 투표나 컨트롤러 노드가 정한다.
  3. 쓰기를 새 리더로 보내고, 돌아온 예전 리더는 팔로워로 내린다.

Failover는 잘못될 일이 많다.

- 비동기라면 새 리더가 예전 리더의 마지막 쓰기를 못 받았을 수 있다. 보통 그 쓰기를 버린다.
- DB 밖 시스템과 어긋날 수 있다. 깃허브 사례에서는 뒤처진 팔로워가 리더가 되면서 이미 쓴 자동 증가 PK를 다시 발급했고, 그 PK를 함께 쓰던 Redis와 어긋나 다른 사용자의 데이터가 보였다.
- 두 노드가 모두 자기가 리더라고 믿는 스플릿 브레인이 생길 수 있다. 하나를 강제로 끄는 펜싱(STONITH)을 두지만, 잘못 만들면 둘 다 꺼진다.
- 타임아웃이 길면 복구가 늦고, 짧으면 잠깐 느려진 리더를 죽었다고 보고 불필요한 Failover를 한다.

그래서 자동 Failover를 지원해도 일부러 수동으로 하는 팀이 있다.

#### 복제 로그 구현 방식

| 방식 | 보내는 것 | 장점 | 문제 |
|---|---|---|---|
| 구문 기반 | 실행한 SQL 문 | 단순하다 | `NOW()`, `RAND()`, 자동 증가, 트리거처럼 서버마다 결과가 달라질 수 있는 구문이 있다 |
| WAL 배송 | 저장 엔진의 WAL 그대로 | 추가 작업이 없다 | 디스크 블록 수준이라 저장 엔진 형식에 묶인다. 리더와 팔로워 버전이 다르면 복제가 안 될 수 있어 무중단 업그레이드가 어렵다 |
| 논리적(로우 기반) 로그 | 로우 단위 변경 (INSERT는 새 값, DELETE는 PK, UPDATE는 PK와 새 값) | 버전이나 저장 엔진이 달라도 된다. 외부 시스템이 읽기 쉬워 CDC에 쓴다 | 로그가 클 수 있다 |
| 트리거 기반 | 앱이 정한 변경 | 일부만 복제하거나 다른 DB로 보내는 등 유연하다 | 오버헤드와 버그가 많다 |

MySQL은 5.1 이전에 구문 기반을 썼고, 지금은 비결정적인 구문이 있으면 로우 기반으로 바꾼다. PostgreSQL과 Oracle은 WAL 배송을 쓴다. MySQL binlog를 로우 기반으로 설정하면 논리적 로그 방식이다.

### 2. 복제 지연 문제

읽기가 많은 서비스는 팔로워를 늘려 읽기를 나눈다. 이 구조는 사실상 비동기 복제에서만 가능하고, 비동기 팔로워는 리더보다 뒤처질 수 있다. 쓰기를 멈추고 기다리면 결국 따라잡는데, 이를 최종적 일관성(eventual consistency)이라고 한다. "최종적"이 얼마나 걸리는지에는 제한이 없어서 부하가 크면 몇 초에서 몇 분까지 늘어난다. 비동기로 복제하는 RDB 팔로워도 마찬가지다.

지연이 길면 생기는 대표적인 문제는 세 가지다.

| 보장 | 문제 상황 | 해결 방법 |
|---|---|---|
| 자신이 쓴 내용 읽기 (read-after-write) | 댓글을 쓰고 새로고침했는데, 아직 반영 안 된 팔로워에서 읽어서 댓글이 안 보인다 | 본인이 수정할 수 있는 데이터는 리더에서 읽는다. 마지막 수정 후 1분 동안은 리더에서 읽는다. 클라이언트가 마지막 쓰기 시점을 기억하고 그 시점까지 반영된 서버에서만 읽는다 |
| 단조 읽기 (monotonic read) | 새로고침을 두 번 했는데 처음엔 보이던 댓글이 두 번째엔 사라진다 | 한 사용자는 항상 같은 복제 서버에서 읽게 한다. 예: 사용자 ID 해시로 서버를 고른다 |
| 일관된 순서로 읽기 (consistent prefix read) | "배포 끝났나요?"보다 "네, 끝났어요"가 먼저 보인다 | 인과관계가 있는 쓰기는 같은 파티션에 기록한다. 파티셔닝된 DB에서 주로 생긴다 |

웹과 앱처럼 여러 기기에서 접속하면, 마지막 쓰기 시점을 서버에서 중앙 관리해야 한다. 기기마다 다른 데이터센터로 갈 수도 있어서 리더에서 읽어야 한다면 같은 데이터센터로 보내야 한다.

앱 코드로 이런 보장을 직접 만들면 복잡하고 실수하기 쉽다. 그래서 DB가 강한 보장을 해 주는 트랜잭션이 있다. 분산 DB로 넘어오며 많은 시스템이 "트랜잭션은 비싸니 최종적 일관성을 써야 한다"며 트랜잭션을 버렸는데, 책은 이 주장이 지나치게 단순하다고 본다. 7장과 9장에서 다시 다룬다.

### 3. 다중 리더 복제

쓰기를 받는 노드를 여러 개 두고, 각 리더가 다른 리더의 팔로워 역할도 한다. 한 데이터센터 안에서는 복잡도에 비해 이득이 적어 거의 쓰지 않는다. 쓸 만한 곳은 세 가지다.

- 다중 데이터센터: 데이터센터마다 리더를 두면 쓰기를 가까운 곳에서 처리하고, 데이터센터 하나가 죽거나 사이 네트워크가 끊겨도 각자 동작한다.
- 오프라인 클라이언트: 휴대폰 캘린더처럼 인터넷이 없을 때도 쓰기를 받아야 하면, 기기마다 로컬 DB가 리더 역할을 한다. CouchDB가 이런 용도로 설계됐다.
- 실시간 협업 편집: 구글 독스처럼 변경을 로컬에 먼저 적용하고 나중에 다른 사용자에게 보낸다.

#### 쓰기 충돌

같은 게시글 제목을 두 리더에서 동시에 "점검 공지"와 "이벤트 공지"로 바꾸면 둘 다 성공하고, 나중에 복제하면서 충돌을 발견한다. 동기로 감지하면 다중 리더의 장점이 사라진다.

- 충돌 회피: 같은 레코드의 쓰기는 항상 같은 리더로 보낸다. 사용자마다 홈 데이터센터를 정하는 식이다. 가장 권장되지만, 홈을 바꾸면 깨진다.
- 수렴시키기: 모든 복제본이 결국 같은 값이 되게 한다.
  - 가장 큰 ID나 타임스탬프의 쓰기를 남긴다(LWW, last write wins). 데이터가 사라진다.
  - 값을 합친다. 예: "이벤트 공지/점검 공지"
  - 충돌을 그대로 저장해 두고 나중에 앱이나 사용자가 해결한다.
- 사용자 정의 해결 로직: 쓰기 시점에 핸들러가 처리하거나(Bucardo), 읽기 시점에 여러 버전을 앱에 돌려준다(CouchDB). 충돌 해결은 보통 트랜잭션이 아니라 로우나 문서 단위다. 아마존 장바구니는 추가된 상품만 살리고 삭제는 살리지 않아서, 지운 상품이 다시 나타나는 문제가 있었다.
- 자동 해결 연구: CRDT(집합, 카운터 등을 알아서 합치는 자료구조, Riak 2.0), Git처럼 히스토리로 삼중 병합하는 자료구조, 구글 독스가 쓰는 운영 변환(OT).

회의실 예약처럼 같은 시간대에 두 리더에서 예약이 들어오는 경우도 충돌이다. 이런 충돌은 감지하기 더 어렵다.

#### 토폴로지

| 토폴로지 | 방식 | 특징 |
|---|---|---|
| 원형 | 각 노드가 다음 노드 하나에 전달 | MySQL 기본. 한 노드가 죽으면 흐름이 끊긴다 |
| 별 모양 | 루트 노드가 모두에게 전달 | 루트가 죽으면 끊긴다 |
| 전체 연결 | 모두가 모두에게 전달 | 가장 흔하고 장애에 강하다. 메시지가 서로 추월해 순서가 바뀔 수 있다 |

원형과 별 모양은 쓰기에 거쳐 간 노드 ID를 붙여 무한 루프를 막는다. 전체 연결에서는 INSERT보다 그 로우의 UPDATE가 먼저 도착할 수 있다. 서버 시계를 믿을 수 없어 타임스탬프로는 해결되지 않고, 버전 벡터가 필요하다. 실제 다중 리더 도구 중에는 충돌 감지를 제대로 하지 않는 것도 있어서 문서를 읽고 직접 테스트해야 한다.

### 4. 리더 없는 복제

리더 없이 모든 복제 서버가 쓰기를 직접 받는다. 아마존 내부 시스템 다이나모가 쓰면서 다시 유행했고, Riak, Cassandra, Voldemort가 이를 따른 오픈소스다. 이름은 비슷하지만 AWS DynamoDB는 단일 리더 방식이다.

#### 노드가 죽었을 때

클라이언트가 쓰기를 복제 서버 3대에 동시에 보내고, 2대가 OK를 주면 성공으로 본다. 장애 복구 과정이 필요 없다. 읽기도 여러 서버에 보내서 버전 번호로 최신 값을 고른다. 빠진 데이터는 두 가지로 채운다.

- 읽기 복구: 읽을 때 오래된 값을 준 서버에 최신 값을 다시 써 준다. 자주 읽는 값에 효과적이다.
- 안티 엔트로피: 백그라운드 프로세스가 서버 간 차이를 찾아 복사한다. 순서가 없어서 늦게 반영될 수 있다.

안티 엔트로피가 없으면 거의 안 읽히는 값은 일부 서버에서 계속 빠져 있다.

#### 정족수

n은 복제 서버 수, w는 쓰기 성공에 필요한 확인 수, r은 읽기에 필요한 응답 수다. w + r > n이면 쓴 서버와 읽은 서버가 최소 한 대 겹쳐서 읽은 값 중 하나는 최신이다.

- n=3, w=2, r=2면 1대가 죽어도 된다.
- n=5, w=3, r=3이면 2대가 죽어도 된다.
- 읽기가 많으면 w=n, r=1로 둔다. 읽기는 빨라지지만 1대만 죽어도 쓰기가 실패한다.

요청은 보통 n대 모두에 보내고, w와 r은 그중 몇 대의 응답을 기다릴지를 뜻한다.

w + r > n이어도 오래된 값을 읽는 경우가 있다.

- 느슨한 정족수를 쓰면 쓴 서버와 읽은 서버가 겹치지 않을 수 있다.
- 동시에 두 쓰기가 오면 순서를 모른다. LWW로 고르면 시계 차이 때문에 쓰기를 잃을 수 있다.
- 쓰기와 읽기가 동시에 일어나면 쓰기가 일부 서버에만 반영된 상태에서 읽을 수 있다.
- 일부 서버에서만 성공해서 실패로 보고된 쓰기도 그 서버에서는 롤백되지 않는다.
- 새 값을 가진 서버가 죽고 옛 값에서 복구되면 새 값을 가진 서버 수가 w보다 줄어든다.

그래서 다이나모 스타일 DB는 최종적 일관성을 받아들이는 용도에 맞다. 오래된 값을 읽을 확률은 조절할 수 있지만 절대 보장은 못 한다.

#### 최신성 모니터링

리더 기반은 리더와 팔로워의 로그 위치 차이로 복제 지연을 잴 수 있다. 리더 없는 방식은 쓰기 순서가 없어서 재기 어렵고, 읽기 복구만 쓰면 잘 안 읽히는 값이 얼마나 오래됐는지 제한이 없다. 책은 "최종적"을 숫자로 잴 수 있어야 운영할 수 있다고 말한다.

#### 느슨한 정족수와 암시된 핸드오프

네트워크가 끊겨 그 값의 홈 노드 n대 중 w대에 닿지 못하면 정족수를 채울 수 없다. 이때 닿을 수 있는 다른 노드에 임시로 쓰는 것이 느슨한 정족수(sloppy quorum)다. 네트워크가 복구되면 임시로 받은 쓰기를 홈 노드로 넘기는데, 이를 암시된 핸드오프(hinted handoff)라고 한다. 쓰기 가용성은 높아지지만, w + r > n이어도 최신 값을 읽는다는 보장이 없다. Riak은 기본으로 켜져 있고, Cassandra와 Voldemort는 꺼져 있다.

#### 다중 데이터센터

Cassandra와 Voldemort는 n에 모든 데이터센터의 노드를 포함하고, 클라이언트는 보통 로컬 데이터센터의 정족수만 기다린다. 다른 데이터센터로는 보통 비동기로 보낸다. Riak은 n을 한 데이터센터 안의 수로 보고, 데이터센터 간 복제는 다중 리더처럼 백그라운드에서 한다.

### 5. 동시 쓰기 감지

다이나모 스타일은 같은 키에 동시에 쓰는 걸 허용해서, 네트워크 지연에 따라 노드마다 쓰기가 다른 순서로 도착한다. 각자 받은 순서대로 덮어쓰면 노드끼리 값이 영원히 다르다.

#### LWW

쓰기마다 타임스탬프를 붙이고 가장 큰 값만 남긴다. 모든 복제본이 같은 값으로 수렴하지만, 성공 응답을 받은 쓰기가 조용히 사라진다. Cassandra에서는 유일한 충돌 해결 방식이고 Riak에서는 선택 기능이다. 안전하게 쓰려면 키를 한 번만 쓰고 수정하지 않는다. Cassandra는 키로 UUID를 써서 쓰기마다 새 키를 만들기를 권한다.

#### 이전 발생 관계와 동시성

B가 A를 알거나 A를 바탕으로 했다면 A는 B의 이전 발생(happens-before)이다. 예를 들어 INSERT한 로우를 UPDATE로 +1 했다면 INSERT가 이전 발생이다. 둘 다 서로를 모르면 동시(concurrent)다. 동시인지는 실제 시각이 아니라 서로 알았는지로 정한다. 하나가 먼저면 나중 쓰기가 덮어써도 되고, 동시면 충돌로 보고 해결해야 한다.

#### 버전 번호로 판단하기

두 사람이 같은 공유 쇼핑 목록에 동시에 추가하는 상황으로 보면 이렇다.

| 단계 | 누가 | 보낸 값 (기반 버전) | 서버 상태 |
|---|---|---|---|
| 1 | A | [사과] (없음) | v1 [사과] |
| 2 | B | [우유] (없음) | v1 [사과], v2 [우유]. 동시라서 둘 다 보관 |
| 3 | A | [사과, 빵] (v1 기반) | v1을 덮어씀. v2 [우유], v3 [사과, 빵] |
| 4 | B | [사과, 우유, 계란] (v2 기반) | v2를 덮어씀. v3 [사과, 빵], v4 [사과, 우유, 계란] |

- 서버는 키마다 버전 번호를 두고 쓸 때마다 올린다.
- 읽을 때 서버는 덮어써지지 않은 값을 모두 돌려준다. 클라이언트는 쓰기 전에 먼저 읽는다.
- 쓸 때 클라이언트는 이전에 읽은 버전 번호를 같이 보내고, 읽은 값을 합쳐서 보낸다.
- 서버는 받은 버전 이하의 값은 덮어쓰고, 그보다 높은 버전은 동시에 쓴 것이라 남긴다.

이렇게 하면 어떤 쓰기도 자동으로 사라지지 않는다.

#### 형제 병합

동시에 쓰인 값들을 Riak에서는 형제(sibling)라고 하고, 클라이언트가 합쳐야 한다. 쇼핑 목록이라면 합집합이 자연스럽다. 그런데 한쪽에서 지운 항목이 다른 형제에 남아 있으면 합집합에서 다시 살아난다. 그래서 삭제할 때 실제로 지우지 않고 삭제 표시(툼스톤)를 남긴다. 3장 컴팩션의 툼스톤과 같은 개념이다. 앱 코드로 병합하기는 어려워서 CRDT 같은 자동 병합 자료구조를 쓴다.

#### 버전 벡터

복제본이 여러 개면 키당 버전 번호 하나로는 부족하다. 복제본마다 버전 번호를 따로 두고 다른 복제본의 번호도 추적하는데, 이 묶음이 버전 벡터다. 예: {노드1: 3, 노드2: 1, 노드3: 2}. 읽을 때 받아서 쓸 때 다시 보내면, DB가 덮어쓰기와 동시 쓰기를 구분한다. Riak 2.0은 개선된 도티드 버전 벡터를 쓴다. 벡터 시계와 비슷하지만 같지 않고, 복제본 상태를 비교할 때 맞는 건 버전 벡터다.

### 6. 정리

| | 쓰기를 받는 곳 | 장점 | 단점 |
|---|---|---|---|
| 단일 리더 | 리더 하나 | 이해하기 쉽고 충돌이 없다 | 리더 장애에 약하고 팔로워 읽기는 오래될 수 있다 |
| 다중 리더 | 여러 리더 | 데이터센터 장애, 네트워크 문제, 지연에 강하다 | 쓰기 충돌을 해결해야 하고 일관성 보장이 약하다 |
| 리더 없음 | 여러 노드에 동시에 | 장애 복구가 필요 없고 느린 노드를 견딘다 | 일관성 보장이 약하고 동시 쓰기를 직접 다뤄야 한다 |

비동기 복제는 평소엔 빠르지만, 지연이 커지거나 리더가 죽으면 성공한 데이터를 잃을 수 있다. 복제 지연에는 자신이 쓴 내용 읽기, 단조 읽기, 일관된 순서로 읽기라는 보장이 필요하다. 다중 리더와 리더 없는 방식은 동시 쓰기를 허용하므로 이전 발생인지 동시인지 판단하고 병합해야 한다.

## 백엔드 실무와 연결

- MySQL 리더 1대와 RDS Read Replica 여러 대를 두는 구성이 단일 리더 + 비동기 복제다. Read Replica는 백업이 아니라 읽기 분산용이다.
- 글을 쓰고 바로 목록을 조회하면 안 보이는 버그가 자신이 쓴 내용 읽기 문제다. 쓰기 직후 조회는 리더로 보내서 해결한다.
- Cassandra의 `CONSISTENCY QUORUM` 설정이 이 장의 w, r이다.
- 커밋 응답 직전에 연결이 끊기면 앱은 성공 여부를 모른다. 쓰기 재시도는 멱등 키로 다룬다. 자세한 내용은 딥다이브 노트에 정리했다.
