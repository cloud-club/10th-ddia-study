# DDIA 3·4장 — 질문과 혼동을 중심으로 정리

책을 읽으며 질문한 내용과 추가로 정리한 4장 복습 노트를 묶었다. 장 전체의 요약이 아니라, 어려웠던 개념의 연결과 혼동하기 쉬운 차이를 중심으로 정리했다. 주문·사용자 데이터 예시는 이해를 위한 재구성이며, 제품별 동작은 마지막 참고 자료와 구분해 읽는다.

## 한 줄 요약

칼럼 저장·압축부터 스키마 호환성과 원격 통신까지, DDIA 3·4장에서 혼동했던 개념의 차이와 연결을 질문 중심으로 정리한다.

## 3장. Storage and Retrieval

### 1. Column-oriented Storage와 Column Compression

**질문:** 왜 같은 칼럼끼리 모으면 압축에 유리할까?

주문 데이터를 행별로 저장하면 한 주문의 날짜·상품·금액이 붙어 있다. 칼럼별로 저장하면 여러 주문의 날짜끼리, 상품끼리, 금액끼리 모인다.

```text
Row-oriented
[01일, A, 50] [01일, B, 80] [02일, A, 120] [02일, B, 200]

Column-oriented
날짜: [01일, 01일, 02일, 02일]
상품: [   A,    B,    A,    B]
금액: [  50,   80,  120,  200]
```

칼럼끼리 모으면 같은 자료형과 비슷한 값이 반복되기 쉽다. 반복 패턴에 맞는 압축을 적용하기 좋아진다. 다만 칼럼으로 저장하는 것 자체가 압축은 아니다.

상품별 매출을 계산할 때는 상품과 금액 칼럼만 읽으면 된다. 배송 주소나 주문 메모까지 읽을 필요가 없다. **칼럼 저장은 불필요한 칼럼을 읽는 비용을 줄이고, 압축은 필요한 칼럼의 바이트 수까지 줄인다.**

#### Bitmap Encoding과 Run-Length Encoding

상품 칼럼이 다음과 같다고 하자.

```text
상품: A B A A C B A C

A:    1 0 1 1 0 0 1 0
B:    0 1 0 0 0 1 0 0
C:    0 0 0 0 1 0 0 1
```

값마다 비트열을 만들고, 해당 위치의 값이 일치하면 1로 표시한다. 이 표현을 이용하면 조건에 맞는 행 위치를 찾거나 여러 조건을 AND·OR로 조합할 수 있다.

Bitmap만 만든다고 항상 공간이 줄어드는 것은 아니다. 같은 비트가 길게 이어지는 경우 Run-Length Encoding, RLE로 더 줄일 수 있다.

```text
0000000011100000
→ 0이 8개, 1이 3개, 0이 5개
```

RLE의 효과는 같은 값이 얼마나 길게 연속되는지에 달려 있다. `01010101`처럼 계속 바뀌면 유리하지 않다. Bitmap은 칼럼을 표현하는 한 방법이지 모든 칼럼에 적용하는 고정 규칙은 아니다.

### 2. Memory Bandwidth와 Vectorized Processing

**질문:** 여러 값을 한꺼번에 계산한다는 게 무슨 뜻이며, 압축과는 무슨 관계일까?

분석 쿼리는 계산뿐 아니라 데이터를 운반하는 데도 시간을 쓴다.

```text
디스크 → RAM → CPU Cache → CPU의 계산
```

Memory Bandwidth는 RAM과 CPU 사이에서 단위 시간에 옮길 수 있는 데이터 양이다. 메모리 용량과는 다르다. CPU가 계산을 빨리해도 데이터가 늦게 도착하면 기다려야 한다.

압축한 상태로 RAM에 보관하고 CPU 쪽으로 가져오면 옮길 바이트 수가 줄어든다. 압축 형식에 따라 필요한 부분을 CPU Cache에서 풀거나, 압축 표현에 맞는 연산을 적용한다. 압축 해제 비용보다 데이터 이동을 줄이는 이득이 크면 전체 처리가 빨라질 수 있다.

Vectorized Processing은 여러 값에 같은 작업을 묶어서 적용하는 방식이다. 예를 들어 여러 매출액이 각각 100보다 큰지 검사할 수 있다.

```text
입력: [120, 80, 200, 50]
연산: 각 값이 100보다 큰지 비교
결과: [참, 거짓, 참, 거짓]
```

SIMD는 이를 지원하는 CPU 기능이다. 하나의 명령으로 여러 데이터에 같은 연산을 적용한다. 여러 코어나 스레드에 작업을 나누는 것과는 다르다. 한 코어 안에서도 사용할 수 있다.

같은 칼럼의 값들이 연속해 있으면 이런 처리를 적용하기 좋다. Bitmap의 여러 비트에 AND·OR를 한꺼번에 적용하는 것도 연결해서 생각할 수 있다. 단, RLE 등으로 추가 압축한 데이터는 그 형식에 맞는 처리나 압축 해제가 필요할 수 있다.

**압축과 SIMD는 같은 기술이 아니다. 압축은 옮길 데이터 양을 줄이고, Vectorized Processing은 가져온 데이터에 대한 반복 처리 비용을 줄인다.** JavaScript에서 배열에 `map()`을 썼다고 자동으로 SIMD 처리가 되는 것도 아니다.

### 3. Sort Order in Column Storage

**질문:** 칼럼 저장소에서 정렬한다는 것은 각 칼럼을 따로 정렬한다는 뜻일까?

아니다. 같은 위치의 값들이 같은 행에 속한다는 관계를 유지해야 한다. 날짜 칼럼만 정렬하고 나머지 칼럼을 그대로 두면 주문의 날짜·상품·금액 연결이 깨진다.

정렬할 때는 논리적인 행 전체를 함께 이동시키고, 저장은 칼럼별로 한다.

```text
날짜 → 상품 순으로 정렬한 결과

날짜: [01일, 01일, 02일, 02일]
상품: [   A,    B,    A,    B]
금액: [  50,   80,  120,  200]
```

첫 번째 기준인 날짜가 전체 순서를 정한다. 상품은 날짜가 같은 행들 안에서만 정렬 기준이 된다. 따라서 상품 칼럼 전체가 `A A B B`가 되는 것은 아니다.

날짜로 정렬하면 같은 날짜의 주문이 한 구간에 모인다. 특정 날짜 범위를 조회할 때 관련 구간을 찾아 읽을 수 있고, 같은 날짜가 반복되므로 RLE에도 유리해진다.

이 압축 효과는 일반적으로 첫 번째 정렬 기준에서 강하다. 두 번째 기준은 첫 번째 값이 같은 구간 안에서만 정렬되므로 반복 구간이 더 짧아질 수 있다.

### 4. 여러 Sort Order와 Replica

**질문:** 복제본마다 인덱스를 `(a, b)`, `(b, a)`로 다르게 설정하는 것일까?

방향은 비슷하지만, 여기서는 **인덱스만 다르게 만드는 것이 아니라 실제 데이터의 정렬 배치를 다르게 한다.**

```text
버전 X: 날짜 → 상품 순서
날짜: [01일, 01일, 02일, 02일]
상품: [   A,    B,    A,    B]
금액: [  50,   80,  120,  200]

버전 Y: 상품 → 날짜 순서
날짜: [01일, 02일, 01일, 02일]
상품: [   A,    A,    B,    B]
금액: [  50,  120,   80,  200]
```

날짜 범위 질의에는 X가, 상품 중심 질의에는 Y가 유리할 수 있다. 책의 C-Store·Vertica 설명은 장애 대비를 위해 둘 복제 데이터에 서로 다른 정렬 순서를 부여해 조회에도 활용하자는 아이디어다.

일반적인 Secondary Index는 검색 키와 원본 행을 찾아갈 정보를 담는다. 여기서 말하는 정렬된 칼럼 버전은 실제 값을 담으므로, 필요한 칼럼이 그 버전에 있으면 별도의 원본 행을 찾아가지 않고 읽을 수 있다.

Secondary Index의 행 위치 정보는 구현에 따라 물리 주소가 아니라 Primary Key일 수도 있다. Covering Index처럼 필요한 값을 인덱스에서 모두 얻는 경우도 있다. 따라서 이 비교는 기본 구조의 차이를 설명하는 것이지 모든 인덱스가 반드시 원본 행을 추가 조회한다는 뜻은 아니다.

여러 정렬 버전은 저장 공간과 갱신 비용을 요구한다. 또한 모든 DB에서 Replica의 정렬 순서를 자유롭게 바꿀 수 있다는 뜻도 아니다.

### 5. Column Store와 LSM의 관계

**질문:** 칼럼 저장소는 LSM인가? 모아서 반영하면 모두 LSM 아닌가?

두 개념은 서로 다른 질문에 답한다.

| 개념 | 설명하는 것 |
| --- | --- |
| Column-oriented Storage | 같은 칼럼의 값을 모아 저장하는 데이터 배치 |
| LSM 방식 | 새 쓰기를 정렬된 데이터 묶음으로 만들고, 묶음들을 병합해 관리하는 구조 |

정렬·압축된 칼럼 파일의 중간에 주문을 매번 끼워 넣으면 비싸다. 모든 칼럼의 행 위치를 맞추고 압축 데이터도 다시 작성해야 할 수 있기 때문이다. 책은 이 문제에 LSM의 아이디어를 연결한다.

```text
새 쓰기를 별도 영역에 모음
    ↓
정렬된 데이터 묶음으로 기록
    ↓
기존 데이터 묶음과 병합해 새 파일 작성
```

조회할 때는 아직 병합되지 않은 최신 데이터도 함께 확인해야 한다.

**모아서 쓰는 전략은 넓은 개념이고, LSM은 정렬된 묶음의 생성과 반복 병합까지 포함하는 더 구체적인 구조다.** 모아서 반영한다는 공통점은 있지만, 그것만으로 모두 같은 저장 엔진이라고 할 수는 없다.

대화에서 비교한 제품별 예시는 다음과 같다.

| 예시 | 핵심 구조 |
| --- | --- |
| ClickHouse의 MergeTree | 정렬된 데이터 Part를 만들고 백그라운드에서 병합한다. LSM 아이디어를 활용하지만 전형적인 Level 구조와 동일하지는 않다. |
| SQL Server의 Columnstore | 작은 쓰기를 B-Tree 기반 Deltastore에 모았다가 압축된 칼럼 Row Group으로 변환한다. 이 동작만으로 LSM이라고 분류하지는 않는다. |

ClickHouse는 분석용 Column-oriented DBMS이고, MergeTree는 그 안에서 사용하는 대표적인 저장 엔진 계열이다.

### 6. View와 Materialized View

**질문:** MySQL View는 결과를 캐싱하는 것일까?

일반 View는 SELECT 쿼리에 이름을 붙여 테이블처럼 조회하게 만든 것이다.

```sql
CREATE VIEW paid_orders AS
SELECT id, product_id, amount
FROM orders
WHERE status = 'PAID';
```

이후 `SELECT * FROM paid_orders`로 조회할 수 있지만, 주문 결과를 별도로 저장해 둔 것은 아니다. View는 쿼리 정의를 저장하고, 조회 시 원본을 바탕으로 실행한다. 실행 계획에서 일시적인 결과를 만들 수 있다는 사실과 영구적인 결과 캐시는 별개다.

Materialized View는 쿼리 결과를 실제 데이터로 저장한다. 상품별 매출을 미리 집계해 두면 매번 원본 주문을 모두 더할 필요가 줄어든다.

| 구분 | 저장하는 것 | 원본 변경 시 고려할 점 |
| --- | --- | --- |
| View | 쿼리 정의 | 조회 시 원본과 트랜잭션 가시성에 따라 결과를 구한다. |
| Materialized View | 계산 결과 | 결과를 언제, 어떻게 갱신할지 정해야 한다. |

Materialized View는 DB에 따라 전체 재계산, 변경분 반영, 즉시 또는 주기적 갱신 등을 지원한다. 갱신이 늦으면 결과가 오래될 수 있고, 즉시 갱신하면 쓰기에 추가 비용이 든다.

**일반 MySQL Server는 Materialized View를 기본 기능으로 지원하지 않는다.** 비슷한 효과를 내려면 별도 집계 테이블과 배치·애플리케이션 등의 갱신 로직을 직접 관리해야 한다. InnoDB Buffer Pool에 원본 데이터 페이지가 캐싱되는 것과 View 결과를 저장하는 것은 다른 이야기다.

### 7. Aggregation과 Data Cube

**질문:** Cube와 Dimension은 실제로 무엇을 뜻할까?

Aggregation은 여러 기록을 묶어 합계·개수·평균 등을 구하는 것이다. Data Cube는 여러 기준의 조합으로 집계하고, 그 결과를 조회하는 구조다. 책에서는 미리 계산해 저장한 집계의 형태로 설명한다.

예를 들어 다음 표를 미리 준비했다고 하자.

| 날짜 ＼ 상품 | A | B | 날짜별 합계 |
| --- | ---: | ---: | ---: |
| 01일 | 50 | 80 | 130 |
| 02일 | 120 | 200 | 320 |
| 상품별 합계 | 170 | 280 | 450 |

가운데 칸은 날짜와 상품을 모두 고른 매출이다. 오른쪽은 상품을 구분하지 않은 날짜별 매출이고, 아래쪽은 날짜를 구분하지 않은 상품별 매출이다.

여기에 매장을 추가하면 매장마다 같은 모양의 표가 생긴다.

```text
서울 매장의 날짜 × 상품 매출표
부산 매장의 날짜 × 상품 매출표
대구 매장의 날짜 × 상품 매출표
```

칸 하나를 고르려면 매장·날짜·상품을 정해야 한다. 이 선택 기준들이 Dimension이다. 칸에 들어 있는 매출액은 Measure, 즉 측정·집계한 값이다.

표를 포개면 가로·세로·높이가 있는 모습으로 생각할 수 있어 Cube라는 이름을 쓴다. 실제 저장 장치가 정육면체라는 뜻도, Dimension이 반드시 세 개여야 한다는 뜻도 아니다.

미리 준비한 집계는 자주 하는 질문에 빠르게 답할 수 있지만, 없던 기준을 새로 만들어 주지는 못한다. 날짜·상품·매장별 매출만 있다면 고객 나이별 매출은 알 수 없다. 그런 질문에는 원본이나 다른 집계가 필요하다. 기준과 조합이 늘면 저장 공간과 갱신 비용도 증가하므로 필요한 집계를 선택한다.

**칼럼 저장은 원본을 적게 읽어 계산하도록 돕고, Materialized View와 Data Cube는 자주 하는 계산을 미리 해 두도록 돕는다.**

### 8. Lucene의 FST와 Levenshtein Automaton — 추가 복습 항목

처음 질문한 내용은 SSTable의 희소 인덱스와 Lucene의 Trie 유사 구조, FST, 편집 거리 검색이 어떻게 연결되는가였다. 이 질문은 대화에서 답변이 누락됐으므로 이해를 마친 항목으로 기록하지 않는다.

추가로 확인할 질문은 다음과 같다.

- Trie와 FST는 접두사를 어떻게 공유하는가?
- 사전의 오토마톤과 Levenshtein Automaton을 이용해 오타 후보를 어떻게 찾는가?

## 4장. Encoding and Evolution

### 1. JSON·XML·CSV에서 숫자와 문자열

**질문:** 사람이 읽을 수 있는 형식인데도 왜 데이터 해석에 문제가 생길까?

숫자처럼 보이는 텍스트가 반드시 계산용 숫자는 아니다. `00123`이 수량이라면 숫자로 읽어도 되지만 우편번호라면 앞의 0까지 보존해야 한다.

XML과 CSV는 외부 스키마나 애플리케이션 규칙 없이 값만 보고 이런 의미를 정하기 어렵다. JSON은 숫자와 문자열을 문법으로 구분한다.

```json
{
  "quantity": 123,
  "postal_code": "00123"
}
```

하지만 JSON은 정수를 반드시 어떤 정밀도의 자료형으로 읽으라고 정하지 않는다. 보내는 쪽이 큰 정수를 표현해도 받는 쪽의 숫자 타입이 정확히 보존하지 못할 수 있다.

#### 큰 ID와 JavaScript Number

다음 JSON을 JavaScript의 일반적인 `JSON.parse()`로 읽으면 숫자와 문자열의 결과가 다를 수 있다.

```json
{
  "id": 9007199254740993,
  "id_str": "9007199254740993"
}
```

```text
id를 Number로 읽은 결과: 9007199254740992
id_str를 문자열로 읽은 결과: 9007199254740993
```

이 결과는 대화 중 Node.js에서 직접 확인했다. JavaScript의 `Number.MAX_SAFE_INTEGER`는 `9007199254740991`이다. 이를 넘는 정수가 모두 표현 불가능한 것은 아니지만, 모든 연속 정수를 정확히 구분할 수 없어진다.

책의 당시 Twitter 사례는 같은 ID를 숫자와 문자열 형태로 제공해 이 문제를 피할 수 있게 한 것이다. 문자열을 다시 `Number`로 바꾸면 문제가 되살아날 수 있다. 계산이 필요하다면 문자열에서 `BigInt`로 변환하는 방법이 있지만, 이미 부정확하게 파싱된 Number를 BigInt로 바꿔도 원래 값은 복원되지 않는다.

### 2. Binary Data, Base64, Schema, CSV

**질문:** 텍스트 형식에 파일을 넣거나 데이터의 의미를 전달하려면 무엇이 더 필요할까?

JSON과 XML에는 임의의 바이트열을 그대로 넣는 전용 리터럴이 없다. 사진 같은 Binary Data를 포함하려면 Base64 등으로 문자열로 바꾸는 방법을 쓴다. XML Schema 등에서 바이너리 타입을 지정하더라도 문서 안에는 그에 맞는 텍스트 표현이 들어간다.

```text
원본 바이트 → Base64 문자열 → JSON/XML로 전송
수신한 문자열 → Base64 해제 → 원본 바이트
```

Base64는 일반적으로 원본 3바이트를 문자 4개로 표현하므로 크기가 약 33% 증가한다. 패딩 등으로 짧은 데이터의 비율은 달라질 수 있다. 압축이나 암호화가 아니라 텍스트로 담기 위한 변환이다.

Schema는 필드의 이름·타입·필수 여부·의미를 기술하는 규칙이다. 예를 들어 `id`는 문자열이고 `photo`는 Base64 표현이라는 약속을 적는다. JSON Schema나 XML Schema를 사용하지 않더라도 이 약속이 필요 없어진 것은 아니다. 문서나 코드에서 직접 관리해야 한다.

CSV는 열의 타입과 의미를 기본 문법만으로 충분히 설명하지 못한다. 값 안의 쉼표·따옴표·줄바꿈도 규칙에 맞춰 처리해야 한다.

```csv
name,memo
reader,"안녕, 반가워"
```

여기서 메모 안의 쉼표는 열 구분자가 아니다. 표준적인 따옴표 규칙이 있지만 실제 도구들의 처리 차이도 확인해야 한다. 단순히 쉼표나 줄바꿈으로 문자열을 나누는 것만으로는 안전한 CSV 파서가 되지 않는다.

### 3. MessagePack — 바이트를 어떤 순서로 읽는가

**질문:** `0x83`, `0xA8`, `0xA6`은 무엇을 알려 주는가?

MessagePack은 객체를 바이너리로 직렬화하는 형식이다. JSON의 중괄호·따옴표 등으로 드러나던 구조를 타입·길이를 나타내는 바이트로 표현한다. 모든 문자열 길이가 항상 한 바이트에 들어간다는 뜻은 아니다.

책의 예시에서 첫 번째 필드를 읽는 흐름은 다음과 같다.

```text
[0x83] [0xA8] [userName의 바이트] [0xA6] [Martin의 바이트] …
```

| 부분 | 의미 |
| --- | --- |
| `0x83` | 키·값 쌍이 3개인 Map |
| `0xA8` | 다음 문자열의 길이가 8바이트 |
| `userName` | 첫 번째 키 |
| `0xA6` | 다음 문자열의 길이가 6바이트 |
| `Martin` | 해당 키의 값 |

`0xA8`이라는 글자를 저장하는 것이 아니라 한 바이트 값을 16진수로 표기한 것이다. 길이를 알고 있으므로 문자열의 끝을 찾기 위해 종료 따옴표를 검색할 필요가 없다. 길이는 글자 수가 아니라 UTF-8 바이트 수다.

첫 필드까지의 실제 바이트는 다음과 같다. `0x83`이 세 필드를 선언하므로 이 바이트만으로 완성된 객체는 아니며, 다른 필드들이 이어져야 한다.

```text
83 a8 75 73 65 72 4e 61 6d 65 a6 4d 61 72 74 69 6e
```

Map의 필드 수와 문자열 길이를 바이트 단위로 확인했다. 정확한 비트 구분은 fixmap이 상위 4비트로 종류·하위 4비트로 개수를 표현하고, fixstr가 상위 3비트로 종류·하위 5비트로 길이를 표현한다. 예시의 `0xA8`만 보고 모든 문자열 헤더가 상·하위 4비트로 나뉜다고 일반화하지 않는다.

필드 이름 `userName`은 여전히 메시지에 들어 있다. 바이너리라는 이유만으로 필드 이름까지 자동으로 생략되는 것은 아니다.

### 4. Avro와 Parquet — 형식과 파일 개수의 구분

**질문:** Avro도 DB인가? 행·열 기반이라는 말은 파일을 행이나 칼럼 개수만큼 만든다는 뜻인가?

Avro는 DB가 아니라 Schema 기반 직렬화 체계다. 그중 Object Container File, OCF는 스키마와 여러 레코드를 담는 파일 형식이다. Parquet은 분석에 적합한 칼럼 지향 파일 형식이다.

| 구분 | Avro Object Container File | Parquet |
| --- | --- | --- |
| 정체 | Avro 레코드를 담는 컨테이너 파일 | 칼럼 지향 데이터 파일 형식 |
| 내부 배치 | 레코드 중심으로 블록에 기록 | Row Group 안에서 칼럼별로 기록 |
| 스키마 위치 | 컨테이너 파일 헤더에 Writer Schema 포함 | 파일 메타데이터에 포함 |
| 주된 활용 | 데이터 교환, 순차 레코드 처리 | 필요한 칼럼을 읽는 분석 작업 |
| 파일 개수 | Export의 분할·크기·파티션 설정 등에 따라 결정 | Export의 분할·크기·파티션 설정 등에 따라 결정 |

**행 기반과 열 기반은 파일 개수가 아니라 내부 배치 방식이다.** Avro 파일 하나에 많은 행을 담을 수 있고, Parquet 파일 하나에도 여러 칼럼이 들어간다.

Avro OCF는 파일 자체에 기록용 스키마가 있어 별도 스키마 파일 없이 구조를 해석할 수 있다. 다만 OCF가 아닌 개별 Avro 메시지가 항상 스키마 전체를 내장하는 것은 아니다. 메시징 환경에서는 스키마 ID와 별도의 Schema Registry를 사용하는 구성도 있다.

Avro의 장점을 단순히 작은 용량으로만 이해하지 않는다. Writer Schema와 Reader Schema의 차이를 정해진 규칙으로 해석하는 Schema Evolution도 중요한 특징이다. 어떤 형식이 더 작은지는 데이터와 압축 설정에 따라 달라진다.

### 5. Schema Evolution과 Database Dataflow

**질문:** 파일에 스키마가 있는데 왜 MySQL → S3 → BigQuery에서는 스키마 오류가 날 수 있을까?

파일을 해석할 수 있다는 사실과 파이프라인의 모든 시스템이 같은 스키마를 사용한다는 사실은 다르다.

```text
MySQL에 신규 칼럼 추가
    ↓
Export 파일에 신규 칼럼 포함
    ↓
BigQuery 대상 스키마는 이전 상태
    ↓
적재 설정에 따라 오류 또는 의도하지 않은 처리 가능
```

실제 오류는 파일 형식, 적재 방식, 자동 감지·스키마 변경 옵션, 칼럼명·순서·타입 등에 따라 달라진다. 이 대화에서는 실제 파이프라인 설정을 확인하지 않았으므로 특정 원인을 확정하지 않는다.

자동화를 설계한다면 변경 감지, 타입 매핑, 호환성 검증, 대상 스키마 변경, 적재 순서를 함께 관리해야 한다. 새 nullable 칼럼 추가와 기존 칼럼의 삭제·이름 변경·타입 축소를 똑같이 자동 처리해서는 안 된다.

#### Backward Compatibility와 Forward Compatibility

| 구분 | 읽는 쪽 | 읽어야 하는 데이터 |
| --- | --- | --- |
| Backward Compatibility | 새 코드 | 예전 코드가 쓴 데이터 |
| Forward Compatibility | 예전 코드 | 새 코드가 쓴 데이터 |

예전 데이터에는 `email`이 없고 새 코드에서는 필요하다면, 없을 때 어떻게 처리할지 정해야 한다. 반대로 예전 코드가 새 데이터의 `email`을 몰라도 건너뛸 수 있다면 읽기가 가능할 수 있다. 어느 방향의 호환성이 성립하는지는 구체적인 변경과 형식의 규칙에 달려 있다.

Avro는 Writer Schema와 Reader Schema를 비교해 레코드를 해석한다. Reader에만 있는 필드에 적절한 Default가 있으면 누락 값을 채울 수 있다. Default를 선언했다고 필드 추가·삭제·타입 변경이 모두 자동으로 안전해지는 것은 아니다.

#### Archival Storage와 데이터 덤프

Archival Storage는 오래 보관하거나 나중에 다시 분석·복구할 데이터를 두는 저장소다. 덤프를 한 번 기록한 뒤 변경하지 않는다는 것은 보통 그 파일을 제자리 수정하지 않고 스냅샷처럼 보관한다는 뜻이다. 원본 DB의 갱신까지 멈춘다는 뜻은 아니다.

```text
예전 덤프: id, name
다음 덤프: id, name, age
새 덤프:   id, name, age, email
```

한 번의 Export에서 레코드들을 일관된 스키마로 기록하면 관리가 쉬워질 수 있다. 그러나 과거 파일을 전부 현재 스키마로 다시 써야만 하는 것은 아니다. 파일별 Writer Schema를 보관하고 읽는 시점에 조정하는 방식도 가능하다. 관계형 DB의 물리적 행마다 위의 서로 다른 스키마가 그대로 존재한다고 일반화하지 않는다.

### 6. REST와 SOAP

**질문:** 둘 다 API 통신인데 왜 구분하며, REST로 충분해 보여도 SOAP을 쓰는 이유는 무엇일까?

REST는 분산 시스템의 인터페이스를 구성하는 아키텍처 스타일이다. 실무의 HTTP API에서는 리소스를 URI로 나타내고 HTTP 메서드와 의미를 활용한다. JSON은 흔한 표현 형식이지만 REST의 필수 조건은 아니다.

SOAP은 XML 기반 메시지의 구조와 처리 규칙을 정의하는 메시징 프로토콜이다. 메시지를 HTTP로 보낼 수 있지만 SOAP 자체는 다른 전송 프로토콜에 바인딩하는 것도 고려한다.

| 구분 | REST를 따르는 HTTP API | SOAP |
| --- | --- | --- |
| 중심 | 리소스와 일관된 인터페이스 | XML 메시지 구조와 처리 규칙 |
| 표현 | JSON, XML 등 | XML |
| 실무 선택 요소 | 웹 생태계와 도구, API 설계·운영 편의 | 기존 계약·시스템 호환성, 필요한 WS-* 표준 |

SOAP에는 WS-Security, WS-ReliableMessaging 같은 관련 표준을 결합할 수 있다. 다만 SOAP을 쓴다는 사실만으로 보안이나 신뢰성 보장이 자동으로 생기는 것은 아니다. 관련 표준의 지원과 설정이 필요하다.

**REST가 기술적으로 부족해서 항상 SOAP을 선택하는 것도 아니고, SOAP이 오래됐으니 언제나 불필요한 것도 아니다. 기존 시스템과 계약, 필요한 기능이 선택을 좌우한다.**

### 7. RPC, Promise/Future, gRPC Streaming

**질문:** 원격 기능을 함수처럼 호출할 수 있는데, 로컬 호출과 무엇이 다를까?

RPC는 Remote Procedure Call이다. Procedure는 여기서 호출 가능한 작업이나 루틴을 뜻하며, 반드시 반환값이 없는 함수만을 의미하지 않는다.

```typescript
const user = await userService.getUser(123);
```

이 코드는 로컬 함수처럼 보일 수 있지만 구현이 RPC라면 인자를 부호화하고 네트워크로 보내 원격 서버에서 실행한 뒤 결과를 받는다.

```text
클라이언트가 요청 전송
    ↓
서버가 작업 완료
    ↓
응답이 전달되지 않음
    ↓
클라이언트가 타임아웃
```

클라이언트는 응답이 없다는 사실만으로 서버가 실행하지 않았다고 결론 낼 수 없다. 재시도하면 같은 작업을 중복 실행할 수도 있다. 작업 성격에 따라 Idempotency Key나 중복 제거 등 별도 설계가 필요하다.

Promise/Future는 나중에 성공하거나 실패할 결과를 표현한다. 원격 응답을 기다리는 동안 다른 작업을 진행하는 데 도움이 되지만 네트워크의 불확실성을 없애지는 않는다. `await` 역시 원격 실행을 로컬 실행처럼 확실하게 만들지 않는다.

#### gRPC Streaming

일반적인 Unary RPC는 요청 메시지를 보내고 응답 메시지를 받는다. Streaming은 하나의 RPC 안에서 메시지를 연속으로 주고받는 방식이다.

| 방식 | 예시 흐름 |
| --- | --- |
| Server Streaming | 조회 요청 후 서버가 결과 묶음들을 차례로 보냄 |
| Client Streaming | 클라이언트가 측정값들을 차례로 보내고 서버가 결과를 반환 |
| Bidirectional Streaming | 양쪽이 각각 메시지들을 연속으로 보냄 |

하나의 큰 JSON을 반드시 끝까지 만든 뒤 보내야 하는 방식과 다르다. 그렇다고 한 RPC의 메시지 순서 보장이 서로 다른 RPC 전체의 실행 순서나 처리 성공까지 보장하는 것은 아니다.

#### RPC가 더 빠를 수 있는데 REST를 쓰는 이유

RPC와 REST 중 무엇이 빠른지는 전송 형식, 구현, 연결 재사용, 작업 내용 등에 달려 있다. 특정 gRPC 구현의 성능을 모든 RPC의 속성으로 일반화하지 않는다.

REST를 따르는 HTTP API는 범용 클라이언트, 브라우저·프록시·캐시 도구, 외부 공개 API 운영 등에서 선택할 이유가 있다. RPC는 강한 서비스 계약과 코드 생성, 내부 서비스 호출, Streaming 등에서 선택할 이유가 있다. 성능 하나만으로 모든 선택이 결정되지는 않는다.

### 8. Message Broker와 Unknown Field Loss

**질문:** 예전 소비자가 새 필드를 무시해도 된다면, 왜 재발행할 때는 문제가 될까?

Producer가 메시지를 Broker에 게시하면 Consumer가 나중에 읽는다. Consumer가 가공 결과를 다른 Topic에 게시하면 다음 Consumer로 이어지는 파이프라인이 된다.

새 Producer가 다음 데이터를 보냈다고 하자.

```json
{
  "id": "u-123",
  "name": "reader",
  "email": "reader@example.com"
}
```

예전 Consumer는 `id`, `name`만 알고 있다. 이 필드들만 사용해 처리하는 것은 가능할 수 있다. 하지만 알고 있는 필드만으로 새 메시지를 만들어 재발행하면 결과는 다음과 같다.

```json
{
  "id": "u-123",
  "name": "reader"
}
```

이제 다음 Consumer는 원래 존재하던 `email`을 복원할 수 없다. 이런 현상을 설명하기 위해 Unknown Field Loss라는 표현을 썼다. 특정 브로커의 오류 코드나 모든 형식에서 동일한 공식 기능 이름이라는 뜻은 아니다.

**새 필드를 사용하지 않고 읽는 것과, 새 필드를 버린 채 다시 저장·발행하는 것은 다르다.** Broker가 자동으로 필드를 지웠다는 뜻도 아니다. 중간 애플리케이션의 변환·재직렬화 과정이 원인일 수 있다.

형식과 라이브러리에 따라 모르는 필드를 보존할 수도 있다. 현재 Protobuf의 Binary 메시지는 Unknown Field를 보존하지만, JSON 변환이나 알려진 필드만 복사해 새 메시지를 만드는 과정에서는 유실될 수 있다. JSON도 원본 객체를 그대로 전달한다면 새 필드가 반드시 사라지는 것은 아니다.

### 9. Actor Model과 Location Transparency

**질문:** RPC도 원격 함수를 로컬처럼 호출하는데, 왜 책에서는 Actor Model의 Location Transparency를 다르게 평가할까?

Actor Model은 각 Actor가 자기 상태를 관리하고 메시지를 받아 처리하는 계산 모델이다. Broker를 사용하는 비동기 통신과 마찬가지로 메시지 전달을 다루기 때문에 이 장의 데이터플로 설명에서 이어진다. 다만 Actor Model과 Message Broker는 같은 것이 아니다. Actor 시스템이 반드시 중앙 Broker를 사용하는 것도 아니다.

Location Transparency는 호출하는 쪽이 상대의 구체적인 실행 위치에 덜 의존하도록 만드는 성질이다. 위치를 감춘다는 말이 네트워크 지연·실패·전송 비용까지 없어졌다는 뜻은 아니다.

전통적인 로컬 함수 호출은 같은 프로세스에서 인자를 전달하고 반환값이나 예외를 받는 방식이다. RPC가 호출 문법을 비슷하게 만들더라도 원격 실행에는 타임아웃과 완료 여부의 불확실성이 추가된다. 현대 RPC도 이를 명시적으로 다루지만, 함수 모양만 같다고 실패 특성까지 같아지는 것은 아니다.

Akka처럼 분산 실행을 고려한 Actor 시스템은 로컬에서도 비동기 메시지 전달을 기본으로 삼는다. 원격으로 옮겨도 메시지를 보내고 별도로 결과를 받는 기본 모델을 유지하기 쉽다는 것이 책의 비교를 이해하는 지점이다.

| 비교 | RPC 인터페이스 | 분산 실행을 고려한 Actor 시스템 |
| --- | --- | --- |
| 기본 표현 | 원격 작업 호출과 결과 | Actor에게 비동기 메시지 전송 |
| 응답 | 결과·에러·타임아웃을 API로 표현 | 별도 응답 메시지나 요청·응답 패턴 사용 가능 |
| 위치 추상화 | 가능하지만 원격 실패를 고려해야 함 | Actor 참조 등으로 추상화할 수 있지만 원격 실패를 고려해야 함 |
| 주의점 | 호출 구문이 같아도 로컬 호출과 실패 특성이 다름 | 전송 성공과 처리 완료는 다르며 원격에서는 직렬화·지연·유실 등을 고려 |

**Actor도 응답을 받을 수 있다. 다만 메시지를 보냈다는 사실과 실제 처리가 끝났다는 사실을 구분한다.** 모든 Actor 프레임워크가 동일한 전송 보장이나 위치 추상화를 제공하는 것은 아니다. Actor라는 이유만으로 신뢰성 문제가 해결되는 것도 아니다.

EDA, REST, RPC에서도 논리적인 주소나 서비스 이름을 통해 실제 서버 위치를 감출 수 있다. 따라서 Location Transparency가 있는지 없는지의 이분법보다, 무엇을 감추며 어떤 실패와 비용은 여전히 드러나는지 살피는 편이 정확하다.

## 3·4장을 연결해 이해하기

| 질문 | 3장의 관점 | 4장의 관점 |
| --- | --- | --- |
| 데이터를 어떻게 다룰까? | 저장·탐색·스캔·집계를 효율적으로 수행 | 저장·전송 가능한 표현으로 바꾸고 서로 해석 |
| 무엇이 바뀔까? | 작업부하, 데이터 양, 읽기·쓰기 패턴 | 스키마, 코드 버전, 생산자와 소비자 |
| 무엇을 확인할까? | 탐색 비용, 읽는 바이트 수, 압축·병합 비용 | 타입·스키마 호환성, 필드 보존, 네트워크 실패 |

칼럼 저장과 Parquet은 필요한 칼럼만 읽기 좋다는 공통점을 갖는다. 다만 DB의 저장 엔진과 파일 형식을 같은 종류의 도구로 혼동하지 않는다.

데이터를 작게 표현하는 것은 저장·전송 비용을 줄일 수 있지만 의미 보존까지 자동으로 보장하지 않는다. 숫자 정밀도, 스키마 변경, 중간 Consumer의 필드 유실처럼 별도로 확인할 문제가 남는다.

## 발표에 넣을 메시지 — 개발자가 내부 동작을 배우는 이유

> 저장소 엔진을 배우는 목적은 튜닝 비법을 외우는 것이 아니라, 작업의 성격을 구분하고 선택의 효과와 비용을 이해하는 것이다.

느린 쿼리를 보면 무조건 인덱스를 추가하기 전에 다음을 구분한다.

- 소수의 행을 찾아야 하는가, 많은 행을 집계해야 하는가?
- 탐색 범위를 줄이는 것이 중요한가, 읽는 칼럼과 바이트 수를 줄이는 것이 중요한가?

대량 분석에서도 인덱스나 데이터 건너뛰기가 유용할 수 있다. 다만 대상 데이터 대부분을 읽어야 한다면, 인덱스를 따라 흩어진 행을 찾는 것보다 필요한 칼럼을 순서대로 읽는 편이 유리할 수 있다.

설정 변경도 같은 관점으로 본다. 캐시를 늘리면 디스크 재읽기가 줄어들 수 있지만 메모리를 더 사용한다. LSM의 병합을 뒤로 미루면 당장의 작업 부담은 줄 수 있지만 파일 누적과 후속 읽기·병합 비용이 커질 수 있다. 설정값은 무조건 크거나 작을수록 좋은 것이 아니다.

**이 장을 읽었다고 바로 특정 DB의 튜닝 전문가가 되는 것은 아니다. 대신 DB 문서를 이해하고, 어떤 도구와 설정이 내 작업에 적합한지 판단할 어휘와 개념을 얻는다.**

이 문단은 향후 발표자료의 도입이나 마무리에 넣을 후보로 남겨 둔다.

## 다시 설명할 수 있어야 할 질문

- 압축과 Vectorized Processing은 각각 어떤 비용을 줄이는가?
- 칼럼을 정렬할 때 왜 같은 행에 속한 값들을 함께 이동해야 하는가?
- 여러 정렬 버전과 Secondary Index는 무엇을 저장한다는 점에서 다른가?
- Column Store와 LSM을 같은 개념으로 볼 수 없는 이유는 무엇인가?
- View와 Materialized View는 각각 무엇을 저장하며, MySQL은 무엇을 기본 지원하는가?
- Data Cube에서 Dimension과 Measure는 어떻게 다른가?
- 큰 ID를 JSON 숫자로 보낼 때 어디에서 정밀도가 손실되는가?
- Avro와 Parquet의 행·열 기반 배치는 왜 파일 개수와 무관한가?
- 스키마가 파일에 포함되는 것과 파이프라인의 스키마 동기화는 왜 별개인가?
- Unknown Field를 무시하는 것과 유실시키는 것은 어떻게 다른가?
- RPC 타임아웃이 서버의 미실행을 의미하지 않는 이유는 무엇인가?
- Location Transparency는 무엇을 감추고, 무엇까지 같게 만들지는 못하는가?
