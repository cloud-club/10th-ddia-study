읽는 방법

왼쪽 목차를 따라 발표하거나, 궁금한 장으로 바로 이동할 수 있다. 각 장 끝의 원문 보기에는 출처와 해석 범위를 남겼다. 도해·학생 예시·비용 비교는 교육용 재구성이며 실제 DB 측정 결과가 아니다.

01논쟁의 지도

데이터를 표현하고 찾는 문제를
어떻게 나눠 맡았을까?

이 연표는 “어떤 DB가 다음 DB로 교체됐나”가 아니라, “데이터를 표현하고 찾는 문제를 어떻게 나눠 맡았나”를 보여준다. 각 시점에서 무엇이 문제였고, 어떤 선택을 했는지부터 살펴보자.

이름부터 구분하기

IMS·System R·POSTGRES·Spanner는 시스템 이름이고, Codd·Bachman·Date·Selinger는 사람 이름이다. CODASYL은 데이터 처리 언어 등을 논의한 위원회다. 아래 연도는 제품·논문·사양의 기록을 함께 묶은 것이지, 각 모델의 발명 순서를 뜻하지 않는다.

1968IMS · IBM의 계층형 데이터베이스 시스템

“부모 아래 자식을 묶어서 관리하자”

Apollo 우주선의 부품 정보를 생각해보자. 우주선 아래 조립품, 그 아래 하위 조립품과 부품을 두면 “이 조립품에 어떤 부품이 들어가나?”를 위에서 아래로 따라가며 확인할 수 있다. IBM의 회고에 따르면 IMS는 이런 부품·조립 정보 관리에서 출발했다.

우주선
 └─ 조립품
     └─ 하위 조립품
         └─ 부품

그런데 같은 부품을 여러 조립품에서 사용한다면? 부품 정보를 각 위치에 복사하거나 별도 참조 관계를 둬야 한다. 계층 구조는 유용하지만, 여러 곳에서 공유하는 관계를 엄격한 트리만으로 표현하기는 어렵다.

이 시점의 핵심 트리가 잘못된 것이 아니라, 모든 공유 관계를 트리 하나에 담으려 할 때 부담이 생긴다. 실제 IMS에는 이를 보완하는 추가 기능도 있다.

1970Codd · 관계형 모델을 제안한 IBM 연구원

“프로그램이 데이터를 찾는 길까지 알아야 하나?”

Edgar F. Codd(에드거 F. 코드)는 사람 이름이다. 당시에는 응용 프로그램이 “이 레코드에서 시작해서, 이 연결을 따라가라”는 식으로 구체적인 탐색 경로에 의존하는 경우가 있었다. 그러면 데이터 연결이나 접근 방식이 바뀔 때 프로그램도 고쳐야 할 수 있다.

Codd는 데이터를 테이블과 값 사이의 관계로 표현하고, 프로그램을 이런 저장·접근 방식의 의존성에서 분리하는 방향을 제안했다. 현대적인 표현으로 바꾸면 “어느 길로 가라”보다 “어떤 조건의 데이터를 원하는지”를 말하게 하자는 것이다.

이 시점의 핵심 관계형 모델은 단순히 트리를 표로 바꾸는 아이디어가 아니다. 논리적인 데이터 표현과 물리적인 접근 방식을 분리하려는 제안이다. 이 논문에서 SQL과 실행 엔진 전체가 한꺼번에 완성된 것은 아니다.

1971–74CODASYL의 사양 · Bachman의 탐색 관점 · Date·Codd의 비교 논문

“연결을 따라가는 방식도 강력한 접근이다”

이 항목은 Codd 다음에 Network Model이 발명됐다는 뜻이 아니다. 같은 시대에 경쟁하던 접근과 관련 기록을 묶은 것이다. CODASYL 계열의 Network Model은 레코드 사이에 여러 관계를 두어, 단일 트리보다 다양한 연결을 표현했다.

학생–수업 예시에서는 민수와 지연이 각각 수강 레코드를 거쳐 같은 수업 레코드에 연결될 수 있다. 대신 프로그램은 어디서 시작해 어떤 관계를 따라갈지, 현재 어디에 있는지를 관리해야 한다.

Charles Bachman(찰스 바크먼)은 이 탐색 관점을 “프로그래머의 항해”로 설명한 인물이다. C. J. Date(크리스 데이트)와 Codd는 1974년 논문에서 네트워크 접근과 관계형 접근의 프로그래머 인터페이스를 비교했다.

Network “이 레코드에서 이 연결을 따라가라.”

Relational “이 조건을 만족하는 데이터를 구해라.”

이 시점의 핵심 관계를 표현할 수 있느냐뿐 아니라, 탐색 경로를 애플리케이션과 DB 중 누가 책임질지가 중요한 쟁점이었다.

1976 / 79System R · 관계형 연구 시스템 / Selinger 외 · 실행계획 선택 논문

“그럼 DB가 경로를 잘 고르게 만들자”

사용자가 “민수가 듣는 수업을 알려줘”라고 요청해도, DB 내부에서는 여전히 방법을 정해야 한다. 학생 이름부터 찾을까? 수강과 수업을 먼저 결합할까? 어떤 Index를 사용할까? 같은 결과를 만드는 방법이라도 비용은 달라질 수 있다.

System R은 관계형 접근을 실제로 구현하려 한 IBM의 연구 시스템이다. 1976년 논문에도 접근 경로를 고르는 옵티마이저가 나온다. Patricia Selinger(퍼트리샤 셀린저) 등의 1979년 논문은 통계와 비용 추정을 바탕으로 Join 순서와 접근 경로를 선택하는 방법을 자세히 설명한다.

이 시점의 핵심 접근 경로가 없어지는 것이 아니다. 애플리케이션이 직접 작성하던 경로를 DB의 Query Optimizer가 선택하도록 구현한 것이다. 비용은 추정하므로 항상 실제로 가장 빠른 계획을 고른다는 보장은 없다.

1986POSTGRES · 현대 PostgreSQL로 이어지는 연구 시스템

“관계형을 유지하면서 복잡한 데이터도 담자”

관계형 DB가 있어도 숫자와 문자열만으로 다루기 불편한 데이터가 있다. 예를 들어 좌표·도형 같은 자료형과 그 자료형에 맞는 연산을 쓰고 싶다면, 기본 기능만으로는 부족할 수 있다. 이는 확장성이 왜 필요한지를 설명하는 예시다.

Michael Stonebraker(마이클 스톤브레이커)와 Lawrence Rowe(로런스 로)의 POSTGRES 설계는 관계형 모델을 버리기보다, 복합 객체와 사용자 정의 자료형·연산자·접근 방법을 지원하도록 확장하려 했다.

이 시점의 핵심 “관계형이니까 정해진 형태만 담는다”가 아니라, 관계형 기반 위에서 표현할 수 있는 데이터와 연산을 늘리자는 방향이다. 1986년 POSTGRES가 JSON을 지원했다는 뜻은 아니다.

POSTGRES 논문에서 현대 JSON 지원까지 보기 →
2012 / 14Spanner의 지역성 설계 / PostgreSQL의 JSON·jsonb 지원

“다른 접근의 장점을 함께 쓸 수 있다”

마지막 항목에는 성격이 다른 두 사례가 들어 있다. 하나는 어떤 모양의 데이터를 표현하는가이고, 다른 하나는 관련 데이터를 어떻게 배치하는가다.

PostgreSQL: 테이블 안에서 문서도 다룬다

PostgreSQL은 2012년 9.2에서 json을, 2014년 9.4에서 jsonb를 도입했다. 예를 들어 사용자 ID와 고유 제약은 관계형 열로 관리하고, 이력서의 중첩된 내용은 JSON으로 둘 수 있다. 관계형 표현과 문서 표현을 한 DB 안에서 함께 쓰는 사례다.

Spanner: 테이블을 나눠도 지역성을 설계한다

Spanner는 Google의 분산 데이터베이스 시스템이다. 2012년 논문에서는 사용자와 앨범을 별도 테이블로 유지하면서, 관련 데이터의 배치 관계를 선언한다. 논리적으로 테이블을 나누는 것과 관련 데이터를 가까이 두도록 설계하는 것은 양립할 수 있다.

이 시점의 핵심 각 모델을 유지하면서 다른 접근의 유용한 기능을 받아들일 수 있다. 다만 JSON 지원과 저장 지역성은 서로 다른 기능이며, 지원 기능이 겹친다고 저장·갱신 비용까지 같아지지는 않는다.

단일한 교체 순서나 원인으로 읽지 않기

이 접근들은 서로 공존하고 경쟁했다. IMS는 Codd 논문의 비교 대상 중 하나이지 관계형 모델의 유일한 탄생 원인으로 입증된 것은 아니다. 문서 DB도 “네트워크 모델이 실패해서 나온 후계자”라고 설명하지 않는다. 그래프 모델의 역사 역시 별도의 흐름을 가진다.

02계층 모델

트리는 틀리지 않았다.
공유되는 관계가 어려웠다.

CASE 01 / IBM IMS / 1968

IBM의 회고에 따르면 IMS는 Apollo 계획의 부품·조립 정보 관리에서 출발했다. “제품 아래 조립품, 그 아래 부품”처럼 계층을 따라 정보를 조직하는 것은 당시 업무를 다루는 유용한 방식이었다. 계층 자체가 잘못된 발상은 아니었다.

문제는 “민수도 지연도 같은 수업을 듣는다”

일반적인 부모–자식 트리에서는 각 노드가 하나의 부모 아래에 놓인다. 하지만 현실의 수업은 여러 학생이 공유한다. 수업 내용을 복사하면 수정 부담이 생기고, 별도 레코드를 참조하면 트리 바깥의 연결과 조회를 다뤄야 한다. 엄격한 트리만으로 공유 관계를 모두 담기 어려운 것이다.

실제 IMS 제품에는 논리적 관계 등 추가 기능이 있다. 여기서 비교하는 것은 기본적인 계층 모델의 제약이지 “IMS에서는 다대다를 절대 구현할 수 없다”는 주장이 아니다.

CASE 02 / CODASYL & CHARLES BACHMAN / 1971–1974

CODASYL은 위원회 이름이고, Bachman은 탐색 중심 접근을 설명한 연구자 이름이다. CODASYL 계열의 Network Model은 레코드 사이에 여러 관계를 두었다. 여기서 owner–member set은 한 레코드와 그에 연결된 여러 레코드의 관계를 표현하는 방식이다. 하나의 레코드가 여러 set 관계에 참여할 수 있어, 단일 트리보다 다양한 관계를 다룰 수 있었다. 학생–수업은 아래처럼 수강 레코드가 양쪽 관계에 참여하는 방식으로 생각할 수 있다.

“a mobile navigator who is able to probe and traverse a database at will.”

Bachman, The Programmer as Navigator, 1973

Bachman은 이를 낡은 제약이 아니라 데이터베이스 내부를 능동적으로 이동하는 새로운 프로그래밍 관점으로 제시했다. 1973년 8월 튜링상 강연이 같은 해 11월 CACM에 실렸다.

질문을 바꾸어 보기

민수 → 수강 A → 데이터베이스

학생에서 출발해 수강 관계를 따라가고, 각 수업에 도착한다.

개념을 설명하는 경로 모형이다. 실제 CODASYL 문법·커서·실행 엔진을 구현한 시뮬레이터가 아니다.

문제가 바뀌면, 길도 다시 정해야 한다

코드는 현재 레코드와 set의 탐색 상태를 관리하며 경로를 따라간다. 여러 경로가 같은 레코드에 닿는 다대다 관계에서는, 중첩 탐색과 복귀 위치까지 생각해야 한다. DDIA의 “n차원 데이터 공간 항해”는 이런 경로 관리의 비유이지, 실제 수학적 차원을 뜻하지 않는다.

예측 가능한 업무의 접근 경로를 직접 설계하면 효율을 노릴 수 있다. 반면 새로운 질문이 추가될 때는 데이터 연결과 탐색 코드에 대한 의존성이 변경을 어렵게 만든다. 바로 이 지점에서 관계형 접근과의 논쟁이 선명해진다.

PAPER 01 / E. F. CODD / CACM / 1970.06

Edgar F. Codd(에드거 F. 코드)는 IBM 연구원이자 관계형 모델을 제안한 사람이다. SQL 자체를 만든 사람은 아니다. 그의 논문은 단순한 “표가 트리보다 보기 좋다”는 제안이 아니다. 저장과 접근 방식이 바뀔 때 응용 프로그램도 함께 바뀌어야 하는 의존성을 문제로 삼았다.

“ordering dependence, indexing dependence, and access path dependence.”

Codd, A Relational Model of Data for Large Shared Data Banks, §1
Ordering

저장·제공 순서에 프로그램이 기대고 있지는 않은가?

Indexing

Access path

특정 경로를 알아야만 필요한 데이터에 도달하는가?

SELECT c.title
FROM students AS s
JOIN enrollments AS e ON e.student_id = s.id

WHERE s.name = '민수';

질의에는 필요한 데이터와 값 사이의 조건을 적는다. 어떤 인덱스를 쓸지, 어느 테이블부터 읽을지는 실행 시스템의 일이 된다. 다만 1970년 논문이 이 실행 시스템 전체를 이미 완성한 것은 아니다. 논리 모델의 제안과 효율적인 구현은 구분해야 한다.

정확한 표현

관계형 모델이 접근 경로를 없앤 것이 아니다. 논리적인 질의와 물리적 접근 경로를 분리하고, 경로 선택을 DB 쪽에 맡길 수 있게 한 것이다.

PAPERS 03–04 / SYSTEM R 1976 / SELINGER 외 1979

System R은 IBM의 관계형 연구 시스템이고, Patricia Selinger(퍼트리샤 셀린저)는 실행계획 선택 논문의 저자 중 한 명이다. 애플리케이션이 “무엇을 원하는지”만 말해도 DB 내부에서는 여전히 “어떻게 찾을지”를 정해야 한다. 그 선택은 사라지는 것이 아니라 시스템 내부로 이동한다. System R은 관계형 접근을 실제 시스템으로 구현하려 했고, 1976년 논문에도 접근 경로를 고르는 옵티마이저가 등장한다.

Selinger 등의 1979년 논문은 조인 순서와 테이블 접근 경로를 비용 기반으로 선택하는 방법을 자세히 설명한다. 카탈로그 통계와 비용식, 중간 결과의 유용한 정렬 순서인 interesting orders도 계획 선택에 영향을 준다.

이 변화는 “DB가 모든 것을 알아서 완벽하게 한다”는 뜻은 아니다. 통계가 부정확하거나 탐색 범위가 제한되면 비효율적인 계획을 고를 수 있다. 오늘날에도 인덱스 설계와 실행계획 분석이 필요한 이유다.

책임의 이동

탐색 경로를 매번 작성하는 책임 → 경로를 고를 수 있는 DB를 만들고 운영하는 책임

이력서의 경력·학력·연락처처럼 한 사람에게 속하고 함께 조회하는 데이터는 문서 안에 중첩하면 자연스럽다. 이것이 DDIA에서 문서 모델이 계층 모델을 일부 닮았다고 설명하는 지점이다. 옛 모델 전체로 돌아간다는 뜻은 아니다.

문서 경계가 조회 경계와 맞으면

함께 읽는 관련 데이터의 지역성을 얻고, 여러 위치를 찾아 결합하는 작업을 줄일 수 있다. 하지만 문서 크기·인덱스·캐시·갱신 방식에 따라 달라지므로 보편적인 “몇 배”는 없다.

회사 레코드는 공유 / 조회 시 결합 필요

복사하면 읽을 때의 Join을 줄이는 대신, 공유 정보를 바꿀 때 변경 전파·실패 재시도·누락 확인이 필요하다. 참조하면 중복 수정은 줄지만 조회 시 DB 내부 Join이나 애플리케이션 결합을 고민해야 한다.

애플리케이션 Join은 여러 DB 요청·전송·결합 비용을 만들 수 있다. 특히 항목마다 개별 요청하는 N+1 패턴은 불리하다. 그렇다고 항상 요청이 하나씩 직렬 실행되는 것은 아니며, 배치 조회·캐시·DB의 Join 기능에 따라 비용은 달라진다.

모든 쓰기가 늘어나는 것은 아니다

민수의 자기소개를 고칠 때 지연 문서까지 수정할 필요는 없다. 문제는 여러 곳에 복사해 둔 공유 사실이 바뀔 때다. 반대로 주문 당시의 회사명·가격을 스냅샷으로 남긴 것이라면, 현재 값으로 일괄 갱신하는 것이 오히려 잘못일 수 있다.

PAPER 05 / STONEBRAKER & ROWE / THE DESIGN OF POSTGRES / 1986

POSTGRES는 현대 PostgreSQL로 이어지는 연구 시스템이다. Michael Stonebraker(마이클 스톤브레이커)와 Lawrence Rowe(로런스 로)가 설계 논문을 썼다. 복합 데이터 수용이 JSON 열풍과 함께 처음 시작된 것은 아니다. 1986년 POSTGRES 설계는 복합 객체와 사용자 정의 자료형·연산자·접근 방법의 확장성을 목표로 했다. 동시에 관계형 모델의 변경은 최소화하려 했다.

“The relational model … has been preserved”

Stonebraker & Rowe, The Design of POSTGRES, §3 — 생략부호 포함 발췌
1986POSTGRES 설계
복합 객체·확장성
1994SQL 인터프리터 추가
Postgres95로 이어짐
2012PostgreSQL 9.2
json 자료형

jsonb 자료형

이 연표는 1986년부터 JSON 도입까지 하나의 구체적인 구현 계획이 이어졌다는 주장이 아니다. 관계형 시스템도 복잡한 데이터를 받아들이려는 설계 목표를 오래 다뤘다는 사례다.

-- 현대 PostgreSQL의 혼합 모델 예시
CREATE TABLE profiles (
  user_id bigint PRIMARY KEY,
  resume jsonb NOT NULL
);

SELECT user_id, resume -> 'positions' AS positions
FROM profiles;

PostgreSQL 18 공식 문서는 관계형 표현과 JSON이 같은 애플리케이션에서 공존하며 보완할 수 있다고 설명한다. 다만 JSON 문서 변경도 행 수준 잠금을 획득하므로, 큰 문서를 자주 수정하면 경합을 고려해야 한다. JSON을 지원한다는 사실이 모든 저장·갱신 특성을 문서 DB와 같게 만들지는 않는다.

09모델의 경계

기능은 겹쳐도,
모델의 중심은 같지 않다.

CASE 03 / SPANNER OSDI 2012 & MODERN MODEL CHOICES

관계형 테이블도 지역성을 설계할 수 있다

Spanner는 Google의 분산 데이터베이스 시스템이다. 여기서 지역성이란 함께 읽는 관련 데이터를 가까이 두어, 여러 곳을 찾아다니는 부담을 줄이려는 성질이다. Spanner의 2012년 논문은 Users와 Albums를 별도 테이블로 두면서, INTERLEAVE IN PARENT로 배치 관계를 선언하는 사례를 보여준다. 논리적으로 분리된 테이블과 물리적 지역성은 양립할 수 있다는 뜻이다.

그래프 모델은 “연결을 질문의 중심”에 둔다

문서가 소유·중첩의 경계를, 관계형 질의가 값 사이의 조건을 잘 드러낸다면, 그래프 모델은 노드·간선과 경로 패턴을 전면에 둔다. 친구의 친구, 여러 단계의 의존 관계처럼 연결을 따라 묻는 질문 자체가 핵심일 때 유용한 표현이 된다.

사람 A친구 →사람 B근무 →회사 C소재 →지역 D

연결을 다룬다는 이유로 CODASYL과 현대 그래프 DB를 동일시해서는 안 된다. 현대 그래프 시스템 중에는 선언적인 패턴 질의를 지원하는 것도 있다. RDF와 Property Graph도 같은 모델은 아니다. Angles·Gutierrez의 2008년 서베이는 그래프 모델의 여러 흐름을 정리한 자료이지, 그해 그래프 DB가 탄생했다는 증거가 아니다.

수렴의 의미

서로 같은 것이 되기보다,
자기 모델을 유지하며 유용한 기능을 받아들인다.

PostgreSQL의 JSON은 표현 기능이 겹치는 사례이고, Spanner의 interleaving은 저장 지역성 설계의 사례다. 이 둘을 동일한 종류의 수렴으로 섞지는 말자. 표현·질의 기능·물리적 저장을 나누어 비교해야 한다.

10정리와 토론

최종 승자가 아니라,
내 질문과 변경에 맞는 선택

모델중심 표현설계자가 특히 신경 쓸 것공유·다대다에서의 쟁점
계층부모–자식 트리루트·계층·탐색 시작점엄격한 트리만으로 공유를 담기 어려움
Network레코드와 set 연결접근 경로·현재 위치·탐색 상태표현력은 늘지만 탐색 코드가 복잡해짐
관계형테이블·값·조건키·제약·질의·인덱스·실행계획Join을 시스템이 수행하되 비용은 여전히 존재
문서중첩된 문서문서 경계·중복·참조 정책복사본 일관성 또는 문서 간 결합 필요
그래프노드·간선·경로관계 의미·탐색 패턴·범위관계는 직접 표현하나 큰 탐색의 비용은 남음

비교표는 모델의 중심 관점을 요약한 것이다. 실제 제품은 여러 기능을 함께 제공하므로 제품별 실행·저장 특성을 이 표만으로 단정할 수 없다.

  1. 트리는 여전히 유용하다.

    소유와 함께 읽는 경계가 맞으면 자연스럽다. 모든 공유 관계를 하나의 트리에 가두려 할 때 문제가 커진다.

  2. 연결을 표현하는 능력과 변경하기 쉬움은 다르다.

    Network Model과 관계형 모델의 중요한 차이는 애플리케이션 인터페이스와 경로 선택의 책임이었다.

  3. 복잡도는 사라지기보다 이동한다.

    탐색 코드, 옵티마이저, 문서 경계와 복사본 관리 중 어디에 책임을 둘지 선택한다.

  4. 기능의 수렴은 비용 특성의 동일화가 아니다.

    JSON 지원·Join 지원·지역성 기능을 확인한 다음, 실제 조회·갱신·경합 패턴으로 판단한다.

토론할 질문

지금 우리 서비스에서 가장 자주 함께 읽는 것과,
여러 곳에서 공유하며 자주 바뀌는 것은 같은가?

다르다면 문서 경계와 공유 엔티티를 나눌 이유가 있다. “어느 DB가 더 최신인가?”보다 먼저 답할 질문이다.

측정·사실·해석을 구분했다

연도·저자·제목·기능은 출처에서 확인한 사실이다. “복잡도가 이동한다”는 발표의 종합 관점이다. 학생–수업·회사명·SQL·탐색 경로·실행계획·배치 그림은 교육용 재구성이다. 벤치마크와 실제 CODASYL 실행을 수행한 자료가 아니다.
