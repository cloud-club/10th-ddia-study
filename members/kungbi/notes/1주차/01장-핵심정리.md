# DDIA 1장 — 중요하게 읽은 개념 정리

## 1. 용어 사전

| 용어 | 의미·구분 |
|---|---|
| **Reliability — 신뢰성** | 정해진 유형의 결함이나 실수에도 기대한 기능과 성능을 유지하는 것. |
| **Scalability — 확장성** | 특정 방식으로 부하가 늘 때 좋은 성능을 유지할 대응 방법이 있는 것. |
| **Maintainability — 유지보수성** | 사람이 계속 운영·이해·변경하기 쉬운 것. |
| **Fault — 결함** | 구성 요소가 기대한 동작에서 벗어난 것. 예: 디스크 고장. |
| **Failure — 장애** | 사용자에게 필요한 서비스를 약속대로 제공하지 못하는 것. 구성 요소의 Fault가 반드시 서비스의 Failure가 되지는 않는다. |
| **Fault-tolerant — 내결함성이 있는** | 정해진 유형의 Fault가 서비스의 Failure로 번지지 않게 견디는 성질. 모든 종류의 결함을 견딘다는 뜻은 아니다. |
| **Resilient / Resilience — 회복력이 있는 / 회복력** | 역경을 견디고 기능을 유지·회복하는 성질. 이 장에서는 Fault-tolerant와 가까운 의미로 쓴다. |
| **Redundancy — 중복 구성** | 부품·서버·복사본 등을 추가해 하나가 고장 나도 역할을 이어갈 수 있도록 준비하는 것. |
| **Hot-swap — 핫 스왑** | 시스템 전체를 끄지 않고 지원되는 부품을 교체하는 것. CPU는 이를 지원하는 특수 하드웨어·OS에서만 가능하다. |
| **Downtime — 중단 시간** | 서비스를 이용할 수 없는 시간. |
| **High Availability — 고가용성** | 장애·유지보수 중에도 서비스를 제공하도록 중단을 최소화하려는 성질. |
| **Flexibility — 유연성** | 필요에 맞춰 구성이나 자원을 바꾸기 쉬운 폭넓은 성질. |
| **Elasticity — 탄력성** | 부하 변화에 맞춰 자원을 늘리거나 줄이는 성질. 책에서는 부하 증가를 감지해 자동 확장하는 시스템을 설명한다. Resilience의 장애 대응과 구분한다. |
| **Load Parameter — 부하 매개변수** | 부하를 설명하는 숫자. 초당 요청 수, 읽기·쓰기 비율, 데이터 크기, 팔로워 수 분포 등. |
| **Throughput — 처리량** | 단위 시간에 처리한 작업량. 요청 수·레코드 수·바이트 수 등 단위를 명시한다. |
| **Response Time — 응답 시간** | 클라이언트의 요청 전송부터 응답 수신까지의 전체 시간. 네트워크·대기·실제 처리를 포함한다. |
| **Latency — 지연 시간** | 이 책에서는 처리를 기다리는 시간. 현업에서는 전체 응답 시간 등의 뜻으로도 쓰이므로 측정 범위를 확인한다. |
| **Service Time — 처리 시간** | 실제로 요청을 처리하는 데 걸린 시간. 대기 시간과 구분한다. |
| **Tail Latency — 꼬리 지연** | 응답 시간 분포의 느린 쪽 꼬리. p95·p99 같은 상위 백분위로 관찰한다. |
| **SLO — Service Level Objective** | 정해진 측정 조건과 기간에서 달성하려는 서비스 품질 목표. |
| **SLA — Service Level Agreement** | 제공자와 이용자 사이의 서비스 수준 합의·계약. 미달 시 보상 등의 조건을 포함할 수 있다. |

## 2. 응답 시간을 측정하는 위치

```text
클라이언트 요청 전송
→ 네트워크 이동
→ 큐에서 처리 차례 대기
→ 실제 처리
→ 네트워크 이동
→ 클라이언트 응답 수신

Response Time은 이 전체를 클라이언트 관점에서 측정한 시간이다.
```

Throughput이 높아도 개별 요청의 Response Time이 짧다고 보장할 수 없다. 또한 서버 내부의 처리 시간만 측정하면 사용자가 겪는 네트워크·대기 시간을 놓칠 수 있다. **Latency는 현업에서 전체 응답 시간이나 네트워크 지연을 뜻하기도 하므로, 지표마다 측정 구간을 확인해야 한다.** — 책 13–16쪽

## 3. Head-of-Line Blocking: 내 작업은 짧아도 앞의 작업 때문에 늦을 수 있다

처리 가능한 작업자나 자원이 제한돼 있으면 느린 앞선 작업 때문에 뒤의 작업이 기다릴 수 있다. 이것이 이 장에서 설명하는 **Head-of-Line Blocking — 선두 차단**이다. — 책 15–16쪽

```text
처리 순서: [오래 걸리는 요청 A] → [짧은 요청 B] → [짧은 요청 C]
                                  ↑
                     처리 자체는 짧아도 앞에서 기다린다
```

이 그림은 하나의 처리 슬롯을 가정한 단순화다. 실제 서버에 작업자가 여럿 있으면 앞선 요청 하나가 모든 후속 요청을 막는 것은 아니지만, 느린 작업이 제한된 슬롯을 점유하면 대기열이 늘 수 있다.

**느린 요청 하나의 문제가 뒤 요청들의 긴 Response Time으로 번질 수 있으므로**, 내부 처리 시간뿐 아니라 클라이언트 쪽 전체 응답 시간을 봐야 한다.

### 익숙한 예: Redis와 Node.js

- **Redis:** 같은 인스턴스에서 많은 Key를 훑는 무거운 명령이 실행되면, 뒤의 간단한 `GET`도 기다릴 수 있다. `GET` 자체가 느린 것이 아니라 앞선 명령 때문에 응답이 늦어진다. 단, `BLPOP`은 기다리는 클라이언트를 대기시키는 것이지 Redis 전체의 실행을 막는 것은 아니다.
- **Node.js:** 요청 A가 큰 `JSON.parse()`나 긴 동기 반복문으로 Event Loop를 점유하면, 같은 Event Loop에서 처리할 요청 B·C도 기다린다. 반면 비동기 DB 호출을 `await`하는 동안에는 다른 요청을 처리할 수 있다. `async`를 붙여도 내부의 동기 계산이 별도 스레드로 옮겨지는 것은 아니다.

## 4. 실전 백분위: 여러 호출의 느린 꼬리가 사용자 요청에서 증폭된다

사용자 요청 하나를 완성하려고 상품·재고·배송 API를 병렬 호출하고 **모든 결과가 필요하다**고 해보자.

```text
사용자 요청
├─ 상품 API ── 빠르게 완료
├─ 재고 API ── 빠르게 완료
└─ 배송 API ───────────── 느리게 완료
                           ↓
                      최종 응답 가능
```

병렬 호출은 시간을 모두 더하지는 않지만 가장 느린 호출을 기다려야 한다. 동시에 시작한 필수 호출을 단순화하면 다음과 같다. Gateway 자체 처리와 통신 등 추가 비용은 별도다.

```text
전체 응답 시간 ≈ 가장 느린 필수 백엔드 호출 시간 + 추가 비용
```

개별 백엔드에서 느린 호출이 드물어도, 호출이 많아지면 그중 하나가 느릴 가능성이 커진다. 이를 **Tail Latency Amplification — 꼬리 지연 증폭**이라고 한다. — 책 16쪽

각 호출이 같은 기준을 넘겨 느려질 확률이 1%이고, 호출들의 느려짐이 서로 독립적이라고 가정하면:

```text
하나 이상 느릴 확률 = 1 − (모두 빠를 확률)
                   = 1 − 0.99^호출수

10회 호출: 약 9.56%
35회 호출: 약 29.66%
```

**“각 백엔드는 거의 항상 빠른데, 사용자는 꽤 자주 느리다”는 상황이 가능한 이유**다. 이 계산은 설명용이며, 실제 서비스에서는 공유 자원·동시 장애 등으로 지연이 서로 연관될 수 있다. 각 호출의 p99 기준이 서로 다르다면 하나의 공통 사용자 지연 기준으로 바로 해석해서도 안 된다.

### Rolling Window와 Prometheus Bucket은 서로 다른 축이다

**Rolling Window는 “언제의 데이터를 볼지”, Bucket은 “응답 시간을 어떤 범위로 묶을지”를 정한다.** 같은 구조를 가리키는 말이 아니며 함께 사용한다.

```text
시간 축 — Rolling Window
14:00에 조회 → 최근 10분: 13:50–14:00
14:01에 조회 → 최근 10분: 13:51–14:01

값의 축 — Histogram Bucket
응답 시간이 0.1초 이하 / 0.5초 이하 / 1초 이하 / 전체
```

Prometheus의 **Classic Histogram**에서는 `le`가 Bucket의 상한을 나타낸다. 각 Bucket은 “그 상한 이하인 관측값의 누적 개수”다. 예를 들어 0.08초인 요청 하나는 `le="0.1"`, `le="0.5"`, `le="1"`, `le="+Inf"`를 모두 증가시킨다. 서로 배타적인 구간 카운트가 아니므로 이 Bucket 값들을 전부 더하면 안 된다.

다음은 책의 개념을 Prometheus에 연결한 보충 예시다. 메트릭 이름은 설명용이며, 기존에 수집된 Classic Histogram이 있다고 가정한다.

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[10m])
  )
)
```

- **`le` / `_bucket`**: 응답 시간의 분포를 나누는 기준이다.
- **`[10m]`**: 매 평가 시점에서 과거 10분의 샘플을 선택하는 시간 구간이다. Rolling Window에 대응한다.
- **`rate(...)`**: 누적 Counter에서 그 구간의 초당 증가율을 추정한다. Counter 재시작도 고려한다.
- **`sum by (le)`**: 같은 상한의 Bucket을 서버들에 걸쳐 합친다. `le`가 다른 Bucket들을 하나로 더하는 것이 아니다.
- **`histogram_quantile(0.99, ...)`**: 합친 분포에서 p99를 근사한다. 응답 시간 단위는 메트릭과 같은 초이며 정확도는 Bucket 설정 등에 영향을 받는다.

이 쿼리를 매분 평가하면 “최근 10분 p99”가 매분 갱신된다. **10분은 관측 구간 길이, 1분은 갱신 간격**이다. Bucket 자체가 최근 10분만 기억하는 것은 아니며, Prometheus가 저장한 시계열을 시간 구간으로 선택해 계산한다.

이 예시는 조회된 모든 인스턴스·경로 등을 하나의 분포로 합친다. 특정 API 성능을 보려면 라벨로 선택하거나 `sum by (le, route)`처럼 필요한 집계 기준을 남긴다. Native Histogram은 표현과 쿼리 형태가 다르다. — [Prometheus 공식 설명](https://prometheus.io/docs/practices/histograms/)

### 많은 응답 시간을 어떻게 효율적으로 보관할까?

초당 1,000개 요청이면 10분 동안 600,000개의 측정값이 생긴다. 전부 보관하고 정렬할 수는 있지만, 규모가 커지면 메모리·계산 비용을 고려해야 한다. 책은 다음 방법들을 소개한다.

| 방법 | 이해할 핵심 |
|---|---|
| **Forward Decay** | 오래된 값보다 최근 값의 영향력을 크게 두는 시간 감쇠 모델. 고정된 최근 10분 구간과 똑같은 의미는 아니다. |
| **t-digest** | 측정값들을 가중치를 가진 묶음으로 요약해 백분위를 근사하는 방법. |
| **HdrHistogram** | 넓은 측정 범위를 정해진 유효 정밀도로 기록하고 분포와 백분위를 구하는 히스토그램 구현. 단순한 임의 구간 표와 실제 저장 구조는 다르다. |

이 도구들이 시간 구간 관리를 전부 자동으로 해결하는 것은 아니다. 최근 구간의 집계라면 오래된 데이터나 구간을 제외하는 설계도 필요하다.

### p99들을 평균 내면 전체 p99가 되지 않는다

각 서버의 p99는 분포를 숫자 하나로 요약한 것이므로, 원래 요청들의 분포를 복원할 수 없다. 요청 수로 가중평균해도 일반적으로 전체 p99가 되지 않는다.

설명용 반례:

| 측정 대상 | 요청 분포 | p99 |
|---|---|---|
| 서버 A | 요청 100개가 모두 10ms | 10ms |
| 서버 B | 요청 100개가 모두 1,000ms | 1,000ms |

두 p99의 평균은 505ms지만, 전체 요청 200개를 합친 p99는 1,000ms다. 요청 수가 같아도 평균은 틀릴 수 있다.

```text
잘못된 집계: 각 서버의 p99 → 평균 → 전체 p99라고 부르기
올바른 집계: 원본 측정값 또는 호환되는 Histogram을 합침 → p99를 다시 계산
```

Histogram은 각 응답 시간 구간에 들어온 요청 수를 기록한다. 구간·단위·정밀도 등이 호환되는 Histogram을 합치면 전체 분포에서 백분위를 구할 수 있다. 근사 방식에서는 구간 설정 등에 따라 오차가 생긴다.

단, **백엔드 호출들의 Histogram을 합친 p99와 최종 사용자 요청의 p99는 다른 지표**다. 전자는 개별 호출의 분포이고 후자는 여러 호출의 대기와 나머지 처리까지 포함하므로, 사용자 요청 전체를 별도로 측정해야 한다.

### 부하 테스트: 서버가 느릴 때 테스트 도구가 부하를 줄여버리면 안 된다

확인하고 싶은 상황이 **“서버가 느려져도 새로운 요청이 계속 들어오는 상황”**이라고 해보자. 실제로는 앞선 사용자 요청이 끝나지 않았어도 다른 사용자가 새 요청을 보낼 수 있다.

그런데 테스트 도구가 “앞의 응답을 받아야 다음 요청을 보낸다”면 다음처럼 움직인다.

```text
테스트 도구: 요청 A 전송 → A의 응답을 기다림 ─────────→ 응답 수신 → 요청 B
서버가 느려지는 동안:     새로운 요청을 보내지 않음
```

이 도구에서는 **서버가 느려질수록 새 요청이 덜 들어간다.** 의도했던 유입 부하가 유지되지 않으므로, 계속 들어오는 요청들이 줄 서서 기다리는 상황을 충분히 만들지 못한다. 전송한 A의 느림은 기록해도, 그동안 원래 도착했어야 할 요청들의 대기는 측정에서 빠질 수 있다. 관련된 측정 문제를 **Coordinated Omission**이라고 부른다.

반대로 도착률을 기준으로 요청을 시작하는 방식은 앞선 응답과 새 요청의 도착을 분리한다.

```text
예정된 도착: 요청 A → 요청 B → 요청 C → 요청 D
서버 상태:   A 처리 중… B·C·D도 도착 → 처리 슬롯이 없으면 대기
```

이래야 서버가 느려졌을 때 실제로 대기가 얼마나 늘고 사용자 응답 시간이 어떻게 악화되는지 볼 수 있다.

| 모델 | 요청·작업의 시작 기준 | 어울리는 검증 |
|---|---|---|
| **Closed Model** | 정해진 가상 사용자들이 앞선 작업을 끝낸 뒤 다음 작업을 시작 | 고정된 수의 사용자가 응답을 보고 다음 행동을 하는 상황 |
| **Open Model** | 앞선 작업 완료와 독립적으로 정해진 도착률에 따라 새 작업을 시작 | 외부 요청이 계속 유입될 때의 성능·포화 상태 |

**Closed Model 자체가 틀렸다는 뜻은 아니다. 재현하려는 상황과 테스트 도구의 동작이 달라지는 것이 문제다.** k6에서는 `constant-vus`가 Closed Model, `constant-arrival-rate` 등이 Open Model에 해당한다. 도착률 기반 테스트도 부하 생성기 자원이 부족하면 예정한 작업을 시작하지 못할 수 있으므로, 실제 도착률과 `dropped_iterations`도 확인해야 한다. — 책 16쪽 및 [k6 공식 설명](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

## 5. Maintainability: 운영·이해·변경을 쉽게 만드는 것

유지보수는 버그 수정만이 아니다. 운영, 장애 조사, 새 기능 추가, 플랫폼 변경, 기술 부채 정리까지 포함한다. 책은 세 측면을 강조한다. — 책 18–22쪽

| 측면 | 의미 | 예시 |
|---|---|---|
| **Operability — 운용성** | 시스템을 관찰하고 운영하기 쉬움 | 원인 추적에 필요한 지표·로그, 배포·롤백 도구, 이해하기 쉬운 운영 문서 |
| **Simplicity — 단순성** | 사람이 이해하기 어렵게 만드는 불필요한 복잡도를 줄임 | 일관된 명명, 적절한 책임 분리, 복잡한 구현을 명확한 인터페이스로 감추는 추상화 |
| **Evolvability — 발전성** | 요구사항과 환경 변화에 맞춰 시스템을 바꾸기 쉬움 | 새 기능이나 저장 방식 변경의 영향을 제한하고 테스트로 확인할 수 있음 |

**Simplicity는 기능을 무조건 줄이는 것이 아니다.** 사용자 문제 자체가 요구하는 복잡도와 달리, 구현 방식 때문에 추가된 **Accidental Complexity — 우발적 복잡도**를 줄이는 것이 중요하다. 좋은 **Abstraction — 추상화**는 세부 구현을 명확한 경계 뒤로 숨겨 이를 돕는다.

책에서 말하는 **“성능 문제 해결을 목표로 한 해킹”**도 보안 침입이 아니다. 성능을 빨리 개선하려고 덧붙인 특수 처리나 임시방편을 뜻한다. 예외가 쌓이면 변경 시 알아야 할 규칙이 늘어난다. 캐시나 미리 계산하기 자체가 나쁜 것이 아니라, **그 처리의 이유와 갱신 규칙을 이해하고 관리할 수 있는지**가 중요하다.

## 6. 윤초가 어떻게 실제 장애를 일으켰나?

- 2012년 윤초 처리 때 일부 Linux 커널에서 시스템 시각 조정에 맞춰 타이머 기준을 갱신하는 처리가 빠졌다.
- 타이머 쪽이 시스템 시각보다 앞선 상태가 되면서 일부 짧은 대기가 즉시 만료되고, 기다리려던 프로그램이 다시 시도하는 반복으로 CPU를 소모했다.
- 윤초 자체가 하드웨어를 망가뜨린 것이 아니라, 드문 시간 변화가 잠재된 소프트웨어 버그를 드러낸 사례다. 여러 서버가 같은 버그를 가지면 함께 영향을 받을 수 있다.
- 책 9쪽의 사례를 보충한 설명이며, 세부 메커니즘은 당시 Linux 타이머 분석을 대화에서 확인한 내용이다.
