# GitHub 2012 MySQL Failover 장애 분석

2012년 9월 10~11일에 발생한 GitHub 장애를, 구성 요소의 역할부터 사고의 진행 과정까지 연결해 설명한다. 사고 사실은 GitHub의 공식 보고서를 기준으로 하고, 이해를 위한 도식·ID 예시와 일반적인 설계 개선안은 실제 운영 내역과 구분한다.

## 1. 사고 개요

GitHub에서는 DB 서버를 자동으로 교체하는 과정에 문제가 생겨, 데이터가 오래된 MySQL 복제본이 쓰기를 받는 Primary가 됐다. 그 결과 MySQL과 Redis에서 같은 ID가 가리키는 대상이 어긋났고, 일부 대시보드 이벤트와 저장소가 잘못 연결됐다.[1]

이 문제로 비공개 저장소 16개가 권한 없는 사용자에게 접근 가능한 상태가 됐으며, GitHub는 해당 소유자들에게 직접 연락했다고 밝혔다.[1]

| 항목 | 공식 보고서에서 확인한 내용 |
| --- | --- |
| 전체 사고 기간 | 2012년 9월 10~11일의 두 차례 장애 |
| 오래된 Primary가 활성화된 구간 | 9월 11일 08:19~08:26 PDT, 7분 |
| 비공개 저장소 영향 | 16개가 해당 구간에 협업자·팀원 외 사용자에게 접근 가능한 상태였음 |
| 두 장애의 합산 중단 시간 | 1시간 46분 |
| 별도 성능 저하 | 약 1시간 |
| 공식 보고서 표시 발행일 | 2012년 9월 14일 |

7분은 전체 서비스 중단 시간이 아니다. 오래된 DB가 Primary로 동작하면서 데이터 불일치와 저장소 노출이 발생한 구간이다. 1시간 46분은 두 차례 장애의 합산 중단 시간이다.[1]

또한 접근 가능한 상태였다는 사실과 실제로 모든 저장소를 누군가 열람·복제했다는 주장은 다르다. 공식 보고서의 표현을 넘어 실제 접근 횟수나 다운로드 범위를 추정하지 않는다.

## 2. 사고 이전 시스템 구조

### 2.1. Primary, Replica, Standby는 무엇인가?

Primary는 애플리케이션의 쓰기를 받는 DB다. Replica는 Primary의 변경을 복제해 자기 데이터를 유지하는 별도의 DB다. Replica가 있다는 이유만으로 모든 시점에 Primary와 완전히 같은 상태라고 단정할 수는 없다.

이 사건의 GitHub 보고서에서는 역할을 다음처럼 구분한다.[1]

| 당시 표현 | 이 글의 표현 | 역할 |
| --- | --- | --- |
| active, MySQL master | Primary | 읽기와 쓰기를 받는 MySQL |
| standby, read-only MySQL slave | Standby 역할의 Replica | 읽기 전용으로 제공되는 복제 MySQL |

**여기서 Standby는 전원이 꺼진 서버가 아니다.** 새 구성에서는 모든 노드에서 MySQL이 실행되고 있었고, Standby 역할은 읽기 전용 MySQL을 뜻했다.[1]

평소에 읽기를 제공할 수도 있고, 장애 시 쓰기 역할을 맡을 후보가 될 수도 있다. 다만 쓰기 역할을 넘기기 전에는 복제가 얼마나 따라왔는지와 서비스 준비 상태를 확인해야 한다.

### 2.2. DRBD는 무엇인가?

DRBD는 Distributed Replicated Block Device의 약자다. 서버의 디스크·파티션 같은 Block Device 내용을 다른 서버의 장치에 복제하는 소프트웨어다.[5]

쉽게 말하면, MySQL이 저장 장치에 기록한 내용을 저장 장치 계층에서 다른 서버에도 반영하는 방식이다. MySQL의 SQL이나 개별 테이블을 이해해 복제하는 기능은 아니다.[5]

```text
애플리케이션
    ↓
MySQL
    ↓
서버 A의 저장 장치
    ↓ DRBD가 장치의 변경을 복제
서버 B의 저장 장치
```

DRBD의 일반적인 Single-primary 구성에서는 해당 저장 장치를 한 노드만 Primary 역할로 사용한다. 다른 노드는 복제된 저장 장치를 유지하다가 역할을 넘겨받는다.[5]

다만 DRBD에는 여러 복제 모드가 있으므로, DRBD라는 이름만으로 모든 쓰기가 반드시 동기 복제됐다고 단정하지 않는다. GitHub 보고서에는 당시 DRBD 프로토콜과 세부 설정까지 공개돼 있지 않다.[5][1]

### 2.3. DRBD 기반 2노드 구성은 무엇이었나?

GitHub는 2012년 8월 중순까지 DRBD로 뒷받침되는 MySQL 서버 두 대를 사용했고, 이 구성에서 다른 서버로 전환하려면 MySQL을 Cold Start해야 했다고 설명한다.[1]

Cold Start는 새로 시작한 MySQL이 메모리 캐시 등 실행 상태를 준비해야 하는 상황을 뜻한다. 이 사례에서는 저장 장치의 복제본을 가지고 있다는 것과, 다른 MySQL 프로세스가 즉시 같은 성능으로 질의를 처리할 수 있다는 것이 달랐다.

이를 이해하기 위한 단순화된 도식은 다음과 같다. 실제 디스크 마운트 명령이나 운영 절차를 재현한 도식은 아니다.

```text
서버 A                         서버 B
현재 서비스하는 MySQL          전환 시 MySQL 시작 필요
       ↓                              ↑
  저장 장치 A ── DRBD 복제 ──→ 저장 장치 B
```

이 구성은 저장 장치의 데이터를 복제한다. 반면 MySQL 프로세스의 메모리 캐시까지 다른 서버에 그대로 옮기는 것은 아니다.

### 2.4. Pacemaker가 관리하는 3노드 MySQL 클러스터는 무엇인가?

GitHub는 기존 구성을 서버 세 대의 클러스터로 교체했다. 새 구성에서는 모든 노드에서 MySQL이 계속 실행되며, MySQL 복제와 역할 변경을 관리해 Primary를 바꾸도록 했다.[1]

정상 상태를 단순화하면 다음과 같다. A·B·C는 설명용 노드 이름이며, 이 그림이 사고 직전의 정확한 역할 배치를 재현하는 것은 아니다.

```text
                서버 A의 MySQL
                Primary, 쓰기 수락
                    │
             MySQL 변경 복제
              ┌─────┴─────┐
              ↓           ↓
       서버 B의 MySQL   서버 C의 MySQL
       Replica         Replica
       프로세스 실행 중  프로세스 실행 중
```

새 구조의 기대 효과는 장애가 날 때 다른 서버에서 MySQL을 처음부터 시작하는 부담을 줄이는 것이었다. GitHub 보고서는 트랜잭션을 Flush하고 `read_only` 값을 적절히 바꾼 뒤 VIP를 이동하는 방식으로 역할을 전환한다고 설명한다.[1]

그러나 **MySQL이 실행 중이라는 것과, Primary의 트래픽을 즉시 감당할 준비가 됐다는 것은 별개**다. 이 차이가 첫 번째 장애에서 드러났다.

### 2.5. Pacemaker, Heartbeat, PRM은 각각 무엇을 하나?

이 사건에서 클러스터는 MySQL 세 대만으로 동작한 것이 아니다. 노드 간 통신, 서비스 배치 결정, MySQL별 조작을 담당하는 구성 요소들이 함께 있었다.[1][2]

| 구성 요소 | 역할을 쉽게 풀면 | 직접 담당하지 않는 것 |
| --- | --- | --- |
| Heartbeat | 노드 간 통신과 클러스터 참여 상태를 전달하는 기반 | SQL 데이터 자체를 복제하는 기능 |
| Pacemaker | MySQL·VIP 같은 자원을 어느 노드에서 어떤 역할로 실행할지 관리 | MySQL의 모든 복제 동작을 자체적으로 구현하는 것 |
| Percona Replication Manager, PRM | Pacemaker가 MySQL과 복제를 관리할 수 있게 하는 MySQL 전용 연동 | 별도의 데이터베이스 엔진 |
| MySQL 복제 | Primary의 변경을 다른 MySQL에 반영 | 클러스터 전체의 서비스 배치를 모두 판단하는 것 |

Pacemaker는 High Availability Cluster Resource Manager다. 여기서 Resource는 MySQL 프로세스나 VIP처럼 클러스터가 관리하는 서비스·자원을 말한다.[6]

Pacemaker가 MySQL을 다루려면 MySQL을 시작·중지·감시하거나 승격하는 구체적인 방법이 필요하다. PRM의 MySQL Resource Agent는 이런 작업을 `start`, `stop`, `monitor`, `promote` 같은 인터페이스로 제공한다.[2]

Heartbeat는 클러스터 제어 메시지와 참여 상태를 다루는 통신 계층이다. 이름이 비슷하더라도 노드 간 Heartbeat 통신과 PRM이 수행하는 MySQL Health Check를 같은 검사로 혼동하지 않는다.[2][1]

```text
노드 간 상태·제어 메시지 전달
          Heartbeat
              ↓
자원 배치·역할 전환 판단과 조정
          Pacemaker
              ↓
MySQL에 필요한 시작·중지·감시·승격 작업
       PRM Resource Agent
              ↓
        MySQL과 MySQL 복제
```

위 그림은 역할 구분을 위한 도식이다. 실제 구현의 모든 호출 경로나 메시지 방향을 표시한 것은 아니다.

2012년 PRM 설치 가이드는 기본 예시로 Corosync를 설명하지만 Heartbeat도 통신 계층으로 사용할 수 있다고 명시한다. 이 사건의 GitHub는 Heartbeat를 사용했다고 보고했으므로, 가이드의 기본 예시를 GitHub의 실제 구성으로 바꿔 읽어서는 안 된다.[2][1]

### 2.6. VIP는 무엇이며 왜 이동시키나?

VIP는 Virtual IP다. 여기서는 특정 물리 서버에 고정된 주소가 아니라, 서비스를 제공할 노드로 옮겨 붙일 수 있는 접속 주소로 이해하면 된다.

애플리케이션이 서버 A의 고유 주소에만 접속한다면 Primary가 서버 B로 바뀔 때 접속 설정도 바꿔야 한다. VIP를 쓰면 애플리케이션은 같은 서비스 주소를 사용하고, 클러스터가 그 주소를 새 Primary 쪽으로 이동시킬 수 있다.

```text
전환 전
애플리케이션 → 쓰기용 VIP → 서버 A

전환 후
애플리케이션 → 같은 쓰기용 VIP → 서버 B
```

GitHub는 읽기·쓰기용 VIP와 읽기 전용 VIP를 하나씩, 총 두 개 사용했으며, 애플리케이션은 주로 active 역할을 읽기와 쓰기 모두에 사용했다고 밝혔다.[1]

VIP는 데이터 복제 기능이 아니다. 주소를 새 서버로 옮겼다고 그 서버의 데이터가 최신이 되거나 캐시가 준비되는 것은 아니다. 이미 연결된 DB 세션이 자동으로 새 서버에 이어 붙는다고 보장하는 것도 아니다.

### 2.7. 두 구성의 차이

| 비교 | 이전 DRBD 기반 2노드 구성 | 새 3노드 MySQL 클러스터 |
| --- | --- | --- |
| 이 사건에서의 데이터 복제 축 | 저장 장치 계층의 DRBD 복제 | 실행 중인 MySQL 사이의 복제 |
| 전환 시 MySQL 상태 | 다른 서버의 MySQL Cold Start가 필요했다고 보고 | 모든 노드에서 MySQL이 실행 중이었다고 보고 |
| 전환의 주요 작업 | 복제된 저장 장치와 MySQL 서비스를 다른 서버에서 사용 | 복제·읽기 전용 설정·VIP 등 역할 전환 조정 |
| 여전히 확인할 것 | 저장 장치 상태와 DB 시작·준비 상태 | 데이터 최신성, 복제 상태, 캐시·트래픽 수용 준비 |

이 비교는 GitHub가 변경한 두 구성을 설명한다.[1]

**DRBD와 Pacemaker 자체가 경쟁 관계라는 뜻은 아니다.** DRBD는 저장 장치 복제 기술이고 Pacemaker는 자원 관리자이므로 함께 사용할 수도 있다. DRBD 공식 가이드에도 Pacemaker 연동을 다룬다.[5]

또한 이 글의 MySQL 클러스터는 세 서버를 묶은 당시 운영 구성을 뜻한다. 제품명이 비슷한 MySQL NDB Cluster나 현대의 MySQL InnoDB Cluster를 사용했다고 해석하지 않는다.

## 3. 사고 발생 타임라인

### 3.1. 8월 중순: 전환 시간을 줄이기 위한 구조 변경

운영팀은 DRBD 기반 서버 두 대를 Pacemaker·Heartbeat·PRM으로 관리하는 3노드 구성으로 교체했다. 목적은 고가용성이었고, 모든 노드에서 MySQL을 실행해 전환을 더 효율적으로 만드는 것이었다.[1]

### 3.2. 9월 10일: 부하를 장애로 판단한 자동 Failover

GitHub는 서비스 중 스키마를 바꾸기 위한 마이그레이션을 실행했다. 이번에는 이전보다 훨씬 높은 DB 부하가 발생해 Primary의 PRM Health Check가 실패했다.[1]

PRM은 Primary를 실패한 것으로 판단하고 active 역할을 다른 서버로 옮겼으며, 실패한 것으로 간주한 원래 노드의 MySQL을 중지했다.[1]

**Failover는 기존 담당 서버 대신 다른 서버가 그 역할을 맡는 것**이다. 이 사건에서는 쓰기를 받는 MySQL 역할이 다른 노드로 이동했다.

하지만 새 Primary의 InnoDB Buffer Pool이 차가운 상태여서 성능이 좋지 않았고, 실제 질의 부하를 받은 뒤 Health Check가 다시 실패했다. 결국 active 역할이 원래 서버로 돌아가는 Failback이 일어났다.[1]

운영팀은 반복 전환을 막으려고 Pacemaker의 `maintenance-mode`를 켰고, 이후 Buffer Pool이 준비되면서 성능이 점차 회복됐다.[1]

### 3.3. 9월 11일 아침: Standby의 잘못된 질의 결과

다음 날 개발자가 Standby 역할을 제공하는 노드에서 잘못된 질의 결과를 발견했다.[1]

조사 결과, 전날 유지보수 모드에 들어가면서 Standby가 새 복제 원본으로 전환하고 복제를 시작하는 데 필요한 관리 작업이 수행되지 않은 상태였다.[1]

운영팀은 Pacemaker와 PRM이 이 상태를 바로잡게 하려고 `maintenance-mode` 해제를 시도했다.[1]

### 3.4. 08:19 PDT: 클러스터 상태가 갈라지고 오래된 C가 승격

유지보수 모드를 해제하려는 과정에서 Pacemaker에 Segmentation Fault가 발생했고, 클러스터 상태가 분리됐다. A·B는 C의 메시지 대부분을 거부했고, C 역시 A·B의 메시지 대부분을 거부했다.[1]

조정되지 않은 리더 선출이 양쪽에서 시도됐다. A·B 측에서는 다른 쪽 메시지의 영향으로 선출이 중단되고 MySQL이 중지됐지만, 단독으로 남은 C는 08:19에 Primary로 선출됐다. C는 이미 데이터가 오래된 것으로 확인된 노드였다.[1]

### 3.5. 08:26 PDT: 오래된 C의 전원을 차단

운영팀은 데이터 불일치가 더 커지는 것을 막으려고 C의 전원을 껐다. 이 조치로 오래된 노드의 동작은 차단됐지만, 모든 프로덕션 DB 접근도 끊겨 GitHub.com 전체 접근이 중단됐다.[1]

### 3.6. 이후: 클러스터 관리 상태를 복구하고 A에서 서비스 재개

당초 시도한 유지보수 모드 해제는 클러스터 상태에 제대로 반영되지 않았고, 이후 설정 변경 시도도 성공하지 못했다.[1]

운영팀은 A·B에서 Pacemaker와 Heartbeat 프로세스를 모두 중지한 다음 A에서 다시 시작했다. A의 MySQL이 active 역할을 맡았고, Buffer Pool이 준비되면서 사이트 성능도 점차 회복됐다.[1]

## 4. 기술적 장애 원인을 단계별로 이해하기

### 4.1. Health Check 실패는 왜 노드 고장과 다를까?

Health Check는 정해진 검사에 서비스가 정상적으로 응답하는지 확인하는 것이다. 검사에 실패했다는 사실만으로 서버의 전원이 꺼졌거나 데이터가 망가졌다고 단정할 수는 없다.

이 사고의 첫 트리거는 높은 DB 부하였다. 부하 때문에 PRM의 검사에 실패했고, 그 결과 자동 Failover가 수행됐다.[1]

```text
스키마 변경으로 DB 부하 증가
    ↓
Health Check 실패
    ↓
관리 시스템이 Primary를 실패한 것으로 취급
    ↓
역할 전환 및 기존 MySQL 중지
```

단순히 트래픽을 다른 서버로 옮기면 해결될 것 같지만, 새 서버가 그 트래픽을 감당할 준비가 부족하면 상황이 더 나빠질 수 있다.

### 4.2. InnoDB Buffer Pool이 차갑다는 것은 무슨 뜻인가?

InnoDB Buffer Pool은 테이블과 인덱스의 데이터 페이지를 메모리에 보관하는 공간이다. 자주 쓰는 페이지가 여기에 있으면 저장 장치에서 다시 읽는 대신 메모리에서 접근할 수 있다.[4]

```text
필요한 페이지가 Buffer Pool에 있음
→ 메모리에서 읽음

필요한 페이지가 Buffer Pool에 없음
→ 저장 장치 쪽에서 읽어 Buffer Pool에 올림
→ 그 뒤 처리
```

Cold Buffer Pool은 메모리 용량이 작다는 뜻이 아니다. **새 역할의 질의를 처리하는 데 필요한 페이지들이 메모리에 충분히 준비되지 않았다는 뜻**이다. 모든 캐시가 완전히 비어 있어야만 Cold라고 부르는 것도 아니다.

새 Primary에 데이터가 저장돼 있어도, 애플리케이션이 자주 찾는 데이터와 인덱스가 캐시에 부족하면 처음 들어오는 질의들이 많은 페이지를 읽어 와야 한다.[4]

```text
새 Primary로 실제 서비스 트래픽 유입
    ↓
필요한 페이지의 Cache Miss 증가
    ↓
저장 장치 읽기와 질의 처리 부담 증가
    ↓
응답 성능 저하
    ↓
Health Check도 다시 실패
```

GitHub는 새 Primary의 Cold Buffer Pool과 그 위에 들어온 질의 부하가 성능 저하와 재전환을 일으켰다고 보고했다.[1]

Replica가 변경을 복제하는 과정에서 일부 페이지를 읽더라도, 그것이 실제 서비스의 읽기 패턴에 필요한 페이지 전체를 준비해 준다는 보장은 없다. **디스크 데이터 복제와 메모리 Cache Warming은 같은 작업이 아니다.**

따라서 Warm-up은 필요한 페이지를 미리 읽어 캐시에 준비하는 것이다. GitHub는 Replica의 Buffer Pool을 미리 준비하는 방법을 조사·테스트하겠다고 했지만, 이 보고서에서 특정 현대 MySQL 기능을 이미 사용했다고 밝히지는 않았다.[1]

### 4.3. maintenance-mode는 무엇을 멈췄나?

Pacemaker의 `maintenance-mode`는 클러스터의 자동 자원 관리를 잠시 멈추고 운영자가 작업할 수 있게 하는 모드다. PRM 운영 가이드는 감시를 멈추고 자원을 현재 상태로 두며, 자동 Failover도 수행하지 않는다고 설명한다.[3]

여기서 중요한 구분은 다음과 같다.

- 애플리케이션에 점검 화면을 띄우는 웹사이트 기능이 아니다.
- MySQL 프로세스와 모든 질의를 무조건 중지시키는 기능이 아니다.
- 모든 Replica의 기존 복제 스레드를 일괄 정지시키는 MySQL 명령도 아니다.
- Pacemaker가 관리하는 감시·자동 복구·역할 조정 등의 작업이 수행되지 않을 수 있다는 뜻이다.

이 사고에서는 반복 Failover를 막으려고 모드를 켰다. 그러나 **Standby가 새 Primary를 복제 원본으로 지정하고 복제를 시작해야 하는 작업도 실행되지 않았다.**[1]

원리를 설명하기 위한 재구성은 다음과 같다. 특정 시점의 실제 MySQL 명령 로그를 재현한 것은 아니다.

```text
Primary가 바뀜
    ↓
Replica는 새 Primary를 복제 원본으로 삼아야 함
    ↓
Pacemaker·PRM이 복제 설정을 바꿔야 함
    ↓
maintenance-mode라 필요한 관리 작업이 실행되지 않음
    ↓
해당 Replica가 새 변경을 정상적으로 따라오지 못함
```

그래서 "유지보수 모드가 복제를 전부 껐다"보다, **"복제를 올바르게 다시 연결하는 데 필요한 관리 작업이 막혔다"**가 이 사고를 더 정확히 설명한다.

### 4.4. Pacemaker Segfault와 Cluster State Partition

Segmentation Fault는 프로세스가 허용되지 않은 메모리에 접근하는 등의 문제로 비정상 종료될 때 나타나는 오류다. 이 사건에서는 Pacemaker의 Segfault 뒤에 클러스터 상태가 갈라졌다고 보고됐다.[1]

공식 보고서는 다음처럼 메시지가 거부됐다고 설명한다.[1]

```text
A ↔ B
│   │
└───┴── C와의 클러스터 메시지 대부분이 상호 거부됨

C의 서버 자체는 살아 있었음
C는 이후 Primary로 동작함
```

이것은 C의 전원이 꺼져서 응답이 없는 상황과 다르다. C는 살아 있었지만 A·B와 일관된 클러스터 상태를 공유하지 못했다. 공식 보고서만으로 물리 네트워크 케이블이 끊어졌다고 단정할 수도 없다. 보고된 것은 클러스터 상태 분리와 제어 메시지 거부다.[1]

#### Quorum을 설정했는데 왜 문제가 생겼나?

Quorum은 클러스터가 의사결정에 필요한 동의를 확보했는지 판단하는 기준이다. 과반수 기준의 세 노드 구성이면 두 노드 이상의 동의가 필요하다는 식으로 생각할 수 있다.

GitHub는 과반수 합의를 요구하도록 설정했음에도, 상태 분리 뒤 조정되지 않은 선출이 동시에 시도됐다고 보고했다.[1]

```text
A·B 측
선출 시도 → 다른 쪽 메시지로 중단 → MySQL 중지

C 측
단독 선출 → 오래된 C가 Primary로 동작
```

따라서 이 사고를 "두 Primary가 7분 동안 계속 동시에 쓰기를 받았다"고 단순화하면 부정확하다. 공식 보고서는 A·B 측 MySQL이 중지됐고, 오래된 C가 Primary로 동작했다고 설명한다.[1]

또한 "과반수 정책이면 단독 C가 정상적으로 승격될 수 있다"는 뜻도 아니다. 기대한 정책이 사고 과정에서 제대로 지켜지지 않았다는 것이 문제다. Segfault의 정확한 구현 결함과 모든 메시지 처리 경로는 당시 보고서에서 확정적으로 공개되지 않았다.[1]

### 4.5. MySQL과 Redis의 ID 참조는 왜 어긋났나?

GitHub는 MySQL이 자동 생성한 ID를 Redis의 대시보드 이벤트와 저장소 라우팅 정보 조회에도 사용했다고 밝혔다. 이 때문에 MySQL의 ID와 Redis의 참조가 같은 대상을 뜻해야 했다.[1]

```text
MySQL에서 얻은 ID
    ↓
그 ID로 Redis의 이벤트·저장소 경로 조회
    ↓
해당 데이터 제공
```

두 저장소에 걸친 이런 관계는 MySQL 내부 Foreign Key만으로 자동 보호되지 않는다. MySQL이 다른 시점의 상태로 바뀌고 Redis는 그대로 남으면, 각각의 저장소가 동작하더라도 서로의 의미가 어긋날 수 있다.

제공된 DDIA 5장 설명은 이 사고를 **오래된 복제본이 이전 Primary에서 이미 사용한 자동 증가 ID를 다시 할당한 사례**로 해석한다. 다음 표는 그 메커니즘을 이해하기 위한 가상 예시이며 실제 레코드나 키 값이 아니다.

| 시점 | MySQL | Redis |
| --- | --- | --- |
| 기존 Primary가 새 저장소 B를 기록 | ID 101 → 저장소 B | ID 101 → 저장소 B의 라우팅 |
| 오래된 Replica가 Primary로 승격 | 저장소 B에 해당하는 ID 101 기록이 없음 | 기존 라우팅 정보가 남아 있음 |
| 새 Primary가 저장소 C를 기록 | ID 101 → 저장소 C | 참조가 올바르게 재조정되지 않으면 B의 정보와 충돌 |

새 Primary의 로컬 DB에서는 ID 101이 비어 있으므로 해당 ID를 새 레코드에 쓸 수 있다. 그러나 시스템 전체에서는 이미 사용된 ID이므로 Redis 등 외부 참조와 충돌할 수 있다.

이 예시는 **"오래된 MySQL 상태로 되돌아간 것에 Redis가 함께 되돌아가지 않았다"**는 문제를 보여 준다. 실제 Redis 키 구조, SQL 실행 내역, ID 값, 갱신 순서를 복원한 것은 아니다.

GitHub 공식 보고서는 자동 생성 ID를 통한 Cross-data-store 참조가 어긋났다는 사실과 잘못된 라우팅의 영향을 확인해 준다. 자동 증가 ID 재사용의 구체적인 SQL·카운터 내역까지 공개한 것은 아니므로, 공식 확인 사실과 DDIA의 설명·가상 예시를 구분한다.[1]

## 6. GitHub는 어떻게 대응했나?

### 6.1. 실제 사고 당시 수행한 조치

| 수행한 조치 | 목적·효과 |
| --- | --- |
| 오래된 C의 전원 차단 | C의 동작과 추가 데이터 불일치 확대 차단 |
| A·B에서 Pacemaker·Heartbeat 중지 후 A에서 재시작 | 비정상 클러스터 관리 상태를 정리하고 복구 |
| A의 MySQL을 active 역할로 시작 | 정상적인 DB 서비스 재개 |
| 잘못 노출된 이벤트 제거 | 대시보드 정보 노출 후속 조치 |
| 잘못 라우팅된 저장소 감사 | 영향받은 대상 확인 |
| 비공개 저장소 소유자에게 직접 통지 | 보안 사고 대응 |

이 조치들은 공식 보고서에서 실제 수행했다고 밝힌 내용이다.[1]

C의 전원을 끈 것은 단순한 성능 개선이 아니라 잘못된 노드의 동작을 확실히 중단하기 위한 조치였다. 하지만 안전한 노드로 서비스가 바로 이어지는 상태가 아니었으므로 전체 DB 접근 중단을 감수해야 했다.[1]

### 6.2. 실제 변경했다고 발표한 정책

GitHub는 Pacemaker 설정을 바꿔 **운영팀 구성원이 직접 시작할 때만 active DB 역할의 Failover가 발생하도록 했다.** 자동으로 감지한 전환을 사람이 나중에 승인하는 흐름이라고 단정하기보다, Failover의 시작 자체를 운영팀에 맡겼다는 표현이 정확하다.[1]

이는 당시 GitHub의 주 프로덕션 DB에 대한 결정이다. GitHub도 자동 Failover가 좋은 전략인 상황이 많다고 명시했다. 모든 시스템에서 수동 Failover가 더 안전하다는 일반 법칙을 선언한 것은 아니다.[1]

### 6.3. 당시 조사·테스트 중이라고 밝힌 후속 조치

| 후속 조치 | 공식 보고서 당시의 상태 |
| --- | --- |
| Replica의 InnoDB Buffer Pool Warm-up 방법 | 조사·테스트 중 |
| Pacemaker·Heartbeat 스택과 Segfault 발생 경로 | 감사 진행 중 |
| Segfault가 발생한 서버의 하드웨어 | 추가 테스트 진행 중 |

위 항목들은 이미 완료됐다고 발표한 조치와 구분해야 한다.[1]

### 6.4. 2016년: `orchestrator`는 언제 Primary를 교체할까?

아래 두 사례는 **이후 GitHub가 공개한 운영 구조**다. 6.3의 캐시 워밍업, Segfault 감사, 하드웨어 테스트 결과를 보고한 글은 아니다. 두 구성 모두 한 MySQL 클러스터에서 쓰기를 맡는 Primary는 한 대였다.[7][8]

`orchestrator`는 Outbrain에서 시작해 GitHub가 도입한 **오픈소스 MySQL 복제 관리 프로그램**이다. MySQL과 별도로 실행되며, 누가 누구를 복제하는지 관찰하고, 장애를 판단하고, 필요하면 Replica를 새 Primary로 승격한다. 애플리케이션의 SQL 트래픽을 전달하는 프록시는 아니다.[7]

예를 들어 A가 Primary이고 B·C가 Replica라고 하자. B·C는 A에 연결해 새로운 변경 기록(binlog)을 받아온다. `orchestrator`도 각 서버에 별도로 접속해 상태를 확인한다. 이 절과 다음 절의 A·B·C는 설명용이며, 2012년 사고의 실제 노드를 가리키지 않는다.[7]

```text
상황 1: 관리 프로그램만 A에 접속하지 못함
orchestrator ── 접속 실패 ──────→ A
B·C          ── 복제 연결 정상 ─→ A

상황 2: 관리 프로그램과 Replica 모두 A에 접속하지 못함
orchestrator ── 접속 실패 ──────→ A
B·C          ── 복제 연결 실패 ─→ A
```

- **상황 1 — A를 바로 교체하지 않는다.** `orchestrator`는 A에 접속하지 못했지만, B·C의 상태를 확인해 둘 다 A에서 새 변경을 계속 받아 복제가 진행 중임을 알 수 있다. `orchestrator`에서 A로 가는 경로에만 문제가 있을 수도 있다. A가 모든 앱에 정상이라는 뜻은 아니지만, 관리 프로그램 한 곳의 타임아웃만으로는 승격할 근거가 부족하다.[7]
- **상황 2 — 전환을 판단할 근거가 생긴다.** `orchestrator`는 B·C의 상태를 확인할 수 있고, 양쪽 모두 A와의 복제 연결이 끊어졌다고 보고한다. 쓰기가 없어서 binlog가 조용한 게 아니라, 새 변경이 생겨도 이를 받아올 연결 자체가 없다는 뜻이다. A가 실제로 꺼졌는지, 살아 있지만 네트워크에서 고립됐는지는 몰라도 현재 복제 경로가 작동하지 않는다는 건 알 수 있다. 반대로 B·C의 상태도 확인할 수 없어 판단이 애매한 경우에는 알림만 보내고 자동 복구를 하지 않을 수도 있다.[7]

**전환할지**와 **누구를 올릴지**는 별도 판단이다. 2016년 글이 설명한 비동기 복제 구성에서는 A의 최신 쓰기가 어느 Replica에도 도착하지 않았을 수 있다. `orchestrator`는 복제 진행 상태, 설정 호환성, 데이터센터 위치 등을 보고 승격 후보를 고른다. 또 한 번 자동 전환이 일어난 클러스터에서 역할이 연달아 바뀌는 일을 줄이기 위해, 일정 시간 또는 운영자의 확인 전까지 추가 자동 전환을 제한했다.[7]

### 6.5. 2018년: 새 Primary로 앱의 연결을 어떻게 바꿀까?

**B가 쓰기 가능해지는 것과 앱의 연결이 B로 향하는 것은 별개다.** 앱이 여전히 A에 붙는다면, B의 승격이 끝났어도 앱의 쓰기는 B에 도달하지 않는다. 2018년 글은 `orchestrator`로 승격을 처리하는 것은 유지하면서, 앱이 현재 Primary에 연결되는 방식을 어떻게 바꿨는지 설명한다.[8]

#### 이전: VIP를 넘기거나 DNS를 바꿨다

```text
평소:               앱 → writer 이름 → VIP → A
같은 VIP 이동 가능: 앱 → writer 이름 → 같은 VIP → B
같은 VIP 이동 불가: 앱 → writer 이름 → B 쪽 IP (DNS 변경)
```

**VIP(Virtual IP)**는 앱이 접속하는 서비스용 IP다. 같은 VIP를 옮길 수 있는 경우, 옛 Primary A가 자기 네트워크 설정에서 해당 IP를 빼고 새 Primary B가 가져간다. 여기서 **`orchestrator`가 A에 연락할 수 없다는 것과 A가 VIP를 더 이상 쓰지 않는다는 것은 다르다.** 예를 들어 관리 프로그램이 A에 보내는 해제 요청은 닿지 않지만, 앱에서 A로 가는 연결은 살아 있을 수 있다. 이때 A가 VIP를 여전히 가지고 있는데 B도 같은 VIP를 가져가면 두 서버가 같은 주소를 사용하게 된다.[8]

같은 네트워크 구간에서 두 서버가 같은 IPv4 주소를 사용하면, 장비가 ARP로 그 IP의 실제 네트워크 주소(MAC)를 알아낼 때 서로 다른 서버를 가리킬 수 있다. 그러면 같은 VIP로 접속하는 앱 중 일부는 A로, 일부는 B로 연결될 수 있다. 같은 요청을 두 서버에 전달한다는 뜻은 아니다.[8][9]

```text
가상 예시: A가 VIP를 반납하지 않았는데 B도 가져감

앱 서버 1 ── 같은 VIP로 접속 ──→ A (기존 Primary)
앱 서버 2 ── 같은 VIP로 접속 ──→ B (새 Primary)
```

A가 쓰기를 막은 상태라면 A에 도착한 쓰기가 실패할 수 있다. 반대로 A와 B 모두 독립적으로 쓰기를 받으면, 같은 클러스터에 쓴다고 생각한 두 앱의 변경이 서로 다른 DB에 쌓일 수 있다. **VIP 충돌은 접속 경로 문제이고, 두 DB가 모두 쓰기를 받는다면 데이터가 갈라지는 Split-Brain 문제로 이어진다.** 이 도식은 이전 방식의 위험을 보인 예시이지, 2012년 장애에서 두 Primary에 동시에 쓰였다는 뜻이 아니다.[8][9]

**다른 데이터센터로 전환할 때는 주소를 옮길 수 있는지부터 문제였다.** GitHub의 이전 구성에서는 일부 VIP가 해당 위치의 스위치나 라우터에 묶여 있었다. 이 경우 A가 VIP를 잘 반납했더라도 다른 데이터센터의 B에 같은 주소를 붙일 수 없었다. 그래서 `writer` 이름이 B 쪽 IP를 가리키도록 DNS 응답을 바꿨다. 그러나 앱이나 DNS 리졸버가 이전 답(`writer → A 쪽 IP`)을 캐시하고 있으면, 새로 연결을 열더라도 캐시가 갱신되기 전까지 A 쪽 IP로 갈 수 있다. 이미 열린 DB 연결도 DNS 변경만으로 B에 옮겨가지 않는다.[8]

#### 이후: 앱이 쓰는 주소는 그대로 두고, 프록시의 목적지를 바꿨다

```text
앱의 연결 경로
평소: 앱 → 같은 writer 주소 → GLB/HAProxy → A
전환: 앱 → 같은 writer 주소 → GLB/HAProxy → B

전환 정보의 전달 경로
orchestrator 리더가 B를 승격
  → Raft로 다른 orchestrator에 변경 공유
  → 각 데이터센터의 Consul에 현재 Primary = B 기록
  → consul-template이 감지해 HAProxy 설정 갱신
```

| 구성 요소 | 이 구조에서 맡은 일 |
| --- | --- |
| `orchestrator` | 장애를 판단하고 쓰기를 맡을 MySQL Replica를 고른 뒤 승격한다. |
| Raft | 여러 `orchestrator` 인스턴스가 과반수의 지지를 받아 관리 리더를 뽑고, 변경 결정을 공유하는 합의 방식이다. |
| Consul | GitHub는 Consul의 Key-Value 저장소에 클러스터의 현재 Primary 주소와 포트를 기록했다. Consul은 Primary를 직접 고르거나 SQL을 전달하지 않는다. |
| GLB / HAProxy | 앱의 DB 연결을 받아 현재 Primary 한 대에 전달한다. GLB는 GitHub의 로드밸런서이며, `consul-template`이 Consul의 변경을 읽어 HAProxy의 목적지 설정을 갱신한다. |

**MySQL에만 HA(고가용성)를 붙인 게 아니라, 전환을 실행하는 `orchestrator` 자체도 여러 인스턴스로 운영했다.** Raft로 뽑는 것은 **MySQL Primary가 아니라 전환을 실행할 `orchestrator` 리더**다. 이 리더가 B를 승격하면 Raft로 변경 소식이 공유되고, 각 지역의 `orchestrator`가 자기 지역 Consul에 기록한다. 이때 데이터센터마다 Consul은 독립적이어서 Consul끼리 직접 복제하는 구조가 아니었다.[8]

앱의 `writer` 이름은 **고정된 Anycast IP**를 가리켰다. 같은 IP를 써도 앱은 자기 데이터센터의 프록시로 연결되고, 프록시가 뒤에서 해당 클러스터의 실제 Primary로 보낸다. Failover 때 DB끼리 VIP를 넘기거나 앱이 새 DNS 응답을 받을 때까지 기다릴 필요가 없다. GitHub는 대부분의 전환에서 전체 중단 시간이 **10~13초**였다고 보고했다.[8]

다만 **프록시의 목적지를 B로 바꾸는 것과 기존 A의 쓰기를 확실히 막는 것은 별개**다. GitHub는 데이터센터 전체가 다른 센터와 단절됐을 때, 그 안의 앱이 같은 센터에 있는 기존 Primary에 계속 쓸 가능성이 남았다고 밝혔다. 따라서 이 사례는 Split-Brain을 완전히 없앴거나 Active-Active를 의도적으로 도입한 사례가 아니다.[8]

## 7. 근본 원인과 설계적 교훈

### 7.1. 세 계층에서 문제가 이어졌다

| 계층 | 이 사고에서 확인한 문제 | 이해할 점 |
| --- | --- | --- |
| 장애 감지 | 높은 부하로 PRM Health Check 실패 | 검사 실패가 곧 서버의 물리적 고장은 아님 |
| 역할 전환·복구 | Cold Buffer Pool, 누락된 복제 재설정, 잘못된 선출 | 새 담당자가 실행 중인 것과 준비된 것은 다름 |
| 데이터 정합성 | MySQL과 Redis의 ID 기반 참조 불일치 | 한 DB의 Failover가 다른 저장소의 의미에도 영향을 줌 |

GitHub 보고서는 불필요한 Failover, 상태 분리 뒤 클러스터 소프트웨어의 잘못된 동작, 전환이 예상보다 크게 성능·가용성을 해친 점을 주요 사건으로 정리한다.[1]

### 7.2. 일반적인 설계 개선안

다음 내용은 사고에서 도출한 일반적인 검토 항목이다. GitHub가 2012년에 모두 적용했다고 확인된 조치는 아니다.

**승격 후보의 데이터와 복제 상태 확인.** 프로세스가 살아 있는지만 보지 않고, 필요한 변경을 어디까지 받아 적용했는지 확인해야 한다. 복제 원본이 올바른지와 복제가 실제로 진행되는지도 점검 대상이다.

**승격 후보의 성능 준비 확인.** 데이터가 최신이어도 Cache Miss와 저장 장치 읽기가 급증하면 실제 트래픽을 감당하지 못할 수 있다. 캐시 준비와 부하 수용 여부를 별도로 검토한다.

**Health Check와 자동 전환 정책 검토.** 일시적 과부하와 복구 불가능한 장애를 같은 방식으로 다루면 전환을 반복할 수 있다. 검사 기준, 관찰 시간, 전환 조건, 재전환 조건을 함께 설계한다.

**Fencing.** 문제가 있는 노드가 더 이상 서비스를 수행하지 못하도록 확실히 차단하는 것이다. 전원 차단이나 서비스 수행에 필요한 접근 차단 등이 사용될 수 있다.[6]

기존 Primary를 멈췄는지 확신하지 못한 채 새 Primary를 허용하면 중복 쓰기 위험이 생길 수 있다. 이 사고의 수동 C 전원 차단은 잘못된 노드의 동작을 멈추는 행동이었지만, 이를 근거로 GitHub의 자동 Fencing 설정 전체를 추정하지 않는다.

**ID 재사용 위험 완화.** 전역적으로 충돌 위험이 낮은 ID 체계 등을 검토할 수 있다. 그러나 UUID·ULID를 사용한다고 오래된 Replica의 누락 데이터나 외부 참조 정합성까지 자동으로 복구되는 것은 아니다.

**외부 저장소까지 포함한 복구 절차.** Redis 데이터의 역할에 따라 무효화·재구축·참조 검증·쓰기 일시 중단 등을 검토한다. 모든 Redis 데이터가 재생성 가능한 캐시라고 가정하고 일괄 삭제하는 식의 처방은 피한다.

## 8. 최종 결론

이 사고는 단순히 "MySQL 서버가 고장 나서 다른 서버로 바꿨다"는 사례가 아니다. 부하로 시작한 검사 실패가 반복 전환으로 이어졌고, 자동 관리를 멈추는 동안 복구에 필요한 작업이 누락됐으며, 관리 소프트웨어 오류로 오래된 DB가 쓰기를 받게 됐다.[1]

그 DB가 응답한다고 해서 서비스가 올바르게 복구된 것은 아니었다. MySQL의 ID를 사용하던 Redis와의 참조가 어긋나면서 가용성 문제는 데이터 정합성과 비공개 저장소 노출 문제로 확대됐다.[1]

> Failover의 성공은 새 Primary가 쓰기를 받을 수 있다는 것만으로 판단할 수 없다. 기존에 성공한 쓰기가 보존됐는지, 승격 후보가 필요한 데이터를 갖고 있는지, 실제 트래픽을 감당할 준비가 됐는지, 외부 시스템의 참조가 여전히 같은 대상을 뜻하는지까지 확인해야 한다.

스터디에서는 다음 질문으로 토론을 이어갈 수 있다.

- 어떤 실패는 자동으로 전환하고, 어떤 실패는 사람이 판단하도록 남겨야 할까?
- MySQL이 복구됐다는 확인에 Redis와의 참조 검증도 포함돼 있는가?
- Replica의 데이터 최신성과 서비스 준비 상태를 각각 어떻게 검증할까?
- 유지보수 모드를 켤 때 함께 멈추는 관리 작업과 해제 후 확인할 작업을 알고 있는가?

## 자료의 범위

GitHub 사고 사실과 대응 상태는 현재 공개된 공식 보고서를 기준으로 확인했다. 페이지 표시 발행일은 2012년 9월 14일이며, 업데이트 표시는 2019년 12월 6일이다.[1]

PRM 설치 가이드는 2012년 6월 자료이고 운영 가이드는 2013년 5월 자료다. 운영 가이드는 maintenance-mode의 일반 동작을 보충하는 데 사용했으며, GitHub의 정확한 설치 버전이나 모든 설정을 증명하는 자료로 사용하지 않았다.[2][3]

현재의 Pacemaker·MySQL 문서는 Resource Manager, Fencing, Buffer Pool 같은 개념을 설명하기 위한 자료다. 현재 기능이 2012년 GitHub에도 있었다고 소급하지 않는다.[6][4]

자동 증가 ID 재사용 설명은 제공된 DDIA 5장 정리를 바탕으로 풀었으며, 이번 글에서 해당 책의 쪽수를 독립적으로 다시 대조하지는 않았다. 실제 ID 값과 시스템 내부 명령을 추정한 예시는 사실 기록과 구분했다.
