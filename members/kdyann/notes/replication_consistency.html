OVERVIEW

복제본이 여러 개라면, 읽기 결과도 항상 같을까?

분산 데이터베이스는 읽기 처리량을 높이고 장애에 대응하기 위해 데이터를 여러 노드에 복제한다. 쓰기는 리더(Leader)가 먼저 처리하고 팔로워(Follower)는 변경 로그를 비동기적으로 적용하는 구성이 흔하다.

비동기 복제에서는 리더의 쓰기가 팔로워에 도착하기까지 시간이 걸린다. 이 시간 차이를 복제 지연(Replication Lag)이라고 한다. 대부분의 경우 지연은 짧지만, 네트워크 문제나 노드 과부하·장애 복구가 겹치면 수 초에서 수 분까지 늘어날 수 있다.

핵심 질문
모든 복제본이 아직 같은 상태가 아닐 때, 사용자가 읽는 데이터가 시간의 흐름이나 사건의 인과관계에 어긋나지 않게 하려면 어떤 보장이 필요할까?
01 · BACKGROUND

최종적 일관성 (Eventual Consistency)

최종적 일관성은 새로운 쓰기가 더 이상 발생하지 않는다면, 시간이 충분히 흐른 뒤 모든 복제본이 같은 값으로 수렴한다는 보장이다. 중요한 점은 수렴하기 전까지 모든 읽기가 같은 값을 반환한다는 뜻은 아니라는 것이다.

이런 시스템은 쓰기 응답을 모든 복제본이 끝날 때까지 기다리지 않아도 되므로 지연 시간과 가용성 측면에서 유리할 수 있다. 대신 애플리케이션이 오래된 데이터를 읽었을 때 어떤 경험을 제공할지 고려해야 한다.

최종적 일관성은 사용자 경험의 일관성을 자동으로 보장하지 않는다.
복제본이 언젠가 수렴하더라도, 그 전에 사용자가 자신의 글이 사라졌다고 느끼거나 화면이 과거로 돌아가거나 대화 순서가 뒤집혀 보일 수 있다.
02 · CASE 1

자신이 쓴 내용 읽기 (Read-your-writes)

사용자가 댓글이나 프로필을 수정하면 쓰기 요청은 리더로 전달된다. 그런데 수정 직후 화면을 다시 불러올 때 팔로워에서 읽으면, 아직 변경 사항을 복제하지 못해 방금 작성한 내용이 보이지 않을 수 있다.

사용자 입장에서는 저장에 성공했다는 응답을 받았는데도 자신의 변경 사항이 사라진 것처럼 보인다. Read-your-writes는 사용자가 성공적으로 완료한 자신의 쓰기를 이후 읽기에서 볼 수 있어야 한다는 보장이다. 다른 사용자의 최신 변경까지 즉시 보여준다는 뜻은 아니다.

문제 상황 · 시퀀스 다이어그램

해결 방법: 마지막 쓰기 이후의 버전을 확인하고 읽기 경로를 선택한다

가장 단순한 방법은 쓰기 직후에는 리더에서 읽는 것이다. 팔로워를 계속 사용하고 싶다면 클라이언트가 마지막 쓰기의 시각이나 버전(예: 로그 위치)을 기억하고, 읽기를 처리할 팔로워가 그 지점까지 복제했는지 확인할 수 있다.

해결 과정 · 시퀀스 다이어그램
  1. 쓰기: 클라이언트가 리더에 데이터를 쓰고 성공 응답과 함께 버전 또는 로그 위치를 받는다.
  2. 기억: 클라이언트나 세션 계층이 마지막으로 성공한 쓰기의 버전을 보관한다.
  3. 읽기: 다음 읽기 요청에 최소 요구 버전을 포함한다.
  4. 판단: 팔로워가 요구 버전까지 반영했다면 팔로워에서 읽고, 아니라면 리더로 보내거나 팔로워가 따라잡을 때까지 기다린다.
핵심: 읽기 요청이 “최신 데이터를 줘”라고 막연히 요구하는 것이 아니라, “내가 성공한 쓰기 버전 42는 반드시 포함해 줘”라고 최소 조건을 전달한다.

대안으로는 마지막 쓰기 이후 일정 시간 동안 리더에서 읽거나, 클라이언트가 마지막 쓰기의 시각·버전을 기억해 그 지점까지 복제한 팔로워를 선택하는 방법도 있다.

03 · CASE 2

단조 읽기 (Monotonic Reads)

단조 읽기는 한 사용자가 여러 번 읽을 때, 이미 관찰한 데이터보다 더 과거의 상태를 나중에 관찰하지 않도록 하는 보장이다. 최신 상태를 항상 읽어야 하는 것은 아니다. 다만 시간이 거꾸로 흐르는 것처럼 보이면 안 된다.

예를 들어 사용자가 새 댓글을 확인했는데, 새로고침한 다음에는 그 댓글이 사라진다면 이상하게 느낄 것이다. 첫 번째 요청은 복제가 빠른 팔로워에서, 두 번째 요청은 복제가 느린 팔로워에서 처리되면 이런 일이 발생할 수 있다.

문제 상황 · 시퀀스 다이어그램

해결 방법: 사용자별 읽기 경로를 고정한다

DDIA에서 제시하는 간단한 방법은 사용자마다 읽기를 항상 같은 복제본으로 보내는 것이다. 예를 들어 사용자 ID를 해시해 복제본을 선택하면, 같은 사용자의 연속된 요청이 서로 다른 복제본을 무작위로 오가는 일을 줄일 수 있다.

해결 과정 · 시퀀스 다이어그램
  1. 사용자가 처음 요청하면 라우터가 사용자 ID 등을 기준으로 읽기 복제본을 선택한다.
  2. 이후 같은 사용자의 읽기 요청은 동일한 복제본으로 보낸다.
  3. 해당 복제본이 점점 최신 데이터를 적용하므로, 같은 사용자가 이전보다 오래된 상태로 돌아갈 가능성을 막는다.
주의할 점: 고정된 복제본이 장애를 일으키면 다른 복제본으로 재배치해야 한다. 이때 새 복제본이 사용자가 이전에 관찰한 버전보다 뒤처져 있지 않은지 확인해야 한다. 단순히 다른 복제본으로 바꾸면 단조 읽기가 깨질 수 있다.
04 · CASE 3

일관된 순서로 읽기 (Consistent Prefix Reads)

일관된 순서로 읽기는 인과관계가 있는 쓰기들이 있다면, 읽는 사람도 그 쓰기들을 같은 순서로 관찰해야 한다는 보장이다. 특히 서로 다른 파티션이 독립적으로 복제되고 복제 지연이 서로 다를 때 문제가 생긴다.

대화 상황을 생각해 보자. A가 질문을 보내고 B가 그 질문에 답했다. 그런데 질문이 저장된 파티션은 복제가 느리고, 답변이 저장된 파티션은 복제가 빠르다면 제3자는 질문보다 답변을 먼저 볼 수 있다. 원인보다 결과가 먼저 보이는 셈이다.

문제 상황 · 시퀀스 다이어그램

해결 방법 A: 인과관계가 있는 쓰기를 같은 파티션에 배치한다

DDIA가 설명하는 한 가지 방법은 서로 인과적으로 관련된 쓰기를 같은 파티션에 저장하는 것이다. 예를 들어 채팅 메시지를 사용자별이 아니라 대화방 ID를 파티션 키로 삼아 저장하면, 같은 대화방의 질문과 답변이 동일한 파티션의 순서에 따라 복제될 수 있다.

해결 과정 · 시퀀스 다이어그램

해결 방법 B: 인과관계 메타데이터를 추적한다

같은 파티션에 배치하기 어렵다면, 답변이 어떤 질문에 의존하는지 인과관계 정보를 함께 기록할 수 있다. 읽기 측에서는 답변을 보여주기 전에 그 답변의 선행 사건이 모두 반영됐는지 확인한다. 예를 들어 답변 A가 질문 Q에 의존한다면, Q가 아직 도착하지 않은 복제본에서는 A를 노출하지 않고 기다리거나 다른 복제본에서 읽는다.

핵심: 단순히 각 파티션에서 최신 데이터를 읽는 것이 아니라, 서로 의존하는 데이터가 사용자에게도 인과관계가 성립하는 순서로 보이도록 해야 한다.
05 · REAL-WORLD CASE

실제 사례: Meta의 FlightTracker

앞서 살펴본 세 가지 문제 중 자신이 쓴 내용 읽기(Read-your-writes)와 직접 연결되는 실제 사례가 Meta(Facebook)의 FlightTracker다.

Facebook의 소셜 그래프 저장소 TAO는 읽기 효율성과 가용성을 위해 여러 계층의 캐시와 지리적으로 분산된 데이터베이스 복제본을 비동기적으로 연결했다. TAO는 원래 Write-through caching으로 Read-your-writes를 제공했지만, 서비스와 데이터센터 규모가 커지면서 이 방식이 고정된 캐시 경로와 트래픽 라우팅에 의존한다는 한계가 드러났다.

문제의 핵심
사용자가 쓰기를 완료한 뒤 다음 요청이 다른 웹 서버 클러스터나 다른 캐시 경로로 라우팅되면, 새 쓰기가 반영되지 않은 캐시를 읽을 수 있었다. 기존 방식은 사용자를 특정 L1 캐시 클러스터에 고정하는 등 제한적인 통신 경로에 의존했다.

FlightTracker의 핵심: Ticket

FlightTracker는 사용자의 최근 쓰기 정보를 Ticket이라는 메타데이터로 관리한다. Ticket은 “이 사용자의 이후 읽기에서 반드시 보여야 하는 쓰기”의 하한을 나타낸다. 특정 복제본이 모든 쓰기를 최신으로 따라잡았는지를 요구하는 대신, 현재 사용자의 쓰기만큼은 읽기 결과에 포함되도록 한다.

Ticket 기반 읽기 처리 · 시퀀스 다이어그램
  1. 요청 시작: 웹 요청이 사용자를 식별하면 FlightTracker에서 getMergedWrites(user)를 호출해 해당 사용자의 Ticket을 가져온다.
  2. 쓰기: 데이터 저장소에 쓰기를 수행하고, 새 쓰기를 식별하는 메타데이터를 얻는다.
  3. Ticket 누적: 클라이언트 라이브러리가 새 메타데이터를 Ticket에 합치고 appendWrite(user, ticket)로 FlightTracker에 기록한다. 논문은 데이터 저장소 쓰기와 appendWrite가 모두 성공한 뒤 애플리케이션에 쓰기 완료를 알린다고 설명한다.
  4. 후속 읽기: 이후 소셜 그래프 읽기 요청에 Ticket을 자동으로 붙인다.
  5. 신선도 확인: 캐시는 로컬 데이터 버전과 Ticket을 비교한다. Ticket이 요구하는 쓰기를 포함하지 못하면 그 캐시 결과를 그대로 반환하지 않고 상위 저장소에서 최신 데이터를 가져와 보완한다. 이를 논문에서는 consistency miss라고 부른다.

기존 Write-through 방식

특정 캐시 경로와 사용자 라우팅을 유지해야 RYW가 성립했다. 경로가 바뀌거나 다른 저장소를 읽으면 보장이 깨질 수 있었다.

FlightTracker 방식

사용자의 최근 쓰기를 Ticket으로 전달한다. 읽는 저장소가 Ticket을 검사하므로 캐시·인덱스·데이터베이스를 넘나드는 읽기에도 일관성 조건을 적용할 수 있다.

왜 모든 복제본을 동기식으로 만들지 않았을까?

모든 읽기가 모든 최신 쓰기를 기다리게 하면 읽기 지연과 가용성 비용이 커질 수 있다. Facebook의 목표는 비동기 복제의 읽기 효율성과 가용성을 유지하면서, 사용자가 직접 수행한 쓰기만 후속 읽기에 보이도록 하는 것이었다. FlightTracker는 전체 시스템을 강한 일관성으로 바꾸기보다, 읽기 요청에 Ticket을 붙여 필요한 쓰기만 확인한다.

DDIA 사례와 연결
DDIA의 Read-your-writes 문제에서 핵심은 “내가 쓴 변경 사항이 복제본에 도착하기 전에 다시 읽으면 보이지 않을 수 있다”는 점이었다. FlightTracker는 이 문제를 사용자별 쓰기 메타데이터(Ticket)와 읽기 시점의 신선도 검사로 해결한 실제 대규모 시스템 사례다.
06 · TAKEAWAYS

세 가지 보장은 무엇이 다른가?

보장막으려는 현상대표적인 구현 아이디어
Read-your-writes내가 쓴 내용이 직후 읽기에서 보이지 않음리더 읽기, 마지막 쓰기 버전/토큰 전달, 복제본 적용 여부 확인
Monotonic Reads최신 데이터를 본 뒤 더 오래된 데이터를 보게 됨사용자별 동일 복제본 라우팅, 이전 관찰 버전보다 뒤처지지 않는 복제본 선택
Consistent Prefix Reads인과관계상 원인보다 결과가 먼저 보임인과적으로 관련된 쓰기를 같은 파티션에 배치, 인과 의존성 추적

세 보장은 모두 최종적 일관성 시스템에서 사용자 경험을 개선하지만, 해결하려는 이상 현상은 서로 다르다. 따라서 서비스의 요구사항에 맞춰 필요한 보장을 선택해야 한다. 이들 보장이 모든 사용자의 모든 읽기를 최신 상태로 만드는 선형화 가능성(Linearizability)과 동일한 것은 아니다.
