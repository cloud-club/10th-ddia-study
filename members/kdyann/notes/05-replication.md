# 05. 복제

### 1. 데이터를 굳이 여러 곳에 두는 이유

복제에는 크게 세 가지 목적이 있다.

- 사용자와 가까운 곳에서 데이터를 읽어 응답 시간을 줄인다.
- 일부 서버가 고장 나도 다른 서버로 서비스를 이어간다.
- 읽기 요청을 여러 서버에 나눠 처리한다.

복제와 파티셔닝은 구분해야 한다.
복제는 같은 데이터를 여러 곳에 두는 것 파티셔닝은 데이터를 나눠 서로 다른 곳에 둔다.

복제본을 늘린다고 쓰기 성능까지 자연스럽게 늘어나는 것은 아니다.
단일 리더 구성에서는 쓰기가 여전히 리더 한 곳을 거치고 복제본이 많아지면 변경을 전파하는 일도 늘어난다.

### 2. 단일 리더: 쓰기 순서를 한 곳에서 정한다

가장 쉬운 구성은 리더 한 대가 모든 쓰기를 받는 방식.
리더는 변경을 복제 로그로 전달하고 팔로워는 그 순서대로 자신의 데이터에 적용한다.
읽기는 리더와 팔로워에서 처리할 수 있지만 팔로워가 아직 변경을 받지 못했다면 오래된 값이 보인다.

```text
쓰기 요청 → 리더 → 변경 로그 → 팔로워 A
                         └→ 팔로워 B
읽기 요청 → 리더 또는 팔로워
```

#### 2.1 동기식과 비동기식은 언제 성공이라고 답할지의 차이

동기식 복제에서는 지정한 팔로워가 변경을 받았다는 확인을 기다린다.
그 팔로워에 사본이 있다는 점은 든든하지만 응답이 느리거나 연결이 끊어지면 쓰기도 기다리게 된다.
확인 시점이 수신인지 디스크 기록인지 등은 시스템의 구체적인 보장에 따라 확인해야 한다.

비동기식 복제에서는 팔로워의 확인을 기다리지 않고 성공을 응답한다.
팔로워가 잠시 느려도 쓰기를 계속 받을 수 있지만 변경이 전달되기 전에 리더를 잃으면 이미 성공했다고 응답한 쓰기가 사라질 수 있다.

모든 팔로워가 확인할 때까지 기다리면 한 대의 문제도 전체 쓰기를 막을 수 있다.
그래서 일부 팔로워만 동기식으로 유지하고 나머지는 비동기식으로 두는 구성도 사용한다.
동기식이라는 말만 보고 모든 복제본이 매 순간 같은 상태라고 생각하면 안 됨.

#### 2.2 새 팔로워는 파일만 복사하면 되나?

운영 중인 DB의 파일을 무작정 복사하면 복사 도중 데이터가 바뀌어 서로 다른 시점의 내용이 섞일 수 있다.
일반적으로는 일관된 스냅샷을 만든 뒤 그 시점 이후의 로그를 따라잡게 한다.

1. 리더의 일관된 스냅샷을 얻고 해당 시점의 로그 위치를 확인한다.
2. 스냅샷을 새 팔로워에 복사한다.
3. 스냅샷 이후에 발생한 변경을 로그로 전달한다.
4. 밀린 변경을 적용하면 정상적인 복제를 이어간다.

스냅샷을 복사하는 동안 생긴 쓰기도 놓치지 않으려면 스냅샷과 로그 위치가 연결돼 있어야 한다.

#### 2.3 팔로워 장애보다 리더 장애가 까다롭다

팔로워는 복구 후 마지막으로 적용한 로그 다음부터 따라잡을 수 있다.
물론 필요한 로그가 이미 지워졌다면 스냅샷부터 다시 준비해야 할 수 있다.

리더가 고장 나면 새 리더를 고르고 클라이언트의 쓰기를 새 리더로 보내고 나머지 팔로워도 새 리더를 따르게 해야 한다.
이 과정에서 다음 문제가 생긴다.

- 비동기 복제 중이었다면 새 리더가 이전 리더의 마지막 쓰기를 모를 수 있다.
- 이전 리더가 돌아오면 두 노드의 데이터가 달라져 있을 수 있다.
- 일시적인 네트워크 지연을 장애로 오해해 살아 있는 리더를 교체할 수도 있다.
- 이전 리더가 계속 쓰기를 받으면 스플릿 브레인이 된다.

타임아웃을 짧게 잡으면 장애에는 빨리 반응하지만 정상 노드를 오해할 가능성이 커진다.
길게 잡으면 잘못된 판단은 줄어들지만 서비스가 기다리는 시간이 길어진다.
따라서 자동 장애 복구는 단순히 예비 서버를 켜는 기능으로 보기 어렵다.

### 3. 변경을 어떤 형태로 복제할까?

| 방식 | 전달하는 내용 | 생각할 점 |
| --- | --- | --- |
| 구문 기반 복제 | 실행한 SQL 같은 명령 | 현재 시간이나 난수, 실행 순서에 의존하는 명령은 그대로 재실행해도 결과가 달라질 수 있다 |
| 쓰기 전 로그(WAL) 전달 | 저장소 엔진이 기록한 낮은 수준의 변경 로그 | 정확한 변경을 전달하지만 저장소 형식과 버전에 강하게 묶일 수 있다 |
| 논리적 로그 복제 | 행 삽입·수정·삭제처럼 논리적인 데이터 변경 | 물리적 저장 형식과 분리하기 쉬워 다른 시스템으로 변경을 보내는 데도 유용하다 |
| 트리거 기반 복제 | 트리거 등이 별도 기록한 변경 | 필요한 데이터만 다루기 좋지만 애플리케이션과 운영의 복잡성이 늘 수 있다 |

예를 들어 `UPDATE ... SET updated_at = NOW()`라는 명령만 전달하면 각 노드의 실행 시점이 문제가 된다.
실제 결정된 값을 보내거나 특별한 처리를 해야 같은 결과를 만들 수 있다.
행의 변경을 보내는 방식은 이런 실행 환경 의존성을 줄일 수 있다.

### 4. 복제 지연은 사용자에게 어떤 모습으로 보이나

비동기 복제에서는 잠깐 동안 복제본마다 값이 다른 것이 자연스럽다.
문제는 그 차이가 사용자에게 어떤 행동으로 보이느냐.

#### 4.1 방금 쓴 글이 사라져 보인다: 자신이 쓴 내용 읽기

```text
1. 사용자: 프로필 이름을 '다영'으로 수정
2. 리더: 저장 성공 응답
3. 사용자: 프로필 화면 새로고침
4. 아직 변경을 못 받은 팔로워: 예전 이름 반환
```

사용자는 저장이 실패했다고 생각할 수 있다.
자신이 쓴 내용 읽기는 이런 상황을 막는다. 다른 사람의 최신 쓰기까지 모두 보장하는 것은 아니다.

자신이 수정할 수 있는 데이터는 리더에서 읽거나 쓰기 후 일정 시간 리더로 읽기를 보내는 방법을 생각할 수 있다.
다만 고정 시간만 기다리는 방식은 복제 지연이 그보다 길어지면 보장이 깨진다.
쓰기의 로그 위치를 기억하고 그 위치까지 따라잡은 복제본에서만 읽는 방식이 더 직접적이다.
여러 기기를 사용한다면 이 기준을 기기 사이에서도 공유할 방법이 필요하다.

#### 4.2 보였던 댓글이 다시 없어진다: 단조 읽기

첫 읽기는 변경을 적용한 팔로워 A와 다음 읽기는 뒤처진 팔로워 B로 갔다고 하자.
사용자는 새 댓글을 봤다가 새로고침 후에는 못 보게 된다.

단조 읽기는 이런 시간의 역행을 막는다.
같은 사용자의 읽기를 같은 복제본으로 보내는 방법이 있지만 그 복제본이 장애를 일으켜 다른 곳으로 옮길 때도 이전에 본 위치를 고려해야 한다.
단조 읽기가 보장되어도 처음부터 계속 오래된 데이터를 읽을 수는 있다.

#### 4.3 답변이 질문보다 먼저 보인다: 일관된 순서로 읽기

질문을 읽고 쓴 답변에는 인과관계가 있다.
그런데 질문과 답변이 서로 다른 파티션에 저장되고 복제 속도가 다르면 어떤 사용자에게는 답변만 먼저 보일 수 있다.

일관된 순서로 읽기는 이런 앞뒤가 뒤집힌 관찰을 막는다.
관련된 쓰기를 같은 파티션에서 처리하거나 서로 다른 파티션 사이의 인과적 의존성을 추적하는 접근이 필요하다.

세 보장은 모두 오래된 읽기와 관련 있지만 해결하려는 문제가 다르다.
“최신 데이터가 필요한가?”만 묻기보다 “어떤 순서와 어떤 사용자의 쓰기를 반드시 보여줘야 하는가?”를 따져보는 편이 구체적이다.

### 5. 다중 리더: 가까운 곳에서 쓰되 충돌을 감당한다

데이터센터가 여러 지역에 있다면 지역마다 리더를 두고 지역 간에는 비동기 복제를 할 수 있다.
사용자는 가까운 리더에 쓰므로 먼 데이터센터의 응답을 매번 기다리지 않아도 된다.
지역 간 연결이 끊겼을 때도 각 지역에서 쓰기를 계속 받을 여지가 생긴다.

오프라인 편집 앱도 비슷하게 볼 수 있다.
각 기기가 로컬에서 쓰기를 받고 다시 연결되면 다른 기기의 변경과 합친다.
공동 편집 역시 여러 위치에서 들어온 변경을 조정해야 한다.

#### 5.1 두 곳에서 같은 값을 바꾸면 누구 말을 따라야 할까?

두 리더가 모두 제목 `초안`을 알고 있다고 하면
A에서는 `복제 정리`, B에서는 `5장 메모`로 수정했다.
서로의 변경이 도착하기 전에 두 쓰기가 성공하면 단일 리더처럼 한 줄로 정해진 쓰기 순서가 없다.

| 접근 | 예시 | 비용 또는 한계 |
| --- | --- | --- |
| 충돌 회피 | 같은 사용자의 쓰기를 항상 같은 리더로 보낸다 | 리더 이동이나 장애 처리 때도 규칙을 유지해야 한다 |
| 한 값 선택 | 타임스탬프나 우선순위로 승자를 정한다 | 다른 수정 내용이 사라질 수 있다 |
| 값 병합 | 집합에 추가한 항목들을 합친다 | 모든 데이터가 의미 있게 합쳐지는 것은 아니다 |
| 충돌 보존 | 두 버전을 남기고 사용자나 애플리케이션이 해결한다 | 충돌을 보여주고 해소하는 로직이 필요하다 |

모든 복제본이 같은 값에 도달하는 것과 모든 사용자의 의도를 보존하는 것은 다르다.
어떤 방법이 맞는지는 데이터의 의미에 달려 있다. 제목 두 개를 단순히 이어 붙여도 좋은 제목이 되는 것은 아니다.

#### 5.2 연결 모양도 결과에 영향을 준다

리더들을 원형이나 별 모양으로 연결하면 중간 노드의 장애가 전파 경로를 끊을 수 있다.
모든 리더가 서로 연결된 구성은 경로가 많지만 같은 변경이 여러 경로로 도착하거나 변경 순서가 뒤집힐 수 있다.

예를 들어 행을 만든 뒤 수정했는데 수정 메시지가 먼저 도착할 수 있다.
변경의 출처를 기록해 순환 전달을 막고 필요한 의존 관계를 지키는 처리가 필요하다.
연결을 많이 만들었다고 충돌과 순서 문제가 자동으로 해결되지는 않는다.

### 6. 리더 없는 복제: 여러 사본에 직접 확인

리더 없는 구성에서는 클라이언트나 조정자가 여러 복제본에 쓰기를 보낸다.
조정자가 있다고 해서 단일 리더인 것은 아니고 모든 쓰기의 순서를 전담해서 정하는지에 차이가 있다.
읽기도 여러 복제본에 보내고 버전 정보를 비교해 오래된 응답을 구분한다.

#### 6.1 정족수의 기본 아이디어

한 키의 복제본 수를 `n`, 쓰기 성공에 필요한 응답 수를 `w`, 읽기에 필요한 응답 수를 `r`이라고 하자.
`n = 3`, `w = 2`, `r = 2`라면 같은 세 복제본 안에서 쓰기 집합과 읽기 집합은 적어도 한 곳에서 겹친다.

```text
쓰기 성공: A, B에 기록
읽기 응답:    B, C에서 읽음
             ↑
        두 집합이 겹치는 노드
```

이 겹침 덕분에 완료된 쓰기를 가진 복제본의 응답을 얻을 수 있다.
하지만 응답 중 어떤 버전을 선택할지, 동시 쓰기는 어떻게 처리할지까지 이 부등식이 정해 주지는 않는다.

#### 6.2 `w + r > n`이면 무조건 최신 값을 읽어?

그렇게 단정할 수는 없다. 아래와 같은 조건을 함께 봐야 한다.

- 읽기와 쓰기가 겹쳐 실행되면 읽기가 일부 변경만 관찰할 수 있다.
- 쓰기가 정족수를 못 채워 실패해도 일부 복제본에는 이미 기록됐을 수 있다. 실패 응답이 전체 롤백을 뜻하지 않는다.
- 동시 쓰기 사이에는 인과적으로 하나의 최신 값을 고를 수 없을 수 있다.
- 타임스탬프로 값을 고르면 시계 오차 때문에 실제로 나중에 한 쓰기가 버려질 수 있다.
- 느슨한 정족수에서는 읽기와 쓰기의 응답 집합이 원래 복제본 집합 안에서 겹친다는 전제가 깨질 수 있다.

정족수는 복제본 집합의 교집합을 만드는 도구다.
그 조건만으로 선형성처럼 더 강한 일관성이 자동으로 생기지는 않는다.

#### 6.3 누락된 복제본은 어떻게 따라잡을까?

읽기 복구는 읽기 응답을 비교하다 오래된 복제본을 발견하면 빠진 변경을 전달한다.
자주 읽는 데이터는 이 과정으로 맞춰질 수 있지만 아무도 읽지 않는 데이터는 계속 뒤처질 수 있다.
안티 엔트로피는 백그라운드에서 복제본들을 비교해 이런 차이도 줄인다.

느슨한 정족수에서는 원래 담당 노드가 사용할 수 없을 때 다른 노드에 임시로 쓰기를 맡길 수 있다.
원래 노드가 돌아오면 암시된 핸드오프로 데이터를 전달한다.
장애 중 쓰기를 받아들이기에는 유리하지만 임시 노드에만 있는 변경을 일반 읽기가 놓칠 수 있다는 점을 생각해야 한다.

### 7. 동시 쓰기는 시각만 비교해서 판단하지 않는다

A가 쓴 값을 B가 읽고 수정했다면 B의 쓰기는 A의 쓰기 이후라는 인과관계가 있다.
반대로 서로의 결과를 모른 채 수정했다면 실제 시계상 몇 초 차이가 나더라도 동시 쓰기로 취급할 수 있다.
여기서 동시는 정확히 같은 시각이라는 뜻이 아니다.

LWW는 한 값을 남기므로 구현과 수렴 규칙이 단순해진다.
대신 성공한 쓰기까지 버릴 수 있다. 서버의 시계가 맞지 않으면 사용자가 나중에 수정한 값이 이긴다는 보장도 없다.
데이터 손실을 받아들일 수 있는지 먼저 판단해야 한다.

#### 7.1 버전 번호에서 버전 벡터로

한 서버가 버전을 관리하는 예에서는 읽을 때 값과 버전 번호를 받고 쓸 때 자신이 읽었던 버전을 함께 보낼 수 있다.
서버는 그 정보를 보고 이전 값을 대체하는 쓰기인지와 다른 변경을 모르고 보낸 동시 쓰기인지 구분한다.

여러 복제본이 독립적으로 쓰기를 받으면 단일 버전 번호만으로 각 복제본의 이력을 표현하기 어렵다.
버전 벡터는 복제본별 버전 정보를 묶어서 어떤 변경들을 이미 알고 있는지 나타낸다.
한 벡터가 다른 벡터의 모든 항목 이상이고 일부 항목에서는 더 크면 후속 버전으로 판단할 수 있다.
어느 쪽도 다른 쪽을 포함하지 않으면 동시 버전이다.

이 정보는 충돌을 찾아내는 데 쓰인다.

#### 7.2 장바구니를 합치는 것도 삭제 때문에 어려워진다

두 기기에서 각각 우유와 빵을 추가했다면 합집합으로 둘 다 남길 수 있다.
하지만 한 기기에서 우유를 삭제했고 다른 기기에 예전 우유 항목이 남아 있다면, 단순 합집합은 삭제한 우유를 되살린다.

그래서 삭제도 변경으로 표현해야 한다. 툼스톤이 그 예시
삭제 표시를 언제까지 보관할지도 중요하다. 오래 끊겨 있던 복제본이 돌아왔을 때 삭제 사실을 모르면 예전 데이터가 다시 나타날 수 있다.
병합 규칙은 추가뿐 아니라 수정과 삭제까지 함께 다뤄야 한다.

## 용어정리

| 용어 | 이해 |
| --- | --- |
| 복제(replication) | 같은 데이터를 여러 노드에 유지하는 것 |
| 복제본(replica) | 복제된 데이터를 보관하는 노드 또는 그 데이터 사본 |
| 리더(leader) / 팔로워(follower) | 쓰기를 받아 변경 순서를 정하는 노드 / 리더의 변경을 전달받아 적용하는 노드 |
| 동기식 / 비동기식 복제 | 지정한 복제본의 확인을 기다린 뒤 쓰기 성공을 알리는 방식 / 그 확인을 기다리지 않는 방식 |
| 복제 지연(replication lag) | 리더의 변경이 다른 복제본에 반영되기까지 생기는 시간 차이 |
| 장애 복구(failover) | 리더가 정상적으로 역할을 수행하지 못할 때 다른 노드가 리더 역할을 이어받는 것 |
| 스플릿 브레인(split brain) | 둘 이상의 노드가 자신을 리더로 여기고 쓰기를 받는 상황 |
| 최종적 일관성(eventual consistency) | 새 쓰기가 멈추고 변경 전파와 충돌 처리가 계속 진행되면 복제본들이 결국 같은 상태로 수렴하는 성질 |
| 자신이 쓴 내용 읽기(read-your-writes) | 성공한 자신의 쓰기가 이후 자신의 읽기에서 보이는 보장 |
| 단조 읽기(monotonic reads) | 한 번 본 상태보다 이전 상태로 되돌아가 읽지 않는 보장 |
| 일관된 순서로 읽기(consistent prefix reads) | 원인과 결과처럼 순서가 있는 쓰기를 읽을 때 그 순서가 뒤집혀 보이지 않는 보장 |
| 다중 리더(multi-leader) | 여러 노드가 쓰기를 받아 서로 변경을 전파하는 구성 |
| 리더 없는 복제(leaderless replication) | 모든 쓰기를 전담하는 리더 없이 여러 복제본에 읽기와 쓰기를 보내는 구성 |
| 정족수(quorum) | 읽기나 쓰기의 성공을 판단할 때 필요한 복제본 응답 수 또는 그 집합 |
| 느슨한 정족수(sloppy quorum) | 원래 담당 복제본이 응답하지 못하면 다른 노드의 응답도 받아 작업을 처리하는 방식 |
| 암시된 핸드오프(hinted handoff) | 다른 노드가 임시로 보관한 쓰기를 원래 담당 노드가 복구되면 넘겨주는 것 |
| 읽기 복구(read repair) | 읽는 도중 발견한 오래된 복제본에 최신 데이터나 누락된 버전을 전달하는 것 |
| 안티 엔트로피(anti-entropy) | 복제본들이 백그라운드에서 데이터를 비교하고 빠진 변경을 교환하는 과정 |
| 동시 쓰기(concurrent writes) | 서로의 결과를 알지 못한 채 발생해 인과적인 선후 관계를 정할 수 없는 쓰기 |
| 최종 쓰기 승리(LWW, last write wins) | 타임스탬프 등의 정렬 기준으로 한 쓰기를 선택하고 나머지를 버리는 충돌 처리 방식 |
| 버전 벡터(version vector) | 복제본별 버전 정보를 함께 관리해 어떤 변경을 이미 알고 있었는지 추적하는 구조 |
| 툼스톤(tombstone) | 삭제했다는 사실을 다른 복제본에도 전달하기 위해 남기는 표식 |

## 읽은 후

- 단일 리더는 쓰기 순서를 정하기 쉽지만 리더 장애와 복제 지연을 다뤄야 한다.
- 다중 리더는 여러 곳에서 쓰기를 받는 대신 충돌 해결이 필요하다.
리더 없는 복제는 여러 복제본의 응답을 이용하지만 정족수와 복구 절차만으로 모든 일관성 문제가 사라지지는 않는다.

먼저 정해야할 것은 사용자에게 허용할 수 있는 동작이다.
조회 수가 잠깐 늦게 보이는 것과 방금 수정한 프로필이 예전 값으로 보이는 것은 다른 문제다.
데이터마다 필요한 보장을 정한 뒤 복제 방식과 읽기 경로를 고르는 편이 이해하기 쉽다.
