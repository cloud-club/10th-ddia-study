호환성 이해하기

1. Intro

4장에서 상위 호환성과 하위 호환성을 읽고, 실제 코드에서는 어떻게 적용되는지 궁금했다.

이 원리를 Jackson의 @JsonIgnoreProperties(ignoreUnknown = true)에 연결해 봤다. 모르는 필드를 무시하면 읽기에 성공할 수 있는데, 그렇다면 그 데이터를 다시 저장할 때도 안전할까?

2. 기본 응답과 DTO

서버는 이름을 응답하고, 클라이언트도 이름을 담을 DTO를 가지고 있다.

{
  "name": "dayoung"
}
public static class User {
  public String name;
}

JSON의 name을 DTO의 name에 넣으면 된다. 응답과 DTO가 알고 있는 필드가 일치하므로 이름을 읽을 수 있다.

3. 서버 응답의 필드 추가

서버 응답에 email이 추가됐다. 클라이언트는 아직 DTO를 바꾸지 않아 name만 알고 있다.

{
  "name": "dayoung",
  "email": "hello@example.com"
}
  • name: DTO에 매핑할 수 있는 필드
  • email: DTO에 정의되지 않은, 알 수 없는 필드

Jackson이 알 수 없는 필드를 거부하도록 설정돼 있다면 읽기에 실패한다. 여기서는 비교 조건을 분명히 하기 위해 이 옵션을 직접 켠다.

ObjectMapper mapper = new ObjectMapper()
    .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);

mapper.readValue(json, User.class);
// UnrecognizedPropertyException: 알 수 없는 필드 email

서버가 필드를 추가했을 뿐인데 클라이언트가 응답 전체를 읽지 못하는 상황이다.

4. ignoreUnknown 설정

DTO에 다음과 같이 설정하면 알 수 없는 필드를 무시하고 읽는다.

@JsonIgnoreProperties(ignoreUnknown = true)
public static class User {
  public String name;
}
  • name은 DTO에 담는다.
  • email은 DTO에 정의돼 있지 않으므로 건너뛴다.
  • 클라이언트는 기존처럼 name을 사용할 수 있다.
필요한 필드만 읽으면 되는 상황에서 사용할 수 있다.

응답에 필드가 늘어났더라도, 클라이언트가 당장 그 필드를 사용해야 하는 것은 아니다. 이 설정은 필요한 데이터를 계속 읽을 수 있게 하는 선택이다.

필드 처리 방식 비교

브라우저에서 Jackson을 실행하는 대신, 아래 전체 Java 예제의 필드 매핑 결과를 재현한다. 입력과 DTO는 고정돼 있다.

서버 응답

클라이언트 DTO

알 수 없는 필드를 거부하면 email에서 읽기가 실패한다. ignoreUnknown = true이면 읽기에 성공하고 DTO에 name=dayoung이 담긴다.

전체 Java 예제 펼쳐보기

Jackson 2.x의 두 DTO를 같은 ObjectMapper로 읽어 비교한다.

import com.fasterxml.jackson.annotation.JsonIgnoreProperties;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.exc.UnrecognizedPropertyException;

public class JacksonUnknownDemo {
  public static class StrictUser {
    public String name;
  }

  @JsonIgnoreProperties(ignoreUnknown = true)
  public static class TolerantUser {
    public String name;
  }

  public static void main(String[] args) throws Exception {
    ObjectMapper mapper = new ObjectMapper()
        .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
    String json = "{\"name\":\"dayoung\","
        + "\"email\":\"hello@example.com\"}";

    try {
      mapper.readValue(json, StrictUser.class);
    } catch (UnrecognizedPropertyException e) {
      System.out.println("모르는 필드: " + e.getPropertyName());
    }

    TolerantUser user = mapper.readValue(json, TolerantUser.class);
    System.out.println(user.name); // dayoung

    user.name = "dayoung-updated";
    System.out.println(mapper.writeValueAsString(user));
    // {"name":"dayoung-updated"}
  }
}

5. 상위 호환성과 하위 호환성

방향상황확인할 점
상위 호환성기존 클라이언트가 필드가 추가된 서버 응답을 읽음알 수 없는 필드를 처리할 수 있는가?
하위 호환성email을 추가한 클라이언트가 name만 있는 서버 응답을 읽음응답에 없는 email을 처리할 수 있는가?

지금의 ignoreUnknown 예시는 기존 클라이언트가 새 필드를 포함한 응답을 받아들이는 상위 호환성과 연결된다.

반대 방향에서는 응답에 email이 없을 수 있다. 기본값을 쓸지, 없는 값을 허용할지, 필수 값 검증을 할지는 별도로 정해야 한다. 알 수 없는 필드를 무시하는 설정이 누락 필드까지 해결하지는 않는다.

6. 적용 기준

  • 외부 서비스의 응답을 읽는 클라이언트: 사용하지 않는 필드가 추가돼도 필요한 필드를 계속 읽도록 허용할 수 있다.
  • 입력 계약을 엄격히 검사하는 API: 알 수 없는 필드를 허용하면 email을 emial로 잘못 보낸 요청도 놓칠 수 있다. 이 경우에는 거부하는 정책이 더 적절할 수 있다.
  • 필드 타입이나 의미가 바뀌는 경우: 이미 아는 필드의 타입 불일치나 필수 값 검증은 따로 처리해야 한다.

7. 확장 / 재직렬화

읽은 데이터를 다시 JSON으로 만드는 경우

필요한 필드만 읽는 목적이라면 앞의 동작으로 충분하다. 다만 DTO를 다시 JSON으로 만드는 작업까지 한다면, DTO에 보관한 필드만 출력된다는 점을 확인해야 한다.

TolerantUser user = mapper.readValue(json, TolerantUser.class);
user.name = "dayoung-updated";
String output = mapper.writeValueAsString(user);
// {"name":"dayoung-updated"}

email은 DTO에 없기 때문에 결과에 포함되지 않는다. ignoreUnknown이 직렬화할 때 필드를 지우는 것이 아니라, 읽는 과정에서 DTO가 그 필드를 보관하지 않은 결과다. 이것이 설정 자체가 잘못됐다는 뜻은 아니다.

현재 비교 설정의 재직렬화 결과

ignoreUnknown = true로 읽은 DTO의 이름을 수정하면 {"name":"dayoung-updated"}로 직렬화된다. 거부 모드에서는 읽기가 실패하므로 수정과 직렬화를 진행하지 않는다.
